# CloudHSM 키 생성에 승인자 공개키를 활용하는 방법

조사일: 2026-10-11. 상태: 조사와 설계 제안. 실제 환경 시험과 행사 통제 채택은 아직 수행하지 않았다.

## 1 조사 결론

승인자 3인의 공개키를 활용해 키 생성 전 다인 승인을 구현할 수 있다. 다만 공개키 등록·공유 사용자 지정만으로 CloudHSM이 생성 요청에 대한 세 사람의 동의를 확인하지는 않는다. **생성 계획에 대한 승인 서명과, 승인 없이는 실행 경로를 사용할 수 없게 하는 통제**를 함께 추가해야 한다.

AWS의 생성 명령에 직접 다인 승인 토큰을 넣는 기능은 확인하지 못했다. 아래의 생성 승인 실행기는 공개 기능을 바탕으로 제안하는 별도 설계이며 AWS가 제공하는 키 생성 quorum 기능이라는 뜻이 아니다. 실제 행사 문서의 생성 통제는 보류 상태로 유지한다.

## 2 공개키가 등록되는 위치

AWS CU quorum 설정 안내는 먼저 각 CU가 자신의 승인용 공개키를 사용자 계정에 등록하고 등록 토큰에 서명해 대응 개인키 보유를 증명하도록 설명한다. 이 등록은 향후 quorum 승인자를 준비하는 절차다. [AWS CU quorum 초기 설정](https://docs.aws.amazon.com/cloudhsm/latest/userguide/key-quorum-auth-chsm-cli-first-time.html)

Root·First 개인키를 생성하는 명령은 승인자 공개키 파일을 인자로 받지 않는다. 대신 `--share-crypto-users`로 공유 CU 이름을, `--use-private-key-quorum-value`와 `--manage-private-key-quorum-value`로 이후 사용·관리 정족수를 지정한다. 문서의 생성 명령 문법에는 `--approval`이 없다. [AWS EC 키 생성 명령](https://docs.aws.amazon.com/cloudhsm/latest/userguide/cloudhsm_cli-key-generate-asymmetric-pair-ec.html)

| 동작 | 확인하는 것 | 확인하지 않는 것 |
|---|---|---|
| 승인 공개키 등록 | 해당 계정의 승인키와 대응 개인키 보유 | 이후 특정 Root 생성 요청에 대한 동의 |
| 생성 시 사용자 공유와 quorum 지정 | 생성된 키의 사용자 연결 및 이후 승인 정책 | 이번 생성 요청에 대한 3인의 승인 서명 |
| 연결 사용자 수 검사 | 지정 정족수에 필요한 사용자 수 | 연결된 사람들이 이번 생성 내용을 읽고 승인했는지 |
| 지원되는 서명 작업의 quorum 검사 | 해당 작업에 유효한 승인 토큰과 승인 서명 | 지원 목록에 없는 생성 명령의 승인 |

사용자 연결 수가 정족수보다 작으면 생성이 실패한다. 연결 수에는 키 소유자도 포함된다. 그러나 공개된 생성 문법에서는 이를 특정 생성 계획의 승인 검사로 사용할 수 없다. [AWS 초기 설정의 생성 시 사용자 수 조건](https://docs.aws.amazon.com/cloudhsm/latest/userguide/key-quorum-auth-chsm-cli-first-time.html), [quorum 지원 작업 목록](https://docs.aws.amazon.com/cloudhsm/latest/userguide/cloudhsm_cli-qm.html)

공개키는 공개 정보이므로 파일을 세 개 넣었다는 사실만으로 세 사람의 참여를 입증할 수 없다. 특정 계획을 각자의 개인키로 서명해야 그 계획에 대한 승인 증거가 된다.

## 3 승인자 3명과 실행자 포함 여부

| 인원 구성 예시 | 정족수 해석 |
|---|---|
| 소유자 O를 포함한 O·A·B 총 3명 | 3 of 3은 세 계정 모두의 승인 |
| 소유자 O와 별도 승인자 A·B·C 총 4명 | 값 3은 연결된 4명 중 3명. O도 승인할 수 있으면 O·A·B로 충족할 수 있어 C를 반드시 요구하지 않음 |

AWS는 요청자가 자신의 quorum 토큰에 서명할 수 있다고 명시한다. 따라서 “별도 수락자 A·B·C 모두 필수”라는 사람 정책과 숫자 3은 같지 않다. 모든 연결 사용자가 승인 가능한 위 예시에서 4 of 4는 O까지 필수로 만들며, 외부 실행기에서 A·B·C 세 명을 명시적으로 요구하는 방법은 별도 설계다. [AWS quorum 고려사항](https://docs.aws.amazon.com/cloudhsm/latest/userguide/key-quorum-auth-chsm-cli.html)

실행자의 승인키 등록 여부·변경 권한까지 검토해야 한다. 단순히 현재 등록하지 않았다는 이유만으로 장래에도 실행자가 승인할 수 없다고 가정하지 않는다. 위 수치는 설명용이며 실제 정족수 채택은 아니다.

## 4 제안하는 생성 승인 흐름

다음은 같은 전용 EC2의 앱과 CLI 구조에서 검토할 수 있는 방식이다. 본문 작성 앱과 별도로 승인 검사·실행 권한을 담당하는 구성 요소가 필요하며, 실제 구현은 아직 없다.

1. **생성 계획 고정:** Root와 First 각각 별도 작업 ID로 계획 파일을 만든다. 아래 항목과 정확한 생성 옵션을 포함한다. 승인자는 아직 존재하지 않는 새 공개키가 아니라 생성할 조건을 승인한다.
2. **3인 승인:** A·B·C가 같은 계획 파일의 정확한 바이트를 각각 본인의 개인키로 서명한다. 개인키는 각자 보관하고 실행 EC2 한 곳에 모으지 않는다.
3. **실행 전 검사:** 생성 실행기가 보호된 승인자 공개키 목록으로 세 서명을 검사한다. 승인자 신원, 계획 해시, 기한, 대상 클러스터, 미사용 작업 ID와 실행본을 대조한다. 요청자가 제출한 임의 공개키 목록은 신뢰하지 않는다.
4. **제한된 생성:** 검사에 통과한 계획의 옵션으로만 CloudHSM CLI를 실행한다. 일반 작업자 계정이 생성 CU의 인증 수단·로그인 세션을 직접 사용할 수 없게 하고 직접 CLI·다른 SDK·다른 호스트 실행 경로를 차단한다.
5. **결과 확인과 종료:** 공개키·개인키 식별자·공유 사용자·속성·사용 quorum을 조회해 계획과 비교한다. 승인·요청·응답을 기록하고 생성 접근을 종료한다. 이후 Root/First 서명에는 이미 결정한 HSM 서명 quorum을 사용한다.

| 생성 계획에 포함할 것 | 목적 |
|---|---|
| 승인 문서 종류·판본 | MFA·quorum 토큰이나 다른 승인 문서를 생성 승인으로 혼용하지 않음 |
| 행사 ID·Root/First 구분·작업 ID·만료 시각 | 대상 식별, 다른 행사 사용과 재사용 방지 |
| AWS 계정·Region·클러스터 ID·HSM 모델·모드 | 다른 환경에서 승인 사용 방지 |
| 알고리즘·곡선/키 길이·라벨·속성 | 승인 이후 생성 옵션 변경 방지 |
| 소유 CU·공유 CU·사용/관리 quorum | 보호되지 않은 다른 키 생성 방지 |
| 승인자 신원·공개키 지문·필수 승인 집합 | 키 바꿔치기와 동일인 중복 승인 방지 |
| 실행기·CLI·설정의 승인 버전과 해시 | 다른 프로그램이나 설정으로 실행 방지 |

승인·실행 중 상태는 내구 저장하고 동시 실행과 재사용을 막는다. 요청 전 기록, 응답 저장, 결과 확인 사이에 장애가 나면 동일 계획을 자동으로 재실행하지 않는다. 먼저 이미 생성된 키가 있는지 확인하고, 결과 불명은 조사·재승인 절차로 넘긴다. “1회 승인” 설계만으로 분산 시스템의 모든 장애 구간에서 정확히 한 번 생성을 보장할 수는 없다.

## 5 승인키를 재사용할 수 있는가

암호학적으로 같은 승인 RSA 키로 별도의 생성 계획 서명을 만드는 설계를 고려할 수 있다. 그러나 HSM에 공개키를 등록했다는 사실만으로 외부 실행기에 그 사람의 신원·권한이 전달되지는 않는다. 승인된 사람·계정·공개키 지문 목록을 별도로 고정해 대조해야 한다.

외부 계획 승인에는 다른 종류의 문서임을 식별하는 형식, 서명 알고리즘, 정확한 바이트와 서명 검증 규칙이 필요하다. AWS quorum 토큰을 임의 생성하거나 service 이름을 key-generation으로 바꾸는 방식은 제안하지 않는다. 기존 토큰은 지정된 지원 작업에 사용하는 것이며 외부 생성 실행기의 승인 문서는 별도 프로토콜이다. [AWS quorum 토큰 사용과 작업 대응](https://docs.aws.amazon.com/cloudhsm/latest/userguide/key-quorum-auth-chsm-cli-crypto-user.html)

실제 승인키 보관 도구가 생성 계획 서명도 허용하는지 확인해야 한다. 인증용 키와 일반 문서 승인용 키의 혼용을 피해야 하는 정책이 있다면, 같은 세 사람이 별도 생성 승인키를 사용하는 방식으로 분리한다.

## 6 가능한 방식 비교

| 방식 | 다인 통제의 위치 | 평가 |
|---|---|---|
| 사용자 3명 연결과 사용 quorum만 설정 | 생성된 키의 이후 HSM 작업 | 생성 자체의 다인 승인 근거로는 부족 |
| 3인이 생성 계획에 서명하고 사람이 CLI 실행 | 절차와 승인 증적 | 명확한 승인 기록은 가능. 실행자가 계획을 무시할 수 있으면 기술적 강제는 없음 |
| 3인 서명을 확인하는 제한된 생성 실행기 | 승인 증적과 호스트·인증 수단·접속 경로 | 우회 경로 차단을 구현·시험하면 생성 전 다인 통제로 검토 가능 |
| 생성 CU 로그인에 MFA를 사용하고 인증 수단을 분리 | 로그인·활성화 단계 | 다인 참여를 추가하는 보조 통제. 로그인 후 명령별 승인이나 3인 정족수를 자동 보장하지 않음 |
| 별도 생성 승인용 HSM 키로 계획에 quorum 서명 | 승인서 서명은 HSM, 생성 허가는 외부 실행기 | 기존 승인자 키와 HSM quorum을 활용하는 추가 대안. 생성 명령 자체의 quorum은 아니며 구성 요소와 초기 설정이 늘어남 |

마지막 대안은 HSM의 서명 quorum으로 생성 계획에 대한 승인서를 만들고 실행기가 이를 검증하도록 설계하는 것이다. 이때도 승인자에게 표시한 계획과 실제 서명 입력을 연결해야 하고, 생성 CU의 직접 사용 경로를 막아야 한다. 별도 승인키의 최초 생성·등록·보호는 준비 단계에서 따로 통제해야 한다. 단순한 생성 승인 증적이 목적이라면 세 사람이 계획에 직접 서명하는 제안이 더 적은 구성 요소로 구현된다.

MFA의 경우 AWS는 비밀번호와 해당 사용자에 연결된 개인키로 로그인 토큰에 서명하는 방식을 제공한다. 인증 수단을 다른 사람에게 분리하는 것은 우리가 추가로 검토하는 활성화 설계이며, AWS MFA 자체가 다인 승인을 뜻하지 않는다. [AWS HSM MFA](https://docs.aws.amazon.com/cloudhsm/latest/userguide/login-mfa-token-sign.html)

## 7 우회 차단이 중요한 이유

CU는 키 생성 기능을 갖고 있다. 일반 작업자나 승인자가 사용 가능한 CU 로그인과 HSM 접속 경로를 보유한다면 승인 실행기를 거치지 않고 다른 키를 생성할 수 있는지 검토해야 한다. Root 키 한 개에 설정한 사용 quorum이 클러스터 전체의 새로운 키 생성 정책이 되는 것은 아니다. [AWS CU 권한](https://docs.aws.amazon.com/cloudhsm/latest/userguide/understanding-users.html)

HSM 내부 작업은 IAM 정책 대신 HSM 사용자 인증을 사용한다. 그러므로 AWS IAM 역할 승인만 추가해서 생성 명령을 제어할 수 있다고 결론 내리지 않는다. IAM은 호스트·클러스터·네트워크 등 주변 관리 경로의 통제로 함께 사용한다. [AWS HSM 사용자와 IAM 구분](https://docs.aws.amazon.com/cloudhsm/latest/userguide/hsm-users.html)

실행자에게 자유로운 shell, 생성 CU 비밀번호와 세션, 실행기를 수정할 권한을 모두 주면 승인 검사 프로그램을 건너뛸 수 있다. 호스트 root, 코드 배포자, 승인자 목록 관리자, CU 비밀번호/MFA 재설정 관리자, 접속을 다시 열 수 있는 AWS 관리자의 단독 우회도 포함해 권한을 분리한다.

hsm2m.medium은 mTLS 강제와 그 설정 변경에 대한 admin quorum을 지원한다. 이를 허가된 실행 환경의 접속 제한과 단독 설정 변경 방지에 활용할 수 있다. mTLS 인증서 자체는 명령별 3인 승인 수단이 아니며, 클라이언트 개인키를 일반 작업자가 복사할 수 있으면 접속 제한을 우회할 수 있다. [AWS mTLS 강제와 승인](https://docs.aws.amazon.com/cloudhsm/latest/userguide/cloudhsm_cli-cluster-mtls-set-enforcement.html), [cluster quorum 범위](https://docs.aws.amazon.com/cloudhsm/latest/userguide/cloudhsm_cli-qm.html)

생성 접근 종료를 “생성 CU 삭제”로 설계하지 않는다. AWS는 키를 소유한 CU를 삭제할 수 없다고 명시한다. 키 소유 계정의 지속 보호와 세션 종료·인증 수단·접속 권한 회수는 별도로 설계해야 한다. [AWS CU 삭제 제약](https://docs.aws.amazon.com/cloudhsm/latest/userguide/delete-user-cloudhsm-cli.html)

## 8 C2PA 요구와 검증

CP v0.2는 CA 키 생성에 다인 통제와 지식 분할을 요구하지만, AWS의 key-generate 명령에 특정 quorum 토큰 옵션을 넣도록 지정하지 않는다. 따라서 외부 생성 승인 통제는 검토 가능한 구현 경로다. 실제 다인 통제와 단독 접근 방지가 입증되어야 하며, 승인 서명만으로 적합성이 확정되는 것은 아니다. [고정 CP 원문](https://github.com/c2pa-org/conformance-public/blob/2466172859fad1215f7aaf7e3768b41a0ac29abc/docs/v0.2/C2PA%20Certificate%20Policy.md)의 `Separation of Duties`, `Key Pair Generation and Installation by CAs`, `Key Usage and Access Control`을 근거로 한 설계 해석이다.

| 시험 | 확인할 결과 |
|---|---|
| 승인 없음·1명·2명·중복 계정·다른 공개키 | 실행 거부 |
| A·B·C의 같은 계획 승인 | 승인된 환경과 옵션으로 생성 허용 |
| 옵션·공유 사용자·quorum·클러스터·실행본 변경 | 새 승인 없이는 실행 거부 |
| 만료·동시 요청·사용 완료된 승인 재사용 | 실행 거부 |
| 일반 계정의 직접 CLI·SDK·다른 호스트 사용 | 생성 경로 접근 거부 또는 검증된 차단 |
| 관리자 1인의 인증 수단 재설정·코드/승인자 목록 교체 | 단독으로 통제를 무력화할 수 없는지 확인 |
| 생성 응답 유실·기록 실패 | 재생성 없이 상태 조사·중단 |
| 생성 후 조회 | 실제 속성·공유·정족수가 승인 계획과 일치 |
| 접근 종료·백업 복원 | 승인 경로 밖에서 재활성화·생성이 가능한지 검증 |

현재는 문서 조사와 설계 제안까지 완료했다. 기존 CLI 방식에서 작업자가 생성 CU를 직접 사용할지, 제한된 생성 실행기를 통해서만 사용할지 결정하고 시험해야 실제 통제로 채택할 수 있다.
