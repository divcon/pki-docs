# Root·First ICA 행사 초안의 C2PA v0.2 적합성 검토

검토일: 2026-10-11. 검토 대상: 프로젝트 commit `aa5371c5c8f83d26d6eee14d4579658041d43c07`의 `root-first-001/` 문서 묶음과 연결된 공통 준비 체크리스트. 실제 키·CSR·인증서·HSM 환경은 검증하지 않았다.

2026-10-12 후속 상태: C03의 필수 조건을 [설정표와 CSR 설정](settings.md#승인-설정)에 작성하고, [프로파일/schema 차이](settings.md#프로파일과-schema-차이-처리)에 Root AKI·First AIA/CDP 외에 AIA caIssuers의 권고/실제 검사 차이를 추가했다. 관련 제약에 대해 합성 JSON 13건으로 기대 허용/거부 동작을 확인했다. C04는 S05/S07의 발급·인수 조건에, C01은 N01과 준비표의 승인 보류 조건에 연결했다. U04는 후속 사용자 결정으로 AIA + OCSP를 확정하고 CDP는 생략한다. OCSP·URL 제공 기능은 미구현이며 실제 URL·운영 값은 추후 결정이다. 남은 선택·실제 산출물 검사·외부 수용·상태 서비스 준비는 미완료이므로 C01/C03/C04를 닫지 않는다. 아래 본문은 10월 11일 검토 당시의 기록이며 최신 상태는 settings/preparation을 따른다.


2026-10-12 생성 승인 후속 상태: O·A·B 중 서로 다른 2명(2 of 3), O+A·O+B·A+B 허용으로 정책을 반영했다. script S01/S03의 승인 인원 문구를 명확히 했으며 아래 과거 정족수 미정 기록보다 최신 N02를 우선한다. 실제 통제 구현·검증이 남아 C02는 미해결이다.

**판정: 현재 초안을 C2PA 준수 완료로 승인할 수 없다.** P-384, ECDSA/SHA-384, 작업자 포함 서명 `2 of 3`, 개인키의 일반 반출 금지라는 선택 자체에서는 명시적 금지와의 충돌을 발견하지 못했다. 그러나 선택한 FIPS 판본과 CP 저장 문구가 일치하지 않으며, 생성 다인 통제·인증서 값·운영 증거가 아직 미완성이다. 현재 문서가 운영 수행 전 초안이고 미완료 상태를 명시한다는 점과, 그 상태로 실제 수행해도 된다는 판단은 구분한다.

## 검토 기준과 범위

기준은 사용자가 선택한 **Conformance Program v0.2 및 CP v0.2**다. 공식 저장소 commit `2466172859fad1215f7aaf7e3768b41a0ac29abc`의 원문 7개를 직접 대조했다. 로컬 원문 저장소의 HEAD·변경 없음과 [준비 현황](preparation.md#적용-원문-고정본)에 적힌 7개 SHA-256의 일치를 확인했다. 제출 시점에 적용 가능한 판본은 신청 전에 다시 확인해야 한다.

설계 문서는 검토 대상이며 요구사항의 근거가 아니다. 근거는 아래 공식 원문이다. 이번 검토는 행사 설계의 문서 검토이며, CA 조직 전체의 CP 준수 심사나 C2PA 승인 결과를 대신하지 않는다. 법인 계약·공개 업무관행·하위 CA/leaf 발급·서비스 전체 운영의 적합성은 별도 검토 대상이다.

| 공식 원문 | 이번 검토에 사용한 내용 |
|---|---|
| [Conformance Program][program] | 등록 대상 인증서의 프로파일 검증, 독립 입회한 키 생성과 서명된 스크립트, 신청·판본 |
| [Certificate Policy][cp] | CA 생성·서명·저장·사용·백업, 역할·접근·기록·상태 서비스, Root·First 프로파일 |
| [Root YAML][root-yaml] / [Root schema][root-schema] | Root 필드·확장, 두 자료 간 AKI 차이 |
| [First YAML][first-yaml] / [First schema][first-schema] | First 필드·확장, OCSP/CDP 조건과 schema 차이 |
| [First CSR schema][csr-schema] | 요청 Subject·공개키·요청 확장 |

아래의 ‘차단’은 이 검토에서 제안하는 운영 행사 승인 조건이다. C2PA가 이 문서의 점검 ID나 특정 AWS 구현을 요구한다는 의미가 아니다. ‘미입증’은 아직 구현·시험·증거가 없다는 뜻이며, 수행한 행사에서 실제 위반이 발생했다는 판정은 아니다.

## 먼저 해결할 사항

### C01 — FIPS 저장 조항과 선택 모델의 판본 불일치: 해석 미해결

**현재 상태:** [settings.md N01](settings.md#n01-cp의-fips-판본-문구-차이)은 `hsm2m.medium`의 FIPS 140-3 Level 3을 선택했고, 외부 수용 근거가 없다고 정확히 기록한다.

**원문 대조:** CP의 `Key Pair Generation and Installation by CAs`는 FIPS 140-2 또는 140-3 Level 2 이상을 허용하지만, `Controls for CA Keys / Key Storage`에는 FIPS 140-2 Level 2 이상만 적혀 있다. **140-3 Level 3이라는 사실만으로 저장 조항까지 충족했다고 판정할 수 없다.** [CP 생성·저장 조항][cp-keys]

AWS는 해당 모델을 FIPS 140-3 Level 3 및 CMVP 4703과 연결한다. NIST 인증은 승인 모드와 지정된 설치·구성 조건을 전제로 한다. 이 인증은 모듈의 보안 인증 근거이며 C2PA 저장 문구에 대한 예외 승인 근거는 아니다. [AWS 인증 안내](https://docs.aws.amazon.com/cloudhsm/latest/userguide/fips-validation.html), [NIST CMVP 4703](https://csrc.nist.gov/projects/cryptographic-module-validation-program/certificate/4703)

**닫는 조건:** 실제 모듈·펌웨어·FIPS 모드의 인증 대응 자료와, 이 구성의 저장 조항 적용에 대한 C2PA 측 해석·수용 근거를 확보한다. 확보 전에는 ‘저장 요구 충족’으로 승인하지 않는 것이 권고다. 단순히 오래된 모듈로 되돌리는 결정을 이 검토에서 내리지는 않는다.

### C02 — 생성 다인 통제와 전체 접근 통제: 설계·구현 미입증

**현재 상태:** [settings.md N02](settings.md#n02-키-생성-승인과-생성-시-quorum-설정의-구분), [권한표](settings.md#사람과-권한의-연결), [생성 검토안](key-generation-control-review.md)에 정족수·개인별 재료·제한된 실행·우회 차단이 미정으로 남아 있다. 서명·관리 quorum을 선택한 사실만으로 생성 요청이 다인 통제되는 것은 아니라는 구분은 맞다.

**원문 대조:** CA 키 생성은 신뢰 역할의 다인 통제와 지식 분할을 따라야 한다. 또한 Root·Intermediate 서명키에 한 사람이 단독으로 물리적·논리적 접근을 할 수 없도록 통제해야 한다. 따라서 생성 계획에 서명만 받고 작업자가 다른 명령·계정·호스트로 단독 생성하거나 통제를 우회할 수 있으면 충족을 입증하기 어렵다. [CP 생성·사용 통제][cp-keys]

**닫는 조건:** 생성 승인 인원, 각자 보유할 인증 재료와 권한, 승인된 계획만 실행하는 경로, 직접 CLI/API 및 관리자·코드 변경 우회 차단을 확정하고 테스트 키로 성공·거부 시험을 남긴다. 지식 분할을 어떤 재료와 권한의 분리로 충족하는지 별도로 설명한다. 승인키가 여러 개 있다는 사실만으로 충족을 선언하지 않는다.

**문구 보완:** script S01/S03의 ‘A/B가 승인’은 두 사람 모두인지 둘 중 누구인지 모호하다. 생성 정족수를 확정할 때 이 문장을 명시적인 인원·조합으로 교체한다. 이번 검토에서 생성 정족수를 새로 결정하지 않았다.

### C03 — 인증서와 CSR 필드: 미작성, 공식 자료 차이도 처리 필요

**현재 상태:** [설정표](settings.md#승인-설정)의 DN·기간·Serial·SKI/AKI·KU/EKU·Basic Constraints·정책 OID·AIA/CDP가 빈칸이다. 잘못된 값을 확정한 것은 아니지만, 아직 프로파일 적합성을 판정할 인증서 정의가 없다.

| 반드시 설정·검증할 항목 | Root | First ICA |
|---|---|---|
| 이름·형식·Serial | X.509 v3, 양수 Serial 최대 20 octets, C/O/CN 포함, Issuer=Subject | X.509 v3, 양수 Serial 최대 20 octets, C/O/CN 포함, Issuer=Root Subject |
| 공개키·서명 | 선택한 P-384와 ECDSA/SHA-384 허용 | 선택한 P-384와 ECDSA/SHA-384 허용 |
| SKI | non-critical, RFC 5280 Method 1의 SHA-1 | non-critical, 같은 방법 |
| AKI | 아래 YAML/schema 차이 처리 | 필수·non-critical, 발급자 키 식별 관계 검증 |
| Key Usage | critical, `keyCertSign`·`cRLSign`; schema는 다른 비트 false 요구 | Root와 동일 |
| Basic Constraints | critical, `cA=true`, `pathLenConstraint<=2`; 의도한 전체 체인을 수용하는 값 선택 | critical, `cA=true`, `pathLenConstraint=1` |
| Certificate Policies | 선택, 포함 시 non-critical | 필수·non-critical, `1.3.6.1.4.1.62558.1.1` 포함 |
| AIA/CDP | 둘 다 금지 | OCSP 주소가 있는 AIA 또는 CDP 필요. 포함된 주소·critical 조건 검사 |

근거: [Root YAML][root-yaml], [First YAML][first-yaml], [Root schema][root-schema], [First schema][first-schema]. YAML의 Root 20년·First 5년은 예시이며 이를 의무 유효기간으로 바꾸지 않는다. **HSM의 `sign=true`와 인증서의 `digitalSignature` 비트는 다른 항목이다. 서명 해시 SHA-384를 선택해도 SKI 계산까지 SHA-384로 바꾸면 안 된다.**

공식 자료 사이에서 확인한 차이는 다음과 같다.

1. **Root AKI:** YAML/CP 프로파일은 OPTIONAL이지만 Root schema의 확장 `contains`는 AKI 존재를 요구한다. AKI를 포함하는 안은 양쪽을 만족할 수 있으므로 설정 시 우선 검토할 수 있다. 아직 채택한 값은 아니다.
2. **First AIA/CDP:** YAML/CP는 OCSP AIA가 없으면 CDP, CDP가 없으면 OCSP AIA를 요구한다. 반면 First schema의 `c2paFirstIntermediateCaConstraints/allOf/5`는 `oneOf`를 사용하므로 두 분기를 모두 충족하는 OCSP AIA와 CDP를 함께 넣으면 이 조건을 통과하지 못한다. 양쪽 자료에 맞는 한 경로를 선택하거나, 둘 다 필요한 경우 적용 schema와 수용 근거를 확인해야 한다. 이 차이를 C2PA가 둘의 병행을 금지한 것으로 일반화하지 않는다.
3. **CSR:** First CSR schema는 critical인 CA Basic Constraints(`pathLen=1`), critical인 `keyCertSign`·`cRLSign`, non-critical인 C2PA 정책 OID를 요청 확장으로 요구한다. 최종 인증서만 검사하고 CSR 검사를 생략하지 않는다. [CSR schema][csr-schema]

**닫는 조건:** 필드별 최종 값·근거·critical 여부를 승인하고, 테스트 CSR/인증서로 schema 검사와 별도 의미·서명·체인 검사를 수행한다. schema 통과만으로 Issuer 연결·SKI/AKI 계산·실제 서명 검증까지 완료되었다고 간주하지 않는다. 이번에는 schema 정의를 정적으로 대조했으며 인증서 검증기를 실행한 결과는 없다.

### C04 — First 인증서 상태 제공 시점: ‘서비스 개시 제외’와 구분 필요

**현재 상태:** script S07은 미가동 상태 서비스에 담당자·기한·운영 개시 제한을 기록하도록 한다. 공통 준비 체크리스트 D13도 주소는 발급 전, 서비스는 운영 개시 전으로 구분한다. 하지만 이번 행사에서는 이미 First 인증서를 발급한다.

**원문 대조:** Subordinate CA 인증서에 OCSP를 제공하지 않으면 CRL로 상태를 제공해야 한다. CP의 Lifecycle Security Controls도 상태 정보의 가용성을 요구한다. 행사 범위에서 서비스 개시를 제외한 것만으로 발급한 First 인증서의 상태 제공 의무가 면제되는 것은 아니다. [CP 상태 서비스][cp-status], [CP 생명주기 통제][cp-lifecycle]

**판정:** 아직 실제 미가동 인증서를 발급한 것은 아니므로 발생한 위반으로 판정하지 않는다. 다만 CP에 명시된 유예를 확인하지 못했으므로 ‘나중에 서비스 시작할 때 준비하면 된다’고 확정해서는 안 된다.

**닫는 조건:** First 상태의 제공 주체·OCSP 또는 CRL 방식·인증서에 넣을 주소·가동 및 인수 시점을 발급 승인 전에 정한다. 권고는 First 발급 시점에 상태 제공을 준비하는 것이다. 늦출 계획이라면 허용되는 시점과 제한의 근거를 먼저 확보한다. OCSP 위임 응답자 등 추가 산출물이 필요하면 별도 준비 작업과 이번 행사의 선행 조건으로 연결한다.

### C05 — 백업·off-site·보존: 방향은 맞지만 충족 증거 없음

**현재 상태:** 암호화된 CloudHSM 백업, 원본과 같은 다인 통제, 복원 후 현재 정책 대조를 선택했다. off-site 사본·권한·복원 시험·보존은 미정이다. 공통 체크리스트 D10에는 연간 검토 담당자를 정할 항목도 있으나 행사별 정책으로 확정되지 않았다.

**원문 대조:** CP는 연 1회 검토하는 공식 백업·복구 계획, 모든 CA 개인키 백업의 관리 및 동일한 다인 통제, 최소 한 개 off-site 사본, 모듈 밖 평문 백업 금지를 요구한다. 동시에 CA 개인키의 archival을 금지한다. [CP 백업·archival][cp-storage]

**닫는 조건:** 백업 사본의 위치와 off-site 판단 근거, 전체 사본 목록·수명·권한·연간 검토자, 신규 키 및 최종 통제의 포함 확인, 복구 후 동일 키·현재 통제의 유지 시험을 작성한다. 자동 백업이 존재한다는 사실만으로 전부 충족했다고 하지 않는다. 복구용 백업과 퇴역 후 개인키의 장기 archival을 구분하고, 감사 기록 보존을 이유로 개인키를 무기한 남기지 않는 정책을 정한다.

### C06 — 신뢰 역할·MFA·코드·로그: 구체 정책과 증거 미완성

**현재 상태:** 역할 적격성·교육 확인, MFA·코드 해시·로그 수집·권한 연결의 준비 항목은 있으나 실명·겸임·통제 구현·시험 결과가 없다. ‘작업자 계정만 EC2 접근 가능’과 ‘quorum 2’라는 설정만으로 전체 요구가 충족되지는 않는다.

**원문 대조:** CP는 중요 업무의 역할 분리, 신뢰 역할 인력의 채용 시 및 5년마다 최소 검증, 정기 교육·중요 변경 시 재교육, 최소 권한·MFA·정기 접근 검토를 요구한다. CA 시스템에 안전한 코딩·코드 서명·보안 업데이트를 적용하고, 시스템·사용자 활동 로그를 보호·검토해야 한다. [CP 역할·인력·접근·로그][cp-procedural], [CP 컴퓨터 보안][cp-computer]

**닫는 조건:** 누가 어떤 역할을 겸할 수 있는지, 개인별 승인 재료를 누가 보유하는지, 접속 구간과 CA 시스템별 인증 방식, 승인·실행 코드의 서명·변경 승인·패치 정책, 로그 원천·검토 주기·보존을 구체화한다. 해시 기록을 코드 서명이나 MFA의 대체로 간주하지 않는다. 인증서 발급 기록의 만료 후 최소 1년 보존은 현재 설정에 반영되어 있으나 실제 저장·접근·복구 증거는 앞으로 확보해야 한다. [CP 저장소 책임][cp-repository]

### C07 — 독립 입회와 확인 서명: 계획 적합, 수행 증거 필요

현재 문서는 W와 참여자 확인 서명을 계획한다. 이 방향은 맞지만 독립 입회자의 실명·독립성·관찰 범위·실제 서명은 미정이다. CP의 생성 조항에는 독립 입회 또는 기록 경로가 있지만, **Program의 등록 증거 요구는 독립 입회한 키 생성과 서명된 스크립트**다. 조건에 맞는 WebTrust 보고서 대체 경로를 쓰지 않는 한 녹화만으로 대체하지 않는다. [Program Certificate Policy][program-ca]

**닫는 조건:** 행사 전에 입회자·독립성·관찰 범위·서명 양식을 확정하고, 실제 생성 키와 등록할 First 인증서를 공개키 식별자·수행 기록으로 연결한다. 지금 이름이 비어 있는 것은 작성 중 상태이며, 사후 입회로 보완할 수 있다는 뜻은 아니다.

### C08 — 속성 잠금과 폐기: C2PA 위반으로 볼 근거는 없지만 잠정안 유지

CP의 `Key Destruction`은 구체 조건을 두지 않는다. 따라서 `destroyable=false` 자체를 C2PA 금지로 판정하지 않는다. `extractable=false`·`modifiable=false`·`destroyable=false`라는 AWS 속성값도 CP가 직접 지정한 요구는 아니다. [CP 저장·백업·폐기][cp-storage]

다만 키 수명 전체 보호, 교체·복구·종료 절차, 개인키 archival 금지와 양립해야 한다. 현재 N03처럼 **폐기 경로·백업 처리·공유 클러스터 영향·승인자 교체·복원 시험이 완료되기 전 운영 키 생성을 막는 조건을 유지**한다. 해당 시험을 통과했다고 이 검토에서 기록하지 않는다.

| Root 자기서명과 Root의 First 인증서 서명 | Root 개인키의 허용 용도에 해당 | [CP 키 사용][cp-usage] |

| 작업자 포함 O·A·B 중 2명 승인 | Root 인증서 서명의 최소 2명 요구와 양립. O의 명시적 실행 지시·두 사람의 신뢰 역할·실제 통제가 전제. 반드시 작업자 외 3명 승인이 필요하다는 근거는 없음 | [CP 발급][cp-issuance], [역할 분리][cp-procedural] |
| 개인키 서명 전용·일반 반출 금지 | 모듈 내 사용·평문 반출 금지와 일치하는 방향. 보호된 필수 백업은 별도 충족 필요 | [CP CA 키 통제][cp-storage] |
| 전용 EC2의 앱으로 본문 준비 후 HSM에서 서명 | 이 구성 자체의 금지는 확인하지 못함. 본문 무결성·인증·권한·코드·로그 통제는 C02/C06의 조건 | [CP 키·컴퓨터 보안][cp-keys] |
| First ICA를 Trust List 등록 대상으로 계획 | Program은 등록할 Root 및/또는 Intermediate 인증서를 다룸. First만 신청한다는 것이 상위 Root의 CP 통제 면제를 뜻하지 않음 | [Program CA 증거][program-ca] |
| 하위 Issuing/leaf 발급·외부 신청은 후속 | 행사 범위 분리는 가능. 등록 완료나 전체 CA 운영 준수로 표현하지 않음. 발급한 First의 상태 의무는 C04 | [Program][program], [CP 상태][cp-status] |
| 동일 키의 즉시 재발급 금지·결과 불명 시 중단 | CP의 동일 키 갱신 및 이미 인증서를 발급한 키에 새 인증서 발급 금지와 일치하는 방향 | [CP 갱신][cp-renewal] |

## 다음 작업과 종료 기준

1. **C01의 외부 해석·수용 확인을 먼저 시작한다.** 모델 선택을 유지한 채 저장 요구 충족을 승인할 수 있는 근거가 필요한 사안이다.
2. **설정표의 인증서 값을 완성한다.** C03의 필드·Root AKI·First 상태 방식과 주소를 정하고, C04의 실제 가동 준비를 연결한다. 사람이 이름과 기간을 정하는 작업과, 규칙으로 이미 정해진 확장 값을 채우는 작업을 구분한다.
3. **생성·접근·백업 통제의 빈칸을 실행 가능한 절차로 바꾼다.** C02/C05/C06, 기존 N03와 M01–M08의 책임자·정족수·명령·허용/거부 결과를 정한다.
4. **독립 입회 계획을 확정한 뒤 테스트 키로 전체 리허설을 한다.** 인증서/CSR 검증·우회 거부·복구·로그·서명 증거를 묶어 검토하고, 모든 미해결 항목을 닫은 후 운영 행사 승인 여부를 판단한다.

이번 작업은 검토 보고서와 연결 링크를 추가했다. 모델·정족수·인증서 값·서비스 가동 정책을 새로 확정하거나 운영 명령을 실행하지 않았다.
