행사 스크립트는 진행 순서, 단계별 기록 목록은 기록지 선택과 회차 연결을 안내한다. 기록지는 단계마다 한 장을 함께 사용하되 작성란을 담당자별로 구분한다. Administrator가 취합해도 승인자·실행자·입회자의 확인을 대신하지 않는다.

인쇄해서 배부할 때

인쇄·배부 목록의 진행자 대본·개인별 책자·공용 기록 원본을 사용한다. 인쇄본은 본문과 서식을 파일 안에 포함하며 행사 중 링크를 누르지 않는다. 진행자가 부르는 S01.2 같은 번호를 개인 책자와 공용 기록지에 똑같이 표시한다.

개인 책자의 현재 단계 첫 면에는 수행 / 대기 / 계속 관찰과 작성할 기록 번호가 있다. 다음 면에는 세부 확인 기준이 있다. 공용 진행판에 현재 번호를 표시하고, 담당자 완료 보고와 필요한 검증 후 다음 번호로 이동한다. Crypto Officer는 Key Custodian 1의 호출도 수행하되 두 역할의 기록 칸을 구분한다.

종이 기록은 단계별 공용 원본 한 묶음에 작성한다. 승인된 장치·앱에서 하는 전자서명과 종이 확인 서명을 구분한다. 개인마다 별도 노트북을 배정한다고 가정하지 않는다.

  • Crypto Officer의 Key Custodian 1 겸임을 허용한다. 실행 자체는 승인으로 세지 않으며 본인 승인 외 다른 보유자 1명 이상의 승인이 필요하다. Key Custodian 2와 3이 승인하면 Crypto Officer는 승인자로 서명하지 않고 실행할 수 있다.
  • Key Custodian 1·2·3은 서로 다른 세 사람이며, 서로의 승인키를 관리하거나 한 사람을 두 명으로 세지 않는다.
  • Independent Witness는 다른 행사 역할을 겸임하지 않는다. 독립성·관찰 범위·접근 방법을 사전에 확인한다: {{Witness_독립성_관찰범위_확인근거}}.

  • 기타 겸임·대체자는 승인 명부와 같은 분리 기준을 적용한다. 대리 서명이나 개인키 인계로 교체하지 않는다: {{기타_겸임_검토와_승인}}, {{역할별_대체자와_교체승인}}.

키와 서명 알고리즘 결정

사용자의 “전부 ecd 384”는 Root와 First ICA 모두 ECDSA 서명용 P-384 키를 사용하는 결정으로 반영한다. 두 CA는 같은 알고리즘을 사용하되 각각 별도의 키 쌍을 생성한다. 해시는 P-384에 맞춰 SHA-384를 선택하며, 이는 이번 행사의 프로젝트 선택이다.

대상 사용할 키 서명 알고리즘·해시
S02 Root 자기서명 인증서 Root P-384 키 ECDSA + SHA-384
S04 First CSR First P-384 키 ECDSA + SHA-384
S05 First 인증서 Root P-384 키. 인증서에는 First P-384 공개키 수록 ECDSA + SHA-384

C2PA v0.2의 Root 공식 프로파일 (근거 원문 식별은 승인 자료 묶음에 보관)과 First 공식 프로파일 (근거 원문 식별은 승인 자료 묶음에 보관)은 ECC 곡선 P-384와 ECDSA SHA-2 계열 서명을 허용한다. P-384는 허용된 곡선 중 이번 행사에서 선택한 값이며, 모든 프로파일 검사나 적합성 심사가 완료되었다는 뜻은 아니다.

CloudHSM의 EC 생성 명령 (근거 원문 식별은 승인 자료 묶음에 보관)에는 --curve secp384r1, ECDSA 서명 명령 (근거 원문 식별은 승인 자료 묶음에 보관)에는 --hash-function sha384를 반영한다. 실제 명령은 키 속성·계정·입출력·CLI 버전을 정한 뒤 완성하고 시험한다.

인증서·CSR의 서명 식별자는 ecdsa-with-SHA384 (1.2.840.10045.4.3.3)를 사용한다. AlgorithmIdentifier의 parameters는 생략한다. RFC 5758 §3.2 (근거 원문 식별은 승인 자료 묶음에 보관)

CLI raw/digest 입력 방식과 변환 도구는 미정이다. 어느 방식을 선택하든 고정 본문에 대해 SHA-384를 한 번 적용한 ECDSA 서명이 되도록 정의한다. CloudHSM의 원본 r||s 서명 응답은 보존하고 인증서·CSR 조립에 필요한 ASN.1 DER 형식으로 변환한다. AWS 서명 입력·출력 정의 (근거 원문 식별은 승인 자료 묶음에 보관)

이 선택은 CA 키와 위 세 서명 작업에 적용한다. 증거 파일의 SHA-256 식별 해시와 AWS quorum 토큰의 승인키·서명 규칙은 별도로 관리한다. AWS CU quorum 초기 설정 문서의 승인키는 RSA 2048이며 이를 CA용 P-384 키로 대체하지 않는다. AWS quorum 승인키 설정 (근거 원문 식별은 승인 자료 묶음에 보관)

사용자 결정: Root·First 개인키는 서명 전용으로 사용하고, 일반 반출은 extractable=false로 금지한다. 복호화·키 파생·다른 키 unwrap을 금지하고, 개인키로 암호화·검증·다른 키 wrap을 수행하는 용도도 허용하지 않는다. sensitive=true, token=true로 보호·영구 보관을 설정한다. 공개키 출력·공개키의 서명 검증과 승인된 백업·관리는 별도 절차를 따른다.

원문: CP의 CA 키 저장·사용·백업 통제 (근거 원문 식별은 승인 자료 묶음에 보관), AWS 키 속성 (근거 원문 식별은 승인 자료 묶음에 보관), AWS 백업 보안 (근거 원문 식별은 승인 자료 묶음에 보관).

관리 quorum은 공유·공유 해제·속성 변경·wrap·unwrap을 지원한다. 이 중 금지한 암호 연산은 quorum 승인으로 허용하지 않는다. 토큰에는 해당 key-management 서비스를 사용하고 키 사용 토큰과 혼용하지 않는다. 관리자 quorum 서비스는 관리자 서비스 값 변경 보호이며 개인키의 사용·관리 값 설정과 구분한다. AWS 지원 범위 (근거 원문 식별은 승인 자료 묶음에 보관), 관리자 값 변경 (근거 원문 식별은 승인 자료 묶음에 보관)

현재값·변경값·명령·대상 키·승인자 명단·기한을 별도 작업 계획으로 고정한다. AWS 토큰만으로 특정 변경값과 명령 전체가 고정된다고 가정하지 않으며, 실행 직전 대조와 사후 조회를 기록한다. modifiable=false가 공유나 승인키 등록까지 잠근다고 단정하지 않고 실제 동작을 시험한다. 관리 quorum 절차 (근거 원문 식별은 승인 자료 묶음에 보관)

AWS API 작업의 접근 권한은 IAM 및 필요 시 SCP로 제한하고 별도 승인 실행 경로에 연결한다. 승인 기록만 있고 직접 실행 권한이 남아 있으면 통제 완료로 보지 않는다. 복원한 환경은 백업 시점 사용자·설정·정책을 현재 명단·등록키·quorum·속성·접속 정책과 대조하기 전 사용하지 않는다. IAM 작업 목록 (근거 원문 식별은 승인 자료 묶음에 보관), 백업 복원 (근거 원문 식별은 승인 자료 묶음에 보관)

공개키에는 AWS 개인키 quorum이 적용되지 않으며, 공개키 출력·검증·보관은 별도 관리한다. 위 잠금 설정은 CA 개인키에 대한 기본안이며 공개키 세부 속성은 실제 명령 작성 시 확정한다.

N01 CP의 FIPS 판본 문구 차이

CP v0.2의 Key Pair Generation and Installation by CAs는 키 생성에 FIPS 140-2 또는 140-3 Level 2 이상을 허용한다. 반면 Controls for CA Keys / Key Storage는 FIPS 140-2 Level 2 이상으로만 표현한다. 고정 CP 원문 (근거 원문 식별은 승인 자료 묶음에 보관)

이 차이를 특이사항으로 기록하고, 이번 행사는 현행 FIPS 140-3의 Level 3 인증 모듈과 FIPS 모드를 사용하는 보안 방향으로 결정한다. Level 2 최소 등급보다 높은 인증 등급을 선택하는 프로젝트 결정이며, 저장 조항의 문구를 임의로 바꾸거나 외부 적합성 수용이 완료되었다고 기록하지 않는다. 문구 차이에 대한 외부 해석·수용 근거는 아직 확보하지 않았다.

AWS는 hsm2m.medium을 FIPS 140-3 Level 3 및 CMVP 4703에 연결한다. 해당 인증은 승인 모드와 정해진 설치·초기화·구성 조건을 전제로 하므로, 구축 후 실제 모듈·펌웨어·모드의 대응 자료를 준비한다. AWS 인증 안내 (근거 원문 식별은 승인 자료 묶음에 보관), NIST CMVP 4703 (근거 원문 식별은 승인 자료 묶음에 보관)

행사 승인 조건: C2PA 측의 저장 조항 적용 해석·수용 근거와 실제 모듈·펌웨어·FIPS 모드의 인증 대응 자료를 함께 확보한다. 해석 자료에는 적용 CP 판본·대상 구성·발행 주체·일자·답변 범위와 남은 조건을 기록한다. 담당자·요청/회신 위치: {{N01_확인담당과_외부근거}}. 현재 외부 회신은 미확보이며 N01은 미해결이다. 보안 등급 선택이나 이번 설정표 작성만으로 해소하지 않고, 근거 미확보 시 운영 행사 승인을 보류한다.

N02 키 생성 승인과 생성 시 quorum 설정의 구분

AWS의 CloudHSM CLI quorum 지원 작업 목록에는 키 서명과 일부 키 관리 작업이 있으나 키 생성 명령은 열거되어 있지 않다. 생성 시 지정하는 키 사용·관리 quorum 값은 생성된 키의 이후 사용·관리에 적용되는 값이며, 생성 요청 자체에 여러 사람의 HSM 토큰 승인이 적용된다는 뜻이 아니다. AWS quorum 지원 범위 (근거 원문 식별은 승인 자료 묶음에 보관)

2026-10-12 사용자 요청 반영: Root·First 키 생성 승인도 O·A·B 중 서로 다른 2명(2 of 3)으로 정한다. O+A·O+B·A+B를 허용한다. 작업자 O도 생성 계획을 명시적으로 승인하면 1명으로 세지만 명령 실행 자체를 승인으로 세지 않는다. Root와 First는 각각 별도 계획·작업 ID로 승인하고 승인 대상은 대상 환경, 키 종류·알고리즘·속성, 소유·공유 및 이후 사용·관리 quorum이다. 독립 입회·검증은 생성 승인 인원과 별도 역할이다.

고정 CP v0.2의 Key Pair Generation and Installation by CAs는 다인 통제·지식 분할을 요구하며 생성 승인에 3명 전원을 지정하지 않는다. Separation of Duties의 다인 접근 통제와 함께 보아 2 of 3은 이번 프로젝트의 통제 정책으로 채택한다. 승인 인원만으로 준수를 선언하지 않으며, 한 사람이 승인 재료·권한을 모두 보유하거나 다른 경로로 단독 생성할 수 없도록 구성·검증해야 한다.

생성 승인 방식 확정: O·A·B는 각자 독립 보유한 개인 승인용 키로 같은 생성 계획에 서명한다. 앱은 사전에 신원을 확인한 승인 명단의 공개키로 서로 다른 2명 이상의 서명을 검증하고 승인된 계획의 생성만 허용한다. 계획에는 전체 승인자 명단·CU 계정·공개키 지문·대상 환경·키 속성·소유/공유·사용/관리 quorum·작업 ID·기한을 포함한다.

생성 계획 검증에 사용한 것과 같은 개인 승인용 공개키를 각자의 CloudHSM CU에 등록한다. 최초 등록 시 AWS 등록 토큰에는 별도로 서명하고, 등록이 완료돼 있으면 공개키·계정 연결을 대조한다. O·A·B 세 명의 등록을 확인한 뒤, 생성 명령에서는 해당 CU들의 소유·공유 관계와 quorum 값을 설정한다. 생성 후 실제 키 설정을 승인 계획과 대조한다. 개인 승인키는 Root·First CA 키와 별개이며 앱에 개인키를 모으지 않는다. AWS 등록·생성 설정 (근거 원문 식별은 승인 자료 묶음에 보관)

CA 인증서 발급과 CSR 서명: S02/S04/S05는 같은 승인자가 같은 개인 승인키로 작업별 새 HSM key-usage 토큰에 서명하고, CloudHSM이 2 of 3을 검증해 CA 키의 서명을 수행한다. 생성 계획 승인·등록 토큰·사용 토큰의 서명은 서로 대체하거나 재사용하지 않는다. AWS quorum 사용 (근거 원문 식별은 승인 자료 묶음에 보관)

공개키 소유자 확인, 승인 명단의 변경 통제, 승인된 생성 옵션과 실행의 일치, 앱 검사를 건너뛰는 단독 생성 방지를 준비 조건으로 둔다. 앱·명령·인증 수단 보호·우회 차단의 구현 상세는 후속 개발 작성 사항으로 미룬다. 기존 S01/S03 및 G01/G05는 구현·시험 완료를 뜻하지 않는다. 생성 통제 검증 전에는 N02를 종료하지 않는다.

검토 자료는 키 생성 승인 검토안에 연결한다. 기존의 3인 전원 승인 제안은 이번 2 of 3 결정으로 대체한다. 실제 신원·계정·승인키 보호·구현은 후속 작성한다. 계획 승인 서명과 생성된 CA 키를 사용하는 AWS 서명 quorum을 구분한다.

N03 속성 잠금과 폐기 검증 조건

modifiable=false·destroyable=false를 생성 시 적용하는 기본안을 잠정 반영한다. AWS에서 modifiable은 false에서 true로 되돌릴 수 없으며, 개별 객체 삭제 허용 여부는 destroyable과 구분한다. 관리 quorum 승인은 속성 잠금을 해제하는 수단이 아니다. AWS 속성 정의 (근거 원문 식별은 승인 자료 묶음에 보관), PKCS #11 객체 속성 (근거 원문 식별은 승인 자료 묶음에 보관)

잠금·소유자 삭제 거부·승인자 교체와 복구를 테스트 키로 검증하고, 키·관련 백업/복사본의 폐기 경로 및 공유 클러스터의 다른 키 영향을 확인해야 한다. 완료 전 운영 키 생성은 금지한다. 실패하면 값을 임의로 완화하지 않고 재검토·변경 승인·필요한 재시험을 거친다. 전체 HSM·클러스터·백업 삭제는 이 속성의 보호 대상이 아니므로 별도 다인 통제가 필요하다. 검토 기준과 기록란은 별도 재검토 기록에 연결한다.

사람과 권한의 연결

역할 배정은 스크립트 명부의 5명 구성을 따른다. Administrator가 진행·검증·기록·운영 인수를 겸하고 Crypto Officer가 Key Custodian 1을 겸한다. Key Custodian 2·3과 Independent Witness는 별도 사람이다. 기존 설정 항목의 식별자를 보존하기 위해 사용하는 대응은 P/V/R/C=Administrator, O=Crypto Officer(Key Custodian 1), A=Key Custodian 2, B=Key Custodian 3, W=Independent Witness이다. 이 식별자는 추가 인원을 뜻하지 않는다.   1. 계획 고정: 작업 ID, 대상 키/클러스터, 서비스, 현재값·변경값, 정확한 명령, 승인자 명단·공개키 지문, 기한, 검사·실패 처리를 고정합니다. 키 공유 변경은 승인자 집합 변경으로 검토합니다.
  2. 권한과 시행 조건 확인: 개인키 관리는 소유자 전용 명령인지 확인하고 개인 CU와 명단을 대조합니다. 잠긴 속성 변경·일반 반출·금지 암호 연산·개별 삭제를 정상 관리 작업으로 허용하지 않습니다. 잠금된 키에서 공유·승인자 교체가 가능한지는 사전 시험 결과를 참조합니다.
  3. 서비스별 토큰과 승인: 개인키 관리는 key-management, 관리자는 해당 user·quorum·cluster 토큰을 사용합니다. 키 관리에는 Key Custodians 중 서로 다른 2명, 관리자에는 지정 관리자 3명 중 서로 다른 2명의 유효한 승인 서명을 확인합니다. 키 사용 토큰을 재사용하지 않습니다.
  4. 실행 직전 대조: 승인한 명령·현재 상태·대상·명단·기한을 다시 확인합니다. 토큰 자체가 변경값 전체를 고정한다고 가정하지 않습니다. 실행자의 명시적 지시와 요청 시작을 기록하고 실제 명령이 지원하는 --approval로 전달합니다.
  5. 결과 조회와 보존: 요청·응답·토큰 상태·실제 승인자와 조합을 보존합니다. 속성·소유/공유·quorum·등록키·관리자 서비스 값 중 해당 항목을 전후 조회하고 계획과 대조합니다. 실패·부분 성공·결과 불명은 자동 재시도하지 않습니다.
  6. 별도 통제 경로: 생성·AWS API·호스트/코드·승인키 등록/교체는 네이티브 quorum 적용을 가정하지 않습니다. 별도 계획의 다인 승인 검사와 제한된 실행 권한을 연결하고 직접 CLI/API·다른 호스트/SDK·관리자·권한 정책·코드 변경의 우회를 차단합니다. 생성 정족수는 2 of 3으로 확정했으며, 그 외 별도 작업 정족수·인증 수단·실제 실행 프로그램은 후속 정의합니다.

  2. Q02 — Crypto Officer·Administrator: 대상 계정·클러스터·키 소유/공유·사용 quorum·승인키 등록을 확인합니다. Root·First 개인키의 사용 quorum이 2이고 승인 가능한 집합이 서로 다른 사람 Key Custodians의 개인 CU 계정·등록키와 일치하는지 확인합니다. 신원·계정·등록키 매핑 미확정, quorum 미설정 또는 승인값 불일치 상태에서는 서명을 진행하지 않습니다. Crypto Officer가 현재 CLI 로그인 세션을 유지하며 기록용 세션 식별자를 작업과 연결합니다.
  3. Q03 — Crypto Officer: 해당 키의 key-usage 토큰을 생성합니다. service·key-reference·토큰 식별 해시·생성/만료시각·세션·작업 ID를 기록하고 승인된 전달 경로로 보냅니다.
  4. Q04 — Key Custodians 중 실제 승인자: 받은 토큰과 본문 승인 묶음의 작업·키·기한을 대조한 뒤 각자에게 등록된 승인용 개인키로 토큰에 서명합니다. Crypto Officer도 본인의 승인키로 자기 토큰에 서명할 수 있습니다. Crypto Officer가 승인 서명을 취합합니다. 실제 서명 입력 변환은 고정 명령 파일을 따릅니다.
  5. Q05 — Administrator: 승인자 개인 계정·등록 공개키·허용 집합·필요 수와 만료/세션 유효성을 검사합니다. Crypto Officer·Key Custodian 2, Crypto Officer·Key Custodian 3, Key Custodian 2·Key Custodian 3 중 하나 또는 세 명 모두의 유효한 승인 서명을 확인합니다. 서로 다른 2명 이상이어야 하며 Crypto Officer의 실행 지시만으로 승인 1명으로 세지 않습니다. 승인 0명·1명, 동일인의 중복, 집합 밖 승인으로 인원 충족은 거부합니다. 실제 승인자·조합·검사 결과를 기록합니다.
  6. Q06 — Crypto Officer·Administrator: 현재 DER·digest·서명 키가 승인값과 같은지 재대조합니다. Crypto Officer의 명시적 실행 지시와 요청 시작을 내구 저장한 뒤 승인 토큰을 --approval로 전달해 해당 ECDSA 작업을 실행합니다. 원본 응답의 보존 실패를 감지합니다.
  7. Q07 — Crypto Officer·Administrator: 반환한 서명값을 포함한 응답을 통제된 저장소에 즉시 보존하고 응답 해시·명령 상태·세션·토큰의 사용/실패 상태를 기록합니다. 성공 토큰을 재사용하지 않으며 실패 응답만으로 재사용 가능하다고 판단하지 않습니다.
  8. Q08 — Crypto Officer·Administrator: raw r||s와 ASN.1 DER 서명 형식 변환 후 고정 본문으로 인증서/CSR을 조립합니다. 독립 도구로 서명·본문 바이트·키·프로파일을 검사하고 산출물과 원장·증거를 확정 저장합니다. 원본 응답이 이미 있으면 이 단계부터 복구하며 HSM 서명을 반복하지 않습니다.

기준 문서의 선택은 완료했으며, 개별 조항과 실제 설정·담당자·명령·증거의 대응은 준비 현황 — 별책「시작 전 준비 확인」의 P02–P06에서 구체화한다. CP 본문·YAML·schema 사이의 차이나 해석이 필요한 사항은 P04에 기록하고 발급 전에 해결 근거를 검토한다. 원문 고정본의 commit과 파일 해시는 사용한 자료를 식별하기 위한 프로젝트 기록이며, C2PA의 별도 규격 버전이나 행사 승인 기록을 뜻하지 않는다.

스크립트에서는 “승인을 확보한다”로 줄이지 않고 아래 ID를 호출한다. 각 ID에 실제 담당자, 실행 위치, 명령 파일·도구 버전·해시, 입력·출력, 통과·중단 기준과 증거 위치를 연결한다. 현재 ID는 수행 절차 식별자이며 실행 가능한 명령이 아니다.

B00 · 초기 설정과 통제의 인계

이 절차는 최초 설정을 매 행사마다 반복하라는 뜻이 아니다. 별도 준비 작업에서 완료한 설정·시험을 S00에서 실제 상태와 대조한다. 설정이 없거나 증거와 현재 상태가 다르면 키 생성을 시작하지 않는다.

  1. 환경 담당자와 검증자가 AWS 계정·리전·클러스터 ID, 각 HSM ID·모델·모드·상태, 모듈 적격성 자료, CLI/SDK·호스트·연결 설정·실행 코드 버전을 확인한다. 일부 HSM 장애, 사용자·키 동기화 미완료, 다른 클러스터 선택 시의 중단 기준을 확정한다. 사람의 승인 quorum과 HSM 복제 가용성 quorum을 구분한다. AWS 키 내구성
  2. 진행 책임자가 실제 사람과 개인 CU/admin 계정, 승인 공개키 지문, Root/First 키 소유·공유 관계, 허용 승인 집합, 대체자·겸임을 대조한다. 한 사람의 여러 계정을 여러 승인자로 세지 않는다. 공유받은 CU의 실제 키 사용 권한까지 포함한다.
  3. 각 승인자의 CA 키와 별개인 RSA 2048 승인키 생성·개인 보관·등록 증거를 확인한다. 준비 작업에는 registration token 발급, 해당 개인키의 소유 증명, 본인 CU/admin으로 공개키 등록, 등록 상태 조회가 포함되어야 한다. 실제 장치와 도구가 AWS 승인 서명 형식을 지원하는지 시험한다. 승인 개인키·비밀번호를 실행 호스트나 증거 묶음으로 모으지 않는다. user list의 quorum 등록 상태만으로 등록 공개키 지문과 실제 사람 연결을 모두 증명했다고 보지 않는다. AWS CU 초기 설정
  4. HSM 관리자와 검증자가 quorum token-sign list-quorum-values로 관리자 user와 quorum 서비스 값을 각각 확인한다. 초기 설정 인계에는 최초 관리자 접근 통제, 개인별 관리자·승인키 등록, 두 값의 설정, 초기 자격의 회수, 관리자 단독 변경 거부 시험이 있어야 한다. AWS 초기 예시의 user=2, quorum=1을 최종 상태로 복사하지 않는다. 실제 선택값과 변경 절차를 검증하며, AWS 변경 안내의 user <= quorum 조건도 대조한다. hsm2m에서 mTLS를 사용하면 관련 cluster 서비스 통제도 확인한다. 관리자 초기 설정 · quorum 값 변경 · 지원 서비스
  5. 생성 통제 담당자가 G01/G05에서 실행할 공동 활성화·회수 수단을 제시한다. CU 자격증명, 직접 HSM 접속, 호스트·네트워크·코드 변경, AWS 관리자·복구 경로에서 한 사람이 우회하지 못하는지 시험한 결과를 인계한다. 승인 티켓이나 입회만 있다면 기술적 차단이 구현됐다고 기록하지 않는다. 키 생성 자체는 AWS quorum 지원 작업에 포함되지 않는다. 지원 서비스
  6. 검증자가 허용 승인 집합을 확인한다. AWS CU는 자기 토큰에도 승인할 수 있다. 따라서 “실행자 O 제외, A/B 모두 승인” 같은 정책을 선택한다면 숫자 2만 설정해서 자동 보장되지 않는다. 본문 승인자와 HSM 토큰 승인자를 구분하고, 승인된 집합·필요수에 맞춰 실행기 승인자 검사, 승인키 등록·교체 경로, 직접 CLI 우회를 함께 시험해야 한다. MFA를 선택한 경우 AWS가 설명하는 승인키와 MFA 키의 관계도 확인한다. CU quorum 주의점
  7. 기록·보관 담당자가 로그 수집, 시간 동기화, 원본 응답 저장, 변경 방지·접근·보존, 백업·복구 권한을 확인한다. CloudWatch HSM 관리 로그, 실행기/CLI 기록, AWS 관리 작업 기록, 본문 승인·입회 기록을 구분하고 각 기록의 담당자와 수집 완료 기준을 정한다.

통과·증거: 승인된 환경·사람/계정/키 대응표, 실제 조회 결과, 초기 설정 기록, 우회·장애·복구 시험 결과를 E00에 연결한다. 실제 값이나 시험 결과가 미정이면 통과하지 않는다. 테스트 키를 사용한 승인 부족·자기승인·동일인 중복·관리자 변경 시험을 운영 키에서 무계획하게 반복하지 않는다.

G01–G05 · 키 생성과 생성 직후 보호

Root와 First 각각 수행한다. 운영 생성 명령의 옵션을 현장에서 즉흥적으로 보완하지 않는다.

G01 · 생성 접근을 공동 활성화한다

진행 책임자가 대상 키·클러스터·승인 설정을 선언하고, 승인자들이 실제 생성 명령·옵션과 생성 통제 범위를 확인한다. 지정 담당자들이 B00에서 검증한 수단으로 임시 생성 접근을 활성화한다. 실행자는 자신의 CU로 접속하고 검증자는 활성화 시각·허용 계정·호스트·유효시간을 기록한다.

통과·증거: 승인 기록과 실제 활성화 결과가 일치한다. 단독 CU 접속만 확보되고 공동 통제 수단이 없는 경우 “공동 활성화 완료”로 적지 않는다. 실패 시 생성 요청을 보내지 않고 X01에 따라 접근을 회수한다.

G02 · 보호 설정을 포함해 키를 생성한다

실행자는 승인된 key generate-asymmetric-pair ec 호출 정의를 사용한다. 곡선, 공개키/개인키 라벨, --cluster-id, 영구 키 여부, 공개키/개인키 속성, --share-crypto-users, 사용·관리 quorum을 생성 시점에 지정한다. 생성 결과의 원본 응답을 보존한다. 생성 후 나중에 quorum·비추출 속성을 붙이겠다는 보호 공백을 두지 않는다. 생성 명령 자체에 존재하지 않는 quorum 승인 옵션을 만들어 사용하지 않는다. EC 생성 명령

속성은 선택한 모델·모드·CLI가 허용하는 조합을 리허설한다. modifiable=false처럼 되돌릴 수 없는 설정은 관리·폐기 절차를 확정한 뒤 사용한다. extractable, sign, 세션 키 여부를 기본값에 맡기지 않는다. 모든 옵션을 무조건 적용하라는 뜻은 아니며, 적용 불가 항목은 검증한 근거와 대체 통제를 남긴다. 키 속성

통과·증거: 승인된 생성 요청 한 건과 반환된 공개키·개인키 식별자, CLI 결과가 연결된다. 응답 유실·부분 실패·저장 실패 시 자동 재생성하지 않는다. 원래 키의 존재와 보호 상태를 조사하고, 확인할 수 없으면 결과 불명으로 보류한다.

G03 · 실제 키와 클러스터 반영 상태를 조회한다

검증자는 라벨만으로 키를 선택하지 않고 생성 결과의 정확한 key-reference와 클래스·공개키 연결을 확인한다. key list의 검증된 필터·상세 조회 절차로 곡선, local, 영구 보관, 비추출·용도·변경·삭제 속성, 소유자·공유자·사용/관리 quorum과 coverage를 승인값에 대조한다. 공개키와 개인키의 quorum을 혼동하지 않는다. key list 실행 정의에는 한 키만 선택했는지 확인하는 기준도 둔다. EC 생성 결과 · CLI 명령 참조

통과·증거: 승인값과 실제 조회값, 예정된 HSM·사용자에 대한 반영 상태가 일치한다. 일부 HSM이나 사용자에서만 확인되면 사전 승인한 장애 기준에 따라 중단한다. 생성 성공 문자열만으로 이 단계를 통과하지 않는다.

G04 · 공개키를 추출하고 지문을 고정한다

실행자는 리허설한 공개키 추출·인코딩 절차로 SPKI DER를 만든다. 이 공개키 추출 명령·변환 도구는 아직 선정·검증되지 않았다. HSM 조회의 EC point를 SPKI DER와 동일한 바이트로 취급하지 않으며, 개인키 반출이나 소프트웨어 대체 키 생성으로 처리하지 않는다. 검증자는 추출 공개키가 G03의 키 쌍·곡선과 연결되는지 확인하고 SPKI DER SHA-256을 계산한다. First에서는 Root와 다른 공개키인지도 검사한다.

통과·증거: 공개키 파일·형식·해시, 양쪽 HSM 키 식별자와 도구 버전·검사 결과를 E01 또는 E03에 남긴다. 공개키 연결을 확인하지 못하면 인증서/CSR 본문을 만들지 않는다.

G05 · 생성 접근을 회수하고 보호 상태를 인계한다

G01 담당자들이 임시 생성 접근을 회수하고 검증자는 직접 재접속·추가 생성 경로에 대한 사전 검증된 확인 절차를 수행한다. 서명용 접근이 필요하면 별도로 승인된 범위만 유지한다. 생성 CU가 키 소유자라는 이유로 계정을 무조건 삭제하거나 후임에게 개인 자격증명을 넘기지 않는다.

통과·증거: 생성 접근 회수, 유지할 서명·관리 권한, 신규 키 보호 책임자와 B01 백업 상태를 기록한다. 회수 실패 시 후속 서명을 중단하고 키 보호를 유지한다.

Q01–Q08 · 매 서명에 적용할 승인과 실행

S02는 Root 키로 TBSCertificate를, S04는 First 키로 CertificationRequestInfo를, S05는 Root 키로 First의 TBSCertificate를 서명한다. 세 작업에 서로 다른 작업 ID와 토큰을 사용한다. 관리 작업에는 별도 서비스와 절차가 필요하며 key-usage 토큰으로 대신하지 않는다.

Q01 · 최종 본문을 준비하고 승인한다

실행자가 승인 프로파일로 최종 DER와 사람이 읽을 필드 목록을 준비하고 검증자가 DN·기간·serial·공개키·확장·발급 허가를 확인한다. 승인자들은 같은 작업 ID·DER SHA-256·서명 키 SPKI 지문·서명 알고리즘·프로파일/도구 버전·승인 기한을 확인한다. CSR도 최종 CertificationRequestInfo DER를 고정한다.

통과·증거: 승인한 DER와 본문 표시·키·승인 기록을 변경 없이 연결한다. 증거용 SHA-256과 ECDSA SHA-384 서명용 digest를 구분한다. 토큰에 서명했다는 사실만으로 인증서 본문 전체를 승인했다고 간주하지 않는다.

Q02 · CLI 세션과 실제 서명 키를 확인한다

실행자는 승인된 호스트에서 CLI 세션을 열어 본인 CU로 로그인한다. 검증자는 대상 클러스터, 로그인 주체, 키 식별자·공개키 지문, 사용 quorum·공유자·속성을 대조한다. 세션을 누가 유지하고 승인 중 잠금·단절을 어떻게 감지할지 정한다. 비밀번호를 명령 기록·화면 녹화·증거 파일에 남기지 않는 입력 방식을 리허설한다.

통과·증거: 작업과 실행 세션·CU·키가 연결된다. CLI 토큰을 별도 OpenSSL provider/PKCS#11 애플리케이션이나 종료된 실행 프로세스에 전달하면 된다고 가정하지 않는다. CLI 안에서의 실제 서명 호출까지 연결되어야 한다. AWS 토큰 제약

Q03 · 해당 작업의 사용 토큰을 발급한다

실행자는 같은 CLI 세션에서 quorum token-sign generate의 --service key-usage, --token, 정확한 키를 선택하는 --filter를 사용한 검증된 호출로 토큰을 발급한다. 검증자는 토큰의 service·key_reference, 토큰 해시와 발급 시각을 작업 ID에 연결한다. 아직 서명되지 않은 토큰 원본은 접근 제한된 임시 승인 저장소에 보존한다. 사용 가능한 토큰·승인 묶음은 일반 증거 폴더나 제출본에 복사하지 않으며, 증거에는 식별 해시·승인자·상태를 연결한다. AWS 토큰 생성

통과·증거: 토큰 대상과 Q02의 키가 일치한다. quorum token-sign list의 minimum-token-count는 클러스터에서 사용 가능한 토큰 수이며 승인자 수가 아니다. 이를 “승인 두 명 완료”의 판정값으로 쓰지 않는다.

Q04 · 승인자가 각자의 승인키로 서명하고 전달한다

각 승인자는 본문 승인 묶음과 작업 ID, 토큰 해시·대상 키·서비스를 확인한 뒤 본인 장치에서 승인 토큰을 서명한다. 전달 대상·경로·무결성 검사·서명 파일 형식과 반환 담당자를 확정한다. 개인키는 전달하지 않는다. 토큰 서명은 CA 개인키가 아닌 등록된 개인별 RSA 승인키를 사용한다. AWS 승인 절차

token 필드는 approval_data를 해시한 값이므로 전체 JSON이나 본문 DER를 대신 서명하지 않는다. Base64 해제·digest 입력·서명 형식·인코딩은 선택 도구의 정확한 절차로 고정하고 등록 공개키로 검증한다. 승인자가 다시 해시해서 서명하는 등 AWS가 검증할 바이트와 달라지는 일을 리허설에서 잡는다. 본문 승인 기록과 토큰 승인 서명은 각각 보존하고 같은 작업 ID로 연결한다.

통과·증거: 각 승인자의 본문 확인과 토큰 서명이 본인·등록키·대상 작업에 연결된다. 전달 오류, 승인키 분실, 승인자의 관찰 불가 상태에서는 다른 사람의 승인키로 대행하지 않는다.

Q05 · 승인 집합과 시간·세션 조건을 검사한다

실행기와 검증자는 서명자 CU·공개키 지문·실제 사람, 승인된 토큰 승인 집합·필요수, 서명 검증, 원본 토큰과의 일치, 본문 승인 기한과 세션 유지를 확인한다. 본문 승인과 토큰 승인의 담당자·필요수가 다르면 각각 검사한다. 예를 들어 토큰에 A/B만 허용하는 정책이라면 O+A 조합을 허용하지 않는 검사·접근 통제가 필요하다. AWS 자기승인 허용을 역할표 한 줄로 바꾸지는 못한다. CU quorum 주의점

통과·증거: 승인 검사 결과·서명자·기한을 기록한다. AWS 안내의 기본 10분 만료를 준비 시간에 반영하고 선택 버전의 실제 동작을 시험한다. 만료·로그아웃·단절·본문 변경이면 이전 승인을 새 토큰에 복사하지 않는다. 결과 상태를 확인하고 Q02 또는 Q03부터 새 토큰과 승인을 확보한다.

Q06 · 실제 입력을 재대조하고 명시적으로 서명을 실행한다

검증자는 CLI가 읽을 최종 파일 바이트 또는 digest가 Q01 승인 DER와 연결되고 서명 키·알고리즘이 일치하는지 확인한다. 담당자의 명시적 실행 지시를 남긴 뒤 실행자가 crypto sign ecdsa의 검증된 호출을 실행한다. 실행 정의에는 --cluster-id, 정확한 --key-filter, --hash-function sha384, --data-type raw 또는 digest 중 선정값, 입력 경로, 서명된 토큰의 --approval 경로가 포함되어야 한다. AWS ECDSA 명령

통과·증거: 요청 전에 작업·입력·키·승인을 원장에 저장하고 실제 호출과 연결한다. token 사용 승인에는 본문 바이트 결합이 자동 제공된다고 가정하지 않는다. 승인 뒤 파일·실행 코드 교체를 막는 통제와 직접 CLI 우회를 함께 검증한다. 구현이 사후 검사로만 바꿔치기를 찾는다면 예방에 성공했다고 기록하지 않는다.

Q07 · 원본 응답을 보존하고 토큰 상태를 기록한다

실행기는 CLI 결과·반환 키 식별자·서명 원본을 손실되지 않는 저장소에 기록하고 저장 성공을 확인한다. 검증자는 요청한 키와 응답의 키를 대조하고 토큰의 사용 후 상태를 수집한다. 토큰은 성공한 한 작업에 사용되며, 실패·취소·세션 종료 때의 처리도 리허설한 절차를 따른다. 살아 있는 승인 토큰은 행사 외부 제출물로 배포하지 않는다. AWS 사용 절차

중단·증거: 요청 시작 후 응답이나 저장 결과가 불명이면 원장에 결과 불명으로 남기고 자동 재서명하지 않는다. HSM 감사 로그의 부재는 서명하지 않았다는 증명이 아니다. AWS의 공개 감사 로그 표는 일반 ECDSA 서명 결과 조회 수단을 제시하지 않는다. 원본 응답이 있으면 조립·검사·저장을 재개할 수 있지만, 없으면 별도 재수행 판단과 새 승인 없이 완료·미실행으로 바꾸지 않는다. AWS 감사 로그 범위

Q08 · 결과를 조립하고 독립 검사한다

실행기는 Base64 서명 응답을 해제하고 ECDSA raw r||s를 인증서/CSR에 필요한 ASN.1 DER 서명 값으로 변환해 조립한다. 이 조립 코드와 독립 검사 명령은 아직 구현·검증되지 않았다. --data-type의 raw/digest 차이, SHA-384 처리, r/s 길이·정수 부호·DER 인코딩, 알고리즘 식별자와 파라미터를 테스트 벡터와 별도 도구로 확인한다. AWS ECDSA 출력 형식

검증자는 승인 DER가 결과 안에 그대로 들어갔는지, 서명과 공개키·프로파일이 맞는지 검사한다. Root는 자기서명 자체, CSR은 First 키의 소유 증명, First 인증서는 Root 서명과 CSR 공개키 연결을 확인한다.

통과·증거: 원본 응답·완성 DER/PEM·각 해시·검사 보고서·원장 저장이 연결되어야 한다. 파일 존재나 CLI 성공만으로 발급 완료로 판정하지 않는다. 검사 실패 때 토큰을 다시 받아 재서명하기 전에 입력·조립·키·승인 중 무엇이 잘못됐는지 조사한다.

B01 · 신규 키의 백업과 복구 권한 확인

보관 담당자는 기존 테스트 키의 복구 시험 결과와 이번 행사 키의 실제 백업 확인을 구분한다. Root·First 생성과 최종 권한 설정을 포함하는 backup ID·상태·시각, 원본 클러스터, 별도 장애 영역의 복제 ID, 보호·보존·복구 책임자를 기록한다. API의 백업 존재만으로 원하는 키와 최종 설정의 포함이 입증된다고 가정하지 않고, 선정한 확인 방법과 리허설 근거를 붙인다.

AWS 자동 백업은 최소 24시간마다 수행되며 즉시 백업을 지시하는 일반 명령은 없다. 클러스터 변경으로 백업을 유발할 수 있지만, 백업만을 위해 HSM을 임의 추가·제거하지 않는다. 생성·최종 설정 시점과 백업을 대조하고 미확보 시 대기한다. 타 리전 복사를 선택하면 대상 backup ID와 READY 상태를 확인한다. off-site를 반드시 타 리전으로만 구현해야 한다는 뜻은 아니다. 백업 주기 · 리전 복사

복구하면 백업 시점의 사용자·키·설정·정책도 돌아온다. 복구 클러스터를 업무에 연결하기 전에 현행 승인키·퇴사자 회수·권한·quorum·원장 상태와 대조하는 절차가 필요하다. 과거 백업, 다른 리전 복사본, 다른 계정 공유와 복구 권한까지 관리한다. 암호화 백업이라는 사실만으로 원본과 같은 다인 통제가 증명되는 것은 아니다. 백업 복구 · 백업 사용 · 백업 공유

통과·증거: 실제 신규 키의 백업 확인과 원본 수준의 보호·복구 절차를 기록한다. 백업 생성·복제·검증이 대기 중이면 S06 완료로 적지 않고, 키 보호 담당자·대기 기한·재확인 방법을 남겨 보류 인계한다. 실제 운영 키를 무조건 현장에서 복구하라는 뜻은 아니며 운영 키 복구가 필요한 검증은 별도 승인된 통제 아래 계획한다.

X01 · 세션·임시 접근 종료와 보호 인계

실행자와 운영 인수자는 활성 CLI 세션·미완료 토큰, 행사 호스트·네트워크·AWS 임시 권한, 승인 장치와 임시 파일의 목록을 대조한다. 세션 종료·토큰 무효화와 접근 회수를 검증한 수단으로 수행하고 검증자가 결과를 확인한다. 토큰 파일을 삭제한 사실만으로 HSM 안의 승인이 종료됐다고 간주하지 않는다.

행사 후 유지할 CU·키 소유·공유·서명/관리 권한은 책임자와 사용 통제를 명시해 인계한다. 로그아웃이 계정·공유 권한 회수와 같지는 않다. 키 삭제는 공개된 key-management quorum 목록에 없으므로, 사용 quorum 설정만으로 소유자의 삭제를 막는다고 가정하지 않는다. 키·클러스터·백업 삭제와 속성 잠금은 별도로 검증한 폐기·관리 절차에 따른다. AWS 키 삭제 · 키 속성
