# Root·First ICA 세레모니 작성 현황과 다음 작업

**2026-10-12 병렬 작업 인계:** [에이전트별 전달 문서](handoffs/2026-10-12-parallel/README.md)를 작성했다. A는 materials의 단계별 자료 작성·검토, B는 script·guides·records의 단계별 흐름 점검을 맡는 분담안이다. 각 진행 파일로 자료/검토 기준/기록 연결 요청을 교환하고 공통 정책·준비 문서는 통합 담당이 갱신한다. 이 인계 작성 자체가 두 에이전트의 착수나 점검 완료를 뜻하지 않는다.

**2026-10-12 S00 자료 양식:** [materials/s00](materials/s00/README.md)에 행사 승인·명부·환경·통제/시험·기록/백업/보호 자료 5종을 작성했다. 필수 기재 항목·첨부 증거·준비 담당·작성 시점을 명시하고 Administrator의 20개 검토 항목 및 개인별 가이드·S00 기록지·E00에 연결했다. 실제 값·시험·승인 완료를 표시하지 않았고 인쇄 묶음은 재생성하지 않았다.

**2026-10-12 records 정리:** 단계별 통과/중단 조건, S00 자료 준비·역할 대조, 보류·재개와 기록 준비·보관 절차를 담당자 가이드로 이동했다. `records/`는 작성자·기입 항목·실제 결과·근거·판정·서명란으로 정리하고 호출 번호 대응은 유지했다. 인쇄 산출물은 재생성하지 않았으며 손서명 대상 정책도 새로 확정하지 않았다.

**2026-10-12 작성 순서 변경:** 사용자 지시에 따라 인쇄 묶음 최종 작성은 마지막으로 미룬다. 현재는 문서의 진행·역할·기록 내용 및 손서명/일반 기록 구분을 먼저 정리한다. 기존 HTML은 이전 검토 초안으로 보존하며 원문 변경에 따라 재생성하지 않는다. 항목별 서명 정책은 아직 확정하지 않았고 모든 기록란에 손서명을 요구하는 것으로 해석하지 않는다.

**2026-10-12 S00 문서 점검:** S00.1–.5를 종이 진행 관점에서 대조해 자료 5종의 제시자·내용·판정 기준, 개인별 기록 항목, 진행자 발언과 보류 조건, 시작 선언 후 입회 기록 순서를 구체화했다. 생성기에서 S02/S03의 제목·기록 연결이 뒤섞이던 오류도 수정했다. [점검 결과](preparation.md#s00-인쇄-문서-점검--2026-10-12)를 참고한다. 실제 인쇄·현장 리허설·환경 시험·행사 승인은 미실시이며 다음 문서 점검은 S01이다.

**2026-10-12 인쇄 진행 보완:** 링크 탐색에 의존하던 당일 안내를 공통 호출 번호(S00.1 등)·개인별 수행/대기 표·같은 번호의 공용 종이 기록란으로 연결했다. [오프라인 인쇄 묶음](print/index.html)은 개인별 책자·진행 대본·공용 기록·진행판·별책으로 배부한다. 외부 자원 없는 HTML 생성과 번호 일치 검증 대상이며 실제 출력·필기 리허설·운영 승인은 아직 아니다.

**2026-10-12 문서 구조 변경:** 당일 진행은 [스크립트](script.md), 담당자 행동은 [5개 가이드](guides/README.md), 결과는 [단계별 기록지](records/record-template.md)로 분리했다. 기존 record-template.md는 회차 목록으로 전환했다. 승인 묶음에는 가이드·각 기록 양식도 포함한다. 이는 문서 구성 변경이며 실제 임명·구현·시험·행사 승인을 완료한 것은 아니다.

**2026-10-12 후속 갱신:** 아래 10월 11일 인계에서 우선 작업으로 지정한 인증서·CSR 설정표의 **규칙상 필수 조건 작성**을 진행했다. [설정표](settings.md#승인-설정)·[CSR 설정](settings.md#first-csr-설정)·[차이 처리](settings.md#프로파일과-schema-차이-처리)에 반영했고, First 상태 제공을 S05/S07과 연결했으며 N01 근거 미확보 시 행사 승인 보류를 명시했다. Root AKI는 고정 schema와의 호환을 위해 포함하도록 작성했고 First 상태 방식은 후속 사용자 결정으로 AIA + OCSP를 확정했다. OCSP·URL 제공 기능은 미구현이다. caIssuers의 SHOULD/실제 schema 검사 차이도 추가 확인했다. 관련 schema 제약에 대한 합성 JSON 13건만 확인했으며 실제 키·CSR·인증서 검증은 미실시다.

**현재 다음 작업:** 2026-10-12 사용자 결정으로 U02의 기간·U03을 확정했다. [선택 현황](settings.md#사용자-선택이-필요한-인증서-값)의 U01(DN)은 사용자 요청으로 **추후 결정**한다. U04는 **방식 A(AIA + OCSP)를 확정**했으며 OCSP·URL 제공 기능은 **미구현**, 실제 URL·운영 주체·가동 시점은 **추후 결정**이다. U05(Serial)는 **5-A 난수 방식으로 확정**, U06(선택 확장)은 **6-A를 정책으로 확정**했다. C2PA/RFC·OpenSSL 비교는 선택 근거로 유지한다. First AIA에는 OCSP·caIssuers를 포함하고 CDP는 생략한다. [공식 근거와 준비 상태](settings.md#first-상태-제공과-발급-조건)를 기록했으며, 실제 시작·만료 UTC 시각은 발급 전에 고정한다. N01 외부 해석·수용과 First 상태 서비스 준비는 계속 미해결이며, 아래 잠금·폐기·승인자 교체 검토도 남아 있다. 환경 구축·운영 행사 승인은 수행하지 않았다. 아래 본문은 10월 11일 기준 기록이며 ‘설정·스크립트 수정 미수행’ 및 ‘필드 미작성’ 상태는 이 후속 기록과 최신 settings/preparation을 우선한다.

**생성 승인·작성 범위 후속 결정(2026-10-12):** Root·First 생성도 O·A·B 중 2명(2 of 3), O+A·O+B·A+B 허용으로 반영했다. 키별로 별도 계획을 승인하며 O의 실행 자체는 승인으로 세지 않는다. 아래 10월 11일 기록의 생성 정족수 미정·3인 제안은 최신 [N02](settings.md#n02-키-생성-승인과-생성-시-quorum-설정의-구분)로 대체한다. 도구·raw/digest·변환·검증 등 개발 구현 상세는 후속 작성으로 미루고 현재는 타 부서 협의용 정책·역할·준비 조건을 우선한다. 후속으로 앱의 생성 계획 서명 검증 및 같은 개인 승인키의 CU 등록·quorum 연결 방식을 확정했다. CA 인증서 발급·CSR 서명은 작업별 새 HSM 토큰의 2 of 3 승인을 사용한다. N02 구현·시험은 미완료다.

**역할 정의 후속 작성(2026-10-12):** [스크립트 참여자](script.md#참여자)에 Ceremony Administrator·Crypto Officer·Key Custodians·Independent Witness와 지원 역할의 허용/금지 행위, 성명·소속·직책 기입란, 직무 분리·겸임 규칙 및 다자 통제 단계를 작성했다. 인적 사항·기타 겸임·대체자는 추후 결정이며 실제 임명·구현·시험·수행 증거는 미완료다.

**역할 통합 후속 작성(2026-10-12):** 기본 5명으로 단순화했다. Administrator가 진행·검증·기록·인수를 겸하고 Crypto Officer는 Key Custodian 1을 겸한다. Key Custodian 2·3과 Independent Witness를 별도 배치한다. HSM 관리자는 추가 행사 참석자를 뜻하지 않으며 세 Key Custodian이 조건부 겸임할 수 있다. 명부와 당일 스크립트는 역할명을 직접 표시하고 기존 역할 기호는 설정 항목 대응에만 남긴다. 아래 과거 역할 배치 기록보다 최신 script를 우선한다.

기준일: 2026-10-11. 작업 폴더: `root-first-001/`. **행사 문서 초안을 작성한 상태이며, 운영용 키 생성·서명·실제 HSM 설정·리허설·행사 승인·외부 등록은 수행하지 않았다.** 다음 작업자는 이 기록을 읽고 [settings.md](settings.md)와 [preparation.md](preparation.md)의 최신 상태를 확인한 뒤 이어서 작성한다.

이 문서는 현재까지의 결정과 작업 인수인계를 위한 설계 산출물이다. 사실·규격의 근거는 연결된 공식 원문에서 확인한다. `root-key-design/`·`c2pa-design/`의 문서나 `references/sources.md` 자체를 독립적인 근거로 사용하지 않는다.

후속 [C2PA v0.2 적합성 검토](c2pa-review-2026-10-11.md)에서 C01–C08의 미해결 조건과 우선순위를 정리했다. 아래 인수인계와 함께 확인한다. FIPS 저장 문구 및 프로파일/schema 차이의 처리, First 상태 서비스의 준비 시점을 추가 검토해야 하며 운영 수행 승인은 아직 없다.

AWS quorum 승인키는 CA용 P-384 키와 별개다. 현재 AWS 문서의 RSA 2048 승인키 규칙과 증거 식별용 SHA-256을 CA의 ECDSA + SHA-384 선택으로 대체하지 않는다. 구체 근거는 [알고리즘 설정](settings.md#키와-서명-알고리즘-결정)에 연결되어 있다.

## 재검토를 전제로 잠정 반영한 기본안

2026-10-11 사용자의 “전부 반영하고 나중에 검토” 요청으로 초안에 반영했다. 실제 적용·시험 완료가 아니다.

| 기본안 | 적용 범위와 남은 조건 |
|---|---|
| 키 관리 `2 of 3` | Root·First 개인키에 사용 quorum과 별도로 관리 값 `2`. 승인 집합은 O·A·B. 서비스별 토큰·소유자 권한·명단 변경·전후 조회를 관리 |
| 관리자 `2 of 3` | 서로 다른 3명의 개인 관리자 계정. user·quorum·cluster 각 값 `2`. CU 역할·계정과 구분. 초기 설정과 단독 변경 거부 시험 필요 |
| 속성 잠금 | 개인키 생성 시 `modifiable=false`, `destroyable=false`. 금지 기능 활성화와 개별 삭제를 막는 기본안. 폐기 경로·잠금/삭제 거부·공유 클러스터 영향 검증 필요 |
| 생성 별도 통제 | 계획·명령 다인 승인과 승인된 요청만 실행하는 제한 경로의 방향 반영. 정족수·인증 수단·실제 구현은 미정 |
| AWS API·환경·등록키 | 백업 복원/복사/삭제/보존 변경, HSM/클러스터 삭제, 호스트/코드/정책 변경, 승인키 등록/교체의 별도 승인 실행과 권한 분리. 구체 정족수·구현·우회 시험 미정 |

**키 생성 검토안의 3인 승인은 확정하지 않았다.** 서명과 키 관리의 2 of 3, 관리자 서비스의 2 of 3을 생성 승인 숫자로 자동 적용하지 않는다. 샘플의 3-of-3이나 과거 사례 조사의 대안도 이번 행사 결정이 아니다.

**폐기 계획·잠금 시험과 필수 통제 검증이 미완료이면 운영 키를 생성하지 않는다.** modifiable=false는 되돌릴 수 없는 선택이다. 관리 승인이 있어도 잠금을 풀 수 있다고 가정하지 않는다. 공유·승인자 교체·복원은 실제 동작을 별도로 확인한다.

## 바로 다음에 이어갈 작업

**먼저 [settings.md의 인증서 설정표](settings.md#승인-설정)에 C2PA가 정한 필수 값을 작성한다.** 적합성 검토 후의 작성 우선순위다. 이번 후속 작업에서는 검토 보고서와 준비 현황·인수인계 연결을 추가했으며, 아래 설정·스크립트 본문 수정은 아직 수행하지 않았다.

1. [적합성 검토 C03](c2pa-review-2026-10-11.md#c03--인증서와-csr-필드-미작성-공식-자료-차이도-처리-필요)을 읽고 공식 원문과 대조해 SKI/AKI·KU·Basic Constraints·정책 OID·AIA/CDP의 필수 조건과 critical 여부를 채운다. First CSR의 요청 확장도 포함한다.
2. Root AKI의 YAML/schema 차이와 First AIA/CDP의 `oneOf` 차이를 처리한다. 규칙으로 정해진 값과 선택이 필요한 값을 구분하며, 실제 DN·유효기간·주소를 임의로 만들지 않는다.
3. First 상태 제공 방식·주소·가동 시점의 확인을 script S05 발급 조건과 S07 인계에 연결한다. 미가동 서비스의 담당자·기한만 적으면 충분하다고 처리하지 않는다. 확인이 필요한 부분은 C04의 미해결 조건으로 남긴다.
4. N01의 외부 해석·수용 근거 확보를 병행 과제로 관리한다. 확보할 근거와 미해결 시 행사 승인 보류 조건을 settings N01과 preparation의 시작 전 확인에 명시한다. 외부 회신을 확보한 것처럼 작성하지 않는다.

이 작업의 결과물은 **규칙상 필수 값이 채워진 인증서·CSR 설정표, 사용자 결정이 필요한 값 목록, 프로파일 차이 처리 기록, First 상태 제공과 FIPS 관련 승인 조건**이다. 기존 알고리즘·서명 정족수·HSM 모델을 임의로 변경하지 않는다.

## 이어서 검토할 잠금·폐기·승인자 교체

**“속성을 잠근 CA 키를 나중에 정상적으로 폐기하고, 승인자를 교체할 수 있는가”를 검토한다.** 이 결과에 따라 잠금 값을 유지할지 바꿀지 결정해야 하므로 검토·시험 전에 운영 키를 생성하지 않는다.

1. Root·First가 사용할 클러스터에 다른 키도 함께 보관할지 확인한다. 개별 키만 폐기해야 하는 상황과 전체 클러스터를 종료해도 되는 상황을 나눈다.
2. 공식 AWS 문서에서 잠긴 객체의 삭제·공유 변경·등록키 교체·복원 동작을 확인한다. 문서로 확인할 수 없는 동작은 배포할 CLI/SDK와 테스트 키의 확인 항목으로 남긴다.
3. 키·HSM·클러스터·관련 백업/복사본 각각의 폐기 경로와 실행 권한·다인 승인·다른 키 영향을 표로 작성한다. 클러스터를 지웠다는 사실만으로 백업까지 폐기되었다고 결론내리지 않는다.
4. 잠긴 키의 승인자 교체 절차를 작성한다. 현재 명단과 새 명단·계정·등록키, 교체 승인, 실행 중 승인 가능한 인원, 전후 조회·복원 시 과거 명단 대조를 포함한다.
5. M02·M03·M06·M07에 기대 결과와 시험 절차를 작성한다. HSM 구축 후에는 리허설용 키로 검증하고 실제 결과·증거를 남긴다.
6. 검토 결과로 `modifiable=false`·`destroyable=false` 기본안의 유지·변경·보류를 결정하고, [재검토 판정란](key-management-control-review.md#다시-검토할-항목과-판정-기록)과 N03·P03/P04에 반영한다. 실행 도구가 미구축이면 검토한 설계와 미실시 시험을 분리해 남긴다.

다음 작업의 결과물은 **폐기 경로표, 승인자 교체 절차, 시험 계획과 실제 결과, 잠금 유지/변경 판단**이다. 담당자·자료·미확인 범위가 연결되어야 하며 추측으로 시험 통과를 적지 않는다.
