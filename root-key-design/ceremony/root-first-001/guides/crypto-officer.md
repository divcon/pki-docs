# Crypto Officer / Key Custodian 1 담당자 가이드

## 처음 배정받았다면

**맡은 일:** HSM(암호키를 보호하고 암호 연산을 수행하는 장비)에서 Root·First 키 생성과 인증서/CSR 서명을 실행하고 결과를 보존합니다. 개인 승인자 Key Custodian 1도 겸합니다.

**먼저 할 일:** Administrator에게 본인 배정·교육, 승인 문서 묶음, 실행 환경/계정과 지원 담당자, 리허설 일정을 요청합니다.

**준비 순서:** 배정 확인 → 본인 계정·승인키 준비 → 실행 환경·절차 인수 → 시험/리허설 → S00 자료 제출.

**당일 흐름:** 자료 제시 → 작업별 승인 확인 → 생성·서명 실행 → 원본 결과·기록 전달 → 임시 접근 종료.

**역할 범위:** 실행 결과의 독립 검증은 Administrator가 맡습니다. 승인 검사 우회·승인 후 입력 변경은 금지합니다. 구축·개발·관리 작업은 별도 배정이 있을 때만 수행합니다.

## 준비 순서

위에서 아래 순서로 준비합니다. 행사일·담당자·실제 마감일은 아직 미정이므로 Administrator와 확정합니다. ‘현재 상태’는 문서에 기록된 상태이며 본인의 준비 완료를 뜻하지 않습니다.

| 언제 | 내가 직접 할 일 | 받을 자료·요청할 사람 | 완료 근거 · 현재 상태 |
|---|---|---|---|
| 배정 직후 | 본인 임명·교육·겸임 범위 확인 | Administrator에게 명부·교육 기준·[설정표](../settings.md)·[실행 절차](../runbook.md)·가이드/기록지 승인본과 일정 요청 | 본인 명부·교육 근거 / 실명·일정 미정 |
| 리허설 전 | 승인된 방법으로 본인 승인키 준비·보호. 개인 CU와 등록 공개키 연결 확인 | Administrator를 통해 계정/등록 담당자의 절차·등록 결과 확보(담당 미정) | 본인 CU·공개키 지문·등록 근거 / 계정·키·구현 미완료 |
| 리허설 전 | 실행 환경·승인된 명령·입출력·저장/회수 방법을 인수하고 본인 접근 확인 | 구축/개발 담당의 환경 인수서·도구/코드 버전·runbook. 연결 요청은 Administrator | 환경/버전·접근·입출력 대조 근거 / HSM 미구축·실행 명령 미작성 |
| 리허설 전 | 기존 시험 보고서를 취합하고, 자신에게 배정된 시험만 수행 | 시험 수행 담당자의 원문·결함/재시험 보고서. 미배정 항목은 Administrator에게 배정 확인 요청 | 자료 4 시험 목록과 사례별 근거 / 시험 담당·기한 미정, 미실시 |
| 행사 전 | 테스트 키로 승인·실행·응답 저장·장애 보고·접근 종료를 리허설 | Administrator의 진행/독립 검증, 다른 승인자의 참여 | 리허설 결과·본인 수행 기록·미비점 해소 / 미실시 |
| 행사 전 → 제시 직전 | 아래 S00의 자료 2·3·4·5 담당분 제출, 제시 직전 현재값 갱신 | Administrator에게 검토 결과·승인본과 잔여 준비 사항 확인 | 자료/첨부 버전·원문·검토 결과 / 양식만 작성, 실제 근거 미확보 |

S01 이후의 계획·본문 생성 도구와 양식은 사전 준비합니다. 실제 운영 공개키·생성 응답·서명 결과는 해당 작업 후 채웁니다. [현재 준비 상태](../preparation.md#설계-보류와-후속-결정)의 생성 승인 앱·실행 명령·OCSP 기능은 미완료이며 당일 즉석 구현으로 대체하지 않습니다.

## 누구에게 제출·보고하나

- **준비 자료·미정 사항·당일 결과:** Administrator(진행·검증 담당)에게 제출·보고합니다. 자료 검토와 단계 진행·종료 판정도 Administrator가 맡습니다.
- **사전 행사 수행 승인:** 별도 지정 승인권자가 맡으며 현재 미정입니다. Administrator에게 승인 근거를 확인받습니다.
- **작업별 생성·서명 승인:** 세 Key Custodian 중 서로 다른 2명 이상이 합니다. Witness의 관찰이나 진행자의 지시는 이 승인을 대신하지 않습니다.

**실패·불일치가 생기면:** 후속 요청을 멈추고 원본·마지막 확정 상태를 Administrator에게 보고합니다. 결과 불명 상태에서 재생성·재서명·삭제하지 않습니다.

**용어:** CU는 개인 HSM 사용 계정, quorum은 필요한 승인 수, key-usage 토큰은 해당 키 사용 작업의 승인 대상입니다. 개인 승인키와 Root·First CA 키는 별개입니다. [본문·작업 번호 풀이](README.md#용어와-작업-번호)

## 겸임 승인 규칙

생성 때는 전체 명단·대상·설정·작업 ID·기한이 연결된 **생성 계획**을 개인 승인키로 서명합니다. 인증서/CSR 서명 때는 고정 본문을 먼저 승인하고 같은 작업·키·기한·세션에 연결된 **새 HSM key-usage 토큰**을 개인 승인키로 서명합니다. 등록 토큰·생성 계획·key-usage 토큰의 서명을 서로 대체하거나 재사용하지 않습니다. CA 개인키는 CloudHSM 밖으로 꺼내지 않습니다. 자기 승인은 다른 보유자 1명 이상의 승인과 함께만 유효하며 어느 두 보유자의 조합도 허용합니다.

**Root 키 생성** · [열 기록지](../records/s01-root-key.md#crypto-officer)

1. **S01.1 — 제시:** S00 이후 진행자의 호출을 받고 Root 고정 계획·내용표·해시·작업 ID·기한을 제시합니다. 전체 승인자 명단·신원/CU/공개키·대상 환경·P-384·보호 속성·소유/공유·생성 옵션·사용/관리 quorum을 승인 설정에 연결합니다. 앱/실행 코드·설정 버전과 접근 담당자의 배정·권한·계정·활성화/회수 범위도 제시합니다. 누락·미정 값이 있으면 보류를 요청합니다. “S01.1 자료 제시 완료”와 실제 자료 참조를 보고합니다.
2. **S01.2 — 개인 승인:** Key Custodian 1로 참여하면 같은 계획·명단·기한을 대조해 자신의 개인 승인키로 계획에 서명합니다. 승인/거부/미참여와 이유·계획 해시·서명 참조·시각을 본인 행에 기록·보고합니다. 실행은 승인으로 세지 않으며 Key Custodian 2·3이 승인하면 본인 승인 없이 실행할 수 있습니다. 승인 검사나 불일치 처리 없이 다음으로 넘어가지 않습니다.
3. **S01.3 — 접근 조치:** 본인이 접근 통제 담당자로도 배정됐을 때만 Administrator의 승인 검사 완료·활성화 지시를 받은 뒤 배정 권한으로 G01을 수행합니다. 생성 계획 승인 참여만으로 접근 권한을 얻지 않습니다. 실제 계정·범위·기한·결과·원문·시각을 `접근 통제 수행 기록`에 적고 보고합니다. 미배정이면 대기합니다. 활성화 성공 자체가 생성 실행 허가는 아닙니다.
4. **S01.4 — 실행:** Administrator의 실행 가능 선언·기록, 앱의 서로 다른 2명 이상 승인 검증 결과와 Witness 관찰 상태를 확인합니다. 현재 작업 ID·기한·미사용 상태·계획 해시·대상·실제 생성 입력을 재대조하고 변경·만료·재사용·입회 단절이면 요청하지 않습니다. 현재 실행 입력과 S01.3 검사/판정 참조를 기록하고 원장에 요청 시작을 남긴 후 G02/CMD-01로 승인된 보호·소유/공유·quorum을 생성 순간부터 적용합니다.
5. **S01.4 완료 보고:** 원본 응답·시각·공개키/개인키 식별자·조회 결과를 저장합니다. 승인된 G04 추출·인코딩 절차로 기존 생성 키의 SPKI DER 공개키 파일을 제시하고 형식·해시·도구 버전·키 연결 자료 및 저장 결과를 기록합니다. 명령·도구는 승인 runbook을 따르며 현장에서 새로 선정하지 않습니다. EC point를 SPKI DER와 같은 바이트로 취급하거나 소프트웨어 대체 키를 만들지 않습니다. “S01.4 요청·자료 저장 완료” 또는 실패 지점과 상태를 보고합니다. 독립 검증과 최종 지문 대조는 Administrator가 수행합니다.
6. **S01.5–.7:** 독립 검사 중에는 후속 생성·서명을 하지 않습니다. 조회 자료에 대한 요청이 있으면 원문을 제시합니다. S01.6에 본인이 배정된 G05만 수행해 회수 결과를 보고하고, 지속 계정·소유/공유는 임의 삭제하지 않습니다. S01.7의 판정과 다음 호출을 기다립니다. 끊긴 세션을 후속 서명에 그대로 쓰지 않고 Q02에서 새로 확인합니다.

**중단·재개:** 응답 유실·부분 성공·저장/공개키 추출 실패·입회 단절이면 후속 요청을 멈추고 마지막 확정 상태·원본을 제시합니다. 정상 S01.6을 기다리지 않고 배정받은 중단 절차로 접근을 회수합니다. 결과 불명 상태에서는 재생성·삭제하지 않습니다. 기존 키가 확인된 경우에도 재개 승인에 적힌 추출·조회·저장·회수만 수행하며 S01.4의 생성 명령을 반복하지 않습니다. 미실행이 입증된 새 요청은 필요한 재승인·접근 검사와 재개 승인권자의 허가를 다시 받아야 합니다. S00-R로 미완료 S01을 건너뛰지 않습니다.

**기록:** 계획 제시·실행·원본 저장은 `Crypto Officer`, 개인 전자 승인은 `Key Custodians`의 Key Custodian 1, 접근 조치는 `접근 통제 수행 기록`의 본인 행에 작성합니다. 앱 검사·활성화 지시·실행 가능 선언은 Administrator 기록을 참조하며 대신 작성하지 않습니다. 각 수행 기록 후 호출 번호·완료 또는 보류 사유를 보고합니다.

3. **실행:** “S05의 승인 본문 해시와 Root 키 지문을 대조했고, First 인증서 서명을 실행합니다”라고 선언하고 요청 시작을 기록해 CMD-09로 서명합니다.
4. Q07 응답 보존 후 Q08 조립·DER/PEM·체인·해시를 제시하고 CMD-10 독립 검사를 받습니다. 실패를 같은 키의 즉시 재발급으로 처리하지 않습니다.

**기록:** 본인 실행은 `Crypto Officer`, 본인 승인은 `Key Custodians`의 Key Custodian 1 행에 기록합니다. 검증·판정은 Administrator에게 넘깁니다.

## 보류와 재개

즉시 후속 요청을 멈추고 마지막 명령·요청/응답과 세션 상태를 제시합니다. 미실행 입증·원본 응답 복구·결과 불명을 구분하고 승인 없이 재실행/삭제하지 않습니다. [장애 판정](../runbook.md#작업-원장과-장애-판정)을 적용하고 결과는 [보류·재개 기록지](../records/hold-resume.md)에 남깁니다. 승인된 별도 관리 작업이 있는 경우만 [관리 변경 기록지](../records/management-change.md)를 사용합니다.

생성 키 조회와 서명 결과 복구를 구분해 원장 상태와 내구 저장된 실행기 요청·응답을 제시합니다. HSM/CloudWatch 관리 로그만으로 해당 본문의 서명 성공·미실행 또는 서명값 복구를 단정하지 않습니다. 저장된 동일 서명 응답이 있으면 승인 범위에서 Q08의 조립·검사만 복구하고 새 HSM 서명을 요청하지 않습니다. 요청 전 미실행이 입증된 작업은 필요한 새 승인·세션과 서명 작업의 새 토큰 및 재개 승인권자의 허가 후에만 실행합니다. 결과 불명 상태에서는 재실행·삭제하지 않습니다. S01의 기존 키 잔여 작업은 본인 S01의 중단·재개 기준을 적용합니다. S00-R 참석 시에는 승인된 최소 조회와 남은 S06 검사·S07 종료만 수행합니다.
