# 담당자 가이드 — 배부와 공통 규칙

초안 · 담당자별 가이드는 배정 직후 준비부터 당일 수행까지 안내합니다. 실제 담당·환경·명령·시험·행사 승인은 아직 미완료입니다.

처음 배정받으면 자기 가이드의 **처음 배정받았다면 → 준비 순서 → 당일 역할 요약**을 읽습니다. 준비 표에는 직접 할 일·받을 자료/요청처·완료 근거·현재 상태가 있습니다. 당일에는 호출된 단계의 행동·기입 표를 따릅니다. Administrator는 같은 승인본의 가이드와 단계별 기록지를 배부합니다.

| 담당자 | 배부할 가이드 |
|---|---|
| Administrator | [Administrator](administrator.md) |
| Crypto Officer / Key Custodian 1 | [Crypto Officer / Key Custodian 1](crypto-officer.md) |
| Key Custodian 2 | [Key Custodian 2](key-custodian-2.md) |
| Key Custodian 3 | [Key Custodian 3](key-custodian-3.md) |
| Independent Witness | [Independent Witness](independent-witness.md) |

## 준비 표의 사용

- 실제 담당·기한·준비 상태는 [preparation의 P02–P07](../preparation.md#먼저-정할-사항)에서 관리합니다. 지원 담당이 미정이면 Administrator에게 담당·기한 확인을 요청합니다. Administrator 본인은 배정 요청자·지정 승인권자와 확인합니다.
- 준비 표의 상태는 현재 문서 기준입니다. 실제 완료는 materials의 작성본·원문과 검토 결과로 연결합니다. 같은 결과를 가이드에 다시 작성하지 않습니다.
- 기존 정책값은 [settings](../settings.md), 실행·검사 방법은 승인된 [runbook](../runbook.md)을 받습니다. 준비 표에 있는 ‘리허설 전/행사 전’은 순서·완료 시점이며 실제 날짜는 아직 미정입니다.
- 승인된 도구·양식과 테스트 키 시험은 사전 준비합니다. 운영 키·본문·서명 결과처럼 해당 호출 후 생기는 실제값은 그때 작성합니다.

## 용어와 작업 번호

| 표기 | 이 가이드에서 뜻하는 것 |
|---|---|
| Administrator / Crypto Officer | 행사 진행·독립 검증 담당 / 키 생성·서명 실행 담당 |
| Key Custodian / Independent Witness | 개인 승인키 보유·작업 승인 담당 / 실제 수행을 독립적으로 관찰·기록하는 담당 |
| Root / First ICA | 이번 행사에서 키·인증서를 만드는 최상위 CA / 그 아래의 첫 중간 CA |
| HSM / CU | 암호키를 보호하고 암호 연산을 수행하는 장비 / 개인 HSM 사용 계정 |
| 개인 승인키 / CA 키 | 사람이 작업 승인에 쓰는 키 / HSM에서 생성해 인증서·CSR 서명에 쓰는 Root·First 키 |
| quorum / key-usage 토큰 | 필요한 승인 수 / 해당 키 사용 작업에서 승인자가 서명할 대상 |
| CSR / TBS / CRI | 인증서 서명 요청 / 서명 전 인증서 본문 / 서명 전 CSR 본문 |
| 지문·해시 / DER | 대상 파일·키를 대조할 식별값(대상 바이트·알고리즘도 확인) / 본문·인증서 등의 바이너리 인코딩 형식 |
| S00–S07 / S00-M01 / M01-01 / E00 | 행사 단계 / 단계별 자료 ID / 자료 안의 항목 ID / 증거 목록 ID. 별도 관리 검토 문서의 M01–M08과 구분 |
| CMD / G / Q / X | 실행 작업 / 생성 접근·생성/조회 / 서명 승인·실행 / 접근 종료 관련 작업 번호. 실제 절차는 runbook 참조 |
| B00 / B01 | HSM 초기 설정·통제 최종 인수 / 신규 키가 포함된 백업의 확인 |

[행사 스크립트](../script.md)는 제출용 상세 절차서의 본문이자 진행자가 읽는 대본이며, 이 가이드는 승인 부속 문서로서 역할별 수행·검사·판정 방법을 안내한다. 낭독 지시는 script에서 관리한다. [단계별 기록 목록](../records/record-template.md)과 `records/`에는 작성자·기입 항목·실제 결과·근거·판정·서명만 남긴다. 기록지는 단계별 묶음으로 사용하고 작성란을 담당자별로 구분한다. Administrator가 취합해도 승인자·실행자·입회자의 확인을 대신하지 않는다.

제시 자료는 [materials](../materials/README.md)의 단계별 양식으로 준비한다. S00의 자료 1–5는 준비 담당·필수 기재사항·첨부 증거가 정해져 있으며, 검토 방법은 본 가이드에, 현장 판정은 records에 남긴다.

## S00 자료 작성과 현장 기록

각 가이드 S00은 **준비할 문서 → 제시 직전 갱신 → 행사 중 기입** 순서입니다. 문서명 옆에 본인 작성 범위를, 호출 옆에 기입 내용과 기록지의 란을 표시합니다. 작성할 것이 없는 시점은 ‘별도 작성 없음’으로 표시합니다.

**승인·판정 담당:** 행사 수행의 사전 승인권자는 별도 지정 대상이며 현재 미정입니다. Administrator는 그 승인 근거를 확보하고 S00.4에서 자료를 검토한 뒤 S00.5에서 S01 시작 여부를 판정합니다. Witness는 실제 선언을 관찰·기록합니다.

- **materials:** 이미 정해진 값은 미리 표시하고, 회차별 미정 값·실제 근거를 보완합니다. 자료별 작성 시점표의 사전 칸과 제시 전 갱신 칸을 구분합니다.
- **records:** 실제 제시·참석·확인·판정·선언을 해당 호출에서 작성합니다. 본인 참석은 참석 확인에, 자료 검토는 담당자 란에 한 번만 씁니다.
- **자료 변경:** 자료 담당자는 기존 제시본을 보존하고 새 버전·갱신 시각·변경 항목·첨부 식별/해시를 남깁니다. Administrator는 영향·필요한 변경 승인을 확인하고 관련 검토를 다시 연결합니다. 각 담당자는 자기 기록에 새 자료 버전·변경/보류 근거를 적으며 이전 판정을 덮어쓰지 않습니다. 필수 기준 미정·근거 누락·불일치이면 다음 호출로 넘기지 않고 보류 절차를 따릅니다.

## 인쇄해서 배부할 때

인쇄 묶음은 내용 확정 후 마지막에 제작한다. 아래는 최종 배부 방식이며 기존 HTML은 이전 검토 초안이다.

[인쇄·배부 목록](../print/index.html)의 진행자 대본·개인별 책자·공용 기록 원본을 사용한다. 인쇄본은 본문과 서식을 파일 안에 포함하며 행사 중 링크를 누르지 않는다. 진행자가 부르는 `S01.2` 같은 번호를 개인 책자와 공용 기록지에 똑같이 표시한다.

개인 책자에는 단계별 준비와 호출별 **할 일 / 대기 / 계속 관찰**, 작성할 기록 위치가 있다. 공용 진행판에 현재 번호를 표시하고, 담당자 완료 보고와 필요한 검증 후 다음 번호로 이동한다. Crypto Officer는 Key Custodian 1의 호출도 수행하되 두 역할의 기록 칸을 구분한다.

종이 기록은 단계별 공용 원본 한 묶음에 작성한다. 승인된 장치·앱에서 하는 전자서명과 종이 확인 서명을 구분한다. 개인마다 별도 노트북을 배정한다고 가정하지 않는다.

## 역할 정의와 허용·금지 행위

| 역할 | 맡는 사람 | 수행할 수 있는 행위 | 금지 행위 |
|---|---|---|---|
| **Ceremony Administrator — 행사 관리** | Administrator | 준비·참석·승인본 확인, 시작·중단·재개·완료 판단, 실행 결과의 독립 검증, 수행·증거·일탈 기록, 백업·기록·운영 책임 인수 | 생성·서명 실행이나 quorum 승인 참여, 진행 승인으로 2 of 3 대체, 미검사 결과 통과 처리, 승인된 기록 덮어쓰기·증거 삭제, 타인의 승인키 보관 |
| **Crypto Officer — 암호 작업 실행** | Crypto Officer | 생성 계획·서명 본문 제시, 승인 확인 후 키 생성·인증서/CSR 서명 요청, 결과 제시, 이상 시 즉시 실행 중단 | 단독 생성·서명, 앱 승인 검사 우회, 승인 후 설정 변경, 자신이 실행한 결과의 독립 검증, 결과 불명 상태의 임의 재실행 |
| **Key Custodians — 승인키 보관·작업 승인** | Crypto Officer(Key Custodian 1), Key Custodian 2, Key Custodian 3 | 각자 자신의 개인 승인키 보호, 같은 계획·본문 검토 및 승인/거부, 생성 계획·등록 토큰·작업별 HSM 토큰에 각각 서명, 본인 키 등록 확인·교체 요청 | 승인키 공유·대여·대리 승인, 다른 사람의 개인키 보관, 검토하지 않은 작업 승인, 과거 서명 재사용, 명단·quorum의 단독 변경. 승인 역할만으로 실행 권한을 얻지 않음 |
| **Independent Witness — 독립 입회** | Independent Witness | 정해진 범위 관찰, 승인·실행·검증·일탈 기록 대조, 중단 요청, 실제 관찰 범위 확인 서명 | 생성·서명 실행, quorum 승인, 다른 행사 역할 겸임, 운영 자격증명·승인키 보관, 관찰하지 않은 작업의 사후 확인 |

Administrator는 검증·기록·인수의 수행 내역을 구분해 기록한다. Independent Witness는 자신의 관찰 범위에 별도로 확인 서명한다.

Key Custodian은 **개인의 승인용 키**를 보관한다. Root·First CA 개인키는 CloudHSM 안에서 보호하며 개인에게 반출하거나 앱에 승인용 개인키를 모으지 않는다.

## 직무 분리와 겸임 규칙

- **Administrator의 진행·검증·기록·운영 인수 겸임을 허용**한다. 생성·서명 실행 및 Key Custodian 역할은 겸임하지 않는다. 자신의 인수·기록 업무를 다른 사람이 검증했다고 표시하지 않는다.
- **Crypto Officer의 Key Custodian 1 겸임을 허용**한다. 실행 자체는 승인으로 세지 않으며 본인 승인 외 다른 보유자 1명 이상의 승인이 필요하다. Key Custodian 2와 3이 승인하면 Crypto Officer는 승인자로 서명하지 않고 실행할 수 있다.
- **Key Custodian 1·2·3은 서로 다른 세 사람**이며, 서로의 승인키를 관리하거나 한 사람을 두 명으로 세지 않는다.
- **Independent Witness는 다른 행사 역할을 겸임하지 않는다.** 독립성·관찰 범위·접근 방법을 사전에 확인한다: {{Witness_독립성_관찰범위_확인근거}}.
- **HSM Administrator는 별도 행사 참석자 3명을 뜻하지 않는다.** 인프라 준비·관리 권한이다. 필요한 경우 Key Custodian 1·2·3이 각자의 HSM 관리자 역할을 겸할 수 있으나 CU/admin 계정과 역할별 승인 재료를 구분하고 단독 명단 교체·권한 변경·승인 우회가 불가능함을 검증해야 한다. Ceremony Administrator라는 직함만으로 HSM 관리 권한을 부여하지 않는다.
- 기타 겸임·대체자는 승인 명부와 같은 분리 기준을 적용한다. 대리 서명이나 개인키 인계로 교체하지 않는다: {{기타_겸임_검토와_승인}}, {{역할별_대체자와_교체승인}}.

## 다자 통제의 적용과 확인

| 단계 | 실행·승인 담당 | 검증·기록·입회 |
|---|---|---|
| S01/S03 키 생성 | Crypto Officer가 계획 제시 → Key Custodians 중 2명 이상이 개인 승인키로 서명 → 앱이 고정 명단의 공개키로 검증 → Crypto Officer가 승인된 생성 요청 | Administrator가 CU/공개키·생성 설정·결과 대조 및 기록. Independent Witness가 관찰 |
| S02/S04/S05 인증서·CSR 서명 | 본문 고정 → Key Custodians 중 2명 이상이 같은 개인 승인키로 새 HSM key-usage 토큰에 서명 → CloudHSM quorum 검증 후 CA 키로 서명 | Administrator가 본문·키·결과 검증 및 기록. Independent Witness가 정해진 범위 관찰 |
| S00/S06/S07 및 보류·재개 | Administrator가 준비·검증·백업·인수 증거를 확인해 진행·보류·완료 판단 | 각 참여자가 자신의 수행·관찰 범위 확인 서명. Administrator의 겸임 업무는 한 명의 책임으로 기록 |

모든 참여자는 이상 발견 시 중단을 요청할 수 있고 Crypto Officer는 실행을 멈춘다. Administrator는 원인 해소·필요한 작업 재승인·입회 가능 여부를 확인해 재개를 판단한다. 필수 역할 공백·직무 분리 위반·정족수 부족·필수 입회 단절 상태에서는 해당 작업을 진행하지 않는다.
