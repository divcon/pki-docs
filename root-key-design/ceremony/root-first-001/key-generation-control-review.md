# Root와 First ICA 키 생성 승인 방식과 후속 검토

상태: 2026-10-12 사용자 요청으로 **생성 승인도 Key Custodians 중 서로 다른 2명(2 of 3)**으로 반영했다. 세 보유자 중 어느 두 명의 조합도 허용하며 Crypto Officer의 명시적 계획 승인은 1명으로 세고 실행 자체는 승인으로 세지 않는다. Root·First는 각각 별도 승인한다. 기존 3인 전원 승인 제안은 대체했다. 사용자 결정으로 **개인 승인키의 생성 계획 서명을 앱이 검증하는 방식과, 같은 승인키를 CloudHSM quorum에 연결하는 방식**을 채택했다. 앱·명령·인증 수단 보호 등의 구현 상세는 후속 작성이며 구현·시험은 미완료다.

**키 생성은 앱의 생성 계획 서명 검증으로 다자 통제하고, CA 인증서 발급·CSR 서명은 CloudHSM의 key-usage quorum으로 다자 통제한다.** 이 문서에서 “CA 인증서 발급”은 S02 Root 자기서명 인증서와 S05 First 인증서의 서명을 뜻하며, CA 키 쌍 생성(S01/S03)과 구분한다.

### 확정한 방식 요약

| 구분 | 키 생성 — S01/S03 | 인증서·CSR 서명 — S02/S04/S05 |
|---|---|---|
| 승인 대상 | 키별 생성 계획 | 작업별 서명 본문 승인 및 HSM key-usage 토큰 |
| 승인자·기준 | Key Custodians 중 서로 다른 2명, 2 of 3 | 같은 Key Custodians 중 서로 다른 2명, 2 of 3 |
| 승인키 | 각자가 독립 보유하는 개인 승인용 키 | 생성 계획 승인에 사용한 것과 같은 개인 승인용 키 |
| 검증·실행 통제 | 앱이 고정 승인 명단의 공개키로 서명 검증 후 승인된 생성만 허용 | CloudHSM이 등록된 CU 공개키로 해당 quorum 토큰 승인을 검증하고 CA 키의 서명 수행 |
| 남길 증거 | 생성 계획·승인 서명·앱 검증·CU/공개키 연결·생성 결과 대조 | 본문 승인·작업별 토큰 승인·HSM 서명 결과·독립 검증 |

**등록 대상은 3명, 작업별 최소 승인은 2명**이다. 세 명이 모두 승인해도 유효하지만 전원 승인을 필수로 바꾸지는 않는다. 개인 승인키는 HSM에서 생성하는 Root·First CA 키와 별개이며, 앱은 승인자의 개인키를 수집하지 않고 서명과 공개키로 검증한다. 같은 승인키를 사용하더라도 생성 계획·공개키 등록·HSM 사용 승인은 각각 다른 서명 대상이다.

## 1 검토 대상

| 행사 단계 | 수행하는 일 | 승인 방식과 현재 상태 |
|---|---|---|
| S01 Root 키 생성 | HSM 안에서 새 Root 개인키·공개키를 만든다 | 앱의 개인 승인키 서명 검증, 2 of 3 확정. 구현 후속 작성 |
| S03 First ICA 키 생성 | HSM 안에서 새 First 개인키·공개키를 만든다 | 앱의 개인 승인키 서명 검증, 2 of 3 확정. 구현 후속 작성 |
| S02 Root 자기서명 | 생성된 Root 키로 Root 인증서 본문에 서명한다 | AWS CloudHSM의 서명 quorum 사용 확정 |
| S04 First CSR 서명 | 생성된 First 키로 CSR 본문에 서명한다 | AWS CloudHSM의 서명 quorum 사용 확정 |
| S05 First 인증서 서명 | 생성된 Root 키로 First 인증서 본문에 서명한다 | AWS CloudHSM의 서명 quorum 사용 확정 |

AWS 서명 quorum은 작업자 Crypto Officer를 포함한 Key Custodians 중 2명 승인(`2 of 3`)으로 확정했다. 실제 신원·계정·승인키는 미정이다. 이번 요청으로 키 관리에도 같은 집합의 `2 of 3` 기본안을 잠정 반영했다. 생성은 같은 Key Custodians 집합의 2 of 3을 쓰되 계획 승인 절차는 두 HSM quorum과 별개다. [서명 결정](settings.md#서명-quorum-결정)과 [관리 통제 재검토 기록](key-management-control-review.md)을 참조한다.

## 2 공개키 등록만으로 생성 승인이 되지 않는 이유

신원을 확인한 Key Custodians의 개인 승인용 공개키는 각자의 HSM 사용자(CU) 계정에 등록한다. 앱에서 생성 계획을 검증하는 공개키와 같은 키를 사용하며, 최초 등록은 키 생성 전까지 완료하고 이미 등록된 키는 승인 명단과 일치하는지 확인한다. 각 사용자는 AWS 등록 토큰에 개인키로 별도 서명해 키 보유를 증명한다. 생성 계획의 서명으로 등록 토큰의 서명을 대체하지 않는다. 이것은 “이 사람이 앞으로 quorum 승인에 사용할 키”를 준비하는 절차다. [AWS CU quorum 설정](https://docs.aws.amazon.com/cloudhsm/latest/userguide/key-quorum-auth-chsm-cli-first-time.html)

Root·First 키 생성 명령에서는 공유할 사용자 이름과 이후 사용·관리 정족수를 설정한다. 공개된 생성 명령에는 이번 생성을 허가하는 다인 승인 토큰을 전달할 `--approval` 옵션이 없다. [AWS 키 생성 명령](https://docs.aws.amazon.com/cloudhsm/latest/userguide/cloudhsm_cli-key-generate-asymmetric-pair-ec.html)

| 구분 | 사람이 이해할 의미 |
|---|---|
| 승인 공개키 등록 | 누가 어떤 키로 승인할 수 있는지 준비한다 |
| 생성 시 공유 사용자·quorum 설정 | 새 키를 나중에 사용할 때 누구의 승인이 필요한지 정한다 |
| 이번 키 생성 승인 | 지금 이 조건으로 키를 만들어도 된다는 동의를 받는다 |

앱의 생성 계획 서명 검증은 마지막 행을 담당한다. 공개키 세 개가 등록되어 있다는 사실만으로 이번 생성에 필요한 두 사람이 동의했다고 기록하지 않는다.

## 3 제안하는 절차

**승인자·공개키 확인 → 생성 계획 서명 → 앱 검증 → CloudHSM 등록·설정 대조 → 키 생성 → 결과 확인** 방식을 채택했다. Root와 First는 각각 별도 계획과 작업 ID로 수행한다. 아래는 세레모니의 승인·확인 단계이며 앱·명령의 상세 구현은 후속 작성한다.

| 순서 | 담당 | 실제로 할 일 | 검토·기록할 결과 |
|---|---|---|---|
| 1 생성 계획 작성 | 작업자 | 사전 확인한 Key Custodians 전체 명단·CU 계정·공개키 지문과 대상 클러스터, 키 종류·알고리즘, 키 속성, 소유·공유 사용자, 이후 사용·관리 quorum, 작업 ID와 기한을 문서로 고정한다 | 사람이 읽을 내용표와 동일한 내용을 담은 고정 파일·해시 |
| 2 생성 계획 승인 | Key Custodians 중 실제 승인자 2명 이상 | 같은 계획을 확인하고 각자의 승인용 개인키로 그 계획 문서에 전자서명한다 | 서로 다른 승인자 2명 이상의 승인 서명과 공개키 지문 |
| 3 승인 검사 | 승인 검사 프로그램 | 미리 고정한 Key Custodians 승인자 공개키로 서로 다른 2명 이상의 서명을 검사한다. 계획·기한·환경·미사용 작업 ID와 실제 생성 옵션을 대조한다 | 통과 또는 거부 판정과 검사 기록 |
| 4 CloudHSM 등록·대조 | 각 승인자·검증자 | 같은 승인용 공개키가 각자의 CU에 등록됐는지 확인한다. 미등록이면 각 사용자가 AWS 등록 토큰에 별도 서명해 등록한다. 등록된 키와 승인 명단의 공개키 지문이 다르면 중단한다 | Key Custodians 세 사람의 신원·CU·공개키 연결과 등록 확인 기록 |
| 5 키 생성 | 작업자가 요청하고 제한된 실행 프로그램이 CLI 호출 | 앱 승인을 통과한 계획대로 생성한다. 공개키 파일을 생성 인자로 넣는 대신 해당 CU들을 소유자·공유자로 연결하고 사용 quorum 2 및 승인된 관리 설정을 생성 시 적용한다 | 실제 요청·응답, 생성된 키 식별자와 공개키 |
| 6 결과 확인과 종료 | 검증자·기록자·운영 인수자 | 실제 키 속성·사용자 연결·서명 quorum을 계획과 대조하고, 생성 접근을 종료해 보호를 인계한다 | 조회·대조 결과, 승인과 생성 결과의 연결, 종료·인수 기록 |

요청과 함께 제출된 임의 공개키만으로 승인자를 인정하지 않는다. 사전 확인·고정된 신원·CU·공개키 명단을 사용하고 각 개인키는 해당 승인자가 독립 보유한다. 승인한 계획과 실제 생성 파라미터가 일치해야 하며 승인자 명단·공개키·quorum 변경은 새 승인 대상으로 처리한다.

여기서 승인자의 전자서명은 **키 생성 계획 문서에 대한 동의**다. 아직 생성되지 않은 Root·First 키를 사용하지 않는다. 생성된 CA 키로 CSR·인증서에 서명하는 S02/S04/S05는 기존 AWS quorum 절차를 따른다. 각 작업의 새 HSM 토큰에 같은 개인 승인키로 다시 서명하며 생성 계획 서명·등록 토큰 서명을 재사용하지 않는다. [AWS 작업별 quorum 사용 절차](https://docs.aws.amazon.com/cloudhsm/latest/userguide/key-quorum-auth-chsm-cli-crypto-user.html)

“승인 검사 프로그램”은 서로 다른 2명 이상의 서명을 확인하는 프로그램이고, “실행 프로그램”은 그 검사 결과에 따라 CLI를 호출하는 프로그램이다. 하나의 통제된 프로그램으로 구현할 수도 있지만 아직 존재하거나 구현을 완료한 것으로 간주하지 않는다.

한 작업의 승인을 다른 작업에 쓰거나 같은 계획으로 동시에 여러 키를 생성하지 못하게 해야 한다. 생성 요청 후 응답을 받지 못했거나 기록 저장에 실패하면 자동으로 다시 생성하지 않고, 이미 생성된 키가 있는지 먼저 확인한다. 결과를 확인할 수 없으면 작업을 중단하고 조사한다.

## 4 프로그램을 우회하지 못하게 해야 한다

이 제안을 실제 통제로 사용하려면 **작업자가 필요한 두 사람의 승인 없이 생성 명령을 직접 실행할 수 없게 해야 한다.** 작업자가 CU 비밀번호와 자유로운 CLI 로그인 세션을 모두 사용할 수 있으면 승인 검사 프로그램을 건너뛸 수 있다. CU는 키 생성 기능을 갖는다. [AWS CU 권한](https://docs.aws.amazon.com/cloudhsm/latest/userguide/understanding-users.html)

| 검토 항목 | 확인할 질문 |
|---|---|
| 생성 CU 인증 수단 | 누가 로그인할 수 있으며 한 사람이 단독으로 생성할 수 있는가? |
| 같은 EC2의 직접 CLI 실행 | 작업자 계정이 승인 검사 없이 생성 CU로 명령을 실행할 수 있는가? |
| 다른 호스트·SDK 경로 | 다른 프로그램이나 호스트로 HSM에 접근해 생성할 수 있는가? |
| 프로그램과 공개키 목록 변경 | 한 사람이 승인 검사 코드를 바꾸거나 승인자 공개키를 자기 키로 교체할 수 있는가? |
| 관리자 권한 | 한 사람이 비밀번호 재설정·접속 허용·코드 변경으로 통제를 우회할 수 있는가? |

이 항목의 답과 구현 방법을 정해야 한다. 기존 “작업자가 전용 EC2에서 CLI로 생성 요청” 방향에 승인 검사와 제한된 CLI 호출을 연결하는 제안이므로, 계정·인증 수단·실행 권한을 추가로 설계해야 한다.

## 5 스크립트에 반영하는 방법

**앱 검증에 의한 2 of 3 생성 승인 방식은 S01과 S03에 반영했다. 실제 신원·CU·공개키와 실행 명령·접근 통제를 연결하고 리허설로 검증해야 한다.** 현재는 당일 수행할 완성된 절차가 아니다. 관리 기본안의 폐기 계획·속성 잠금 시험도 운영 키 생성 전에 완료해야 한다.

| 문서·위치 | 연결할 내용과 후속 준비 |
|---|---|
| script.md S01 / S03 | 계획 제시, 생성 승인 확인, 승인된 생성 요청, 결과 확인, 접근 종료의 진행 순서 |
| settings.md | 생성 승인자 3명의 신원·계정·공개키 지문, 인증 수단 보관, 실행·관리 권한 |
| runbook.md CMD-01 / CMD-05와 G01/G05 | 계획 파일 형식, 서명 검사와 제한된 CLI 호출의 실제 명령, 접근 활성화·종료, 실패 처리 |
| preparation.md | 통제 채택 결정, 구현 증거, 승인 부족·변경·직접 실행·장애 시험 |
| evidence-index.md E01 / E03 | 생성 계획·2명 이상의 승인 서명·검사 결과·생성 요청/응답·실제 설정 조회·접근 종료 증거 |

S02/S04/S05의 서명은 [AWS quorum을 사용하는 공통 Q01–Q08](runbook.md#공통-서명-절차-q01부터-q08)을 유지한다. 문서의 생성 승인 절차를 적었다는 이유로 AWS 서명 quorum이 대체되는 것은 아니다.

## 6 사람이 결정할 항목

| 결정할 항목 | 현재 상태 |
|---|---|
| 별도 다인 승인 실행 방향과 상세 방식 | 개인 승인키의 생성 계획 서명을 앱이 검증하는 2 of 3 방식 확정. 구현 상세는 후속 작성 |

| 생성 계획 승인키 | 이후 CloudHSM quorum에 사용하는 개인 승인키와 같은 키 사용으로 확정. 실제 신원·CU·공개키 연결·보호 방식은 후속 작성 |
| 생성 시 관리 quorum·잠금과 폐기 조건 | [관리 기본안](settings.md#키-관리와-관리자-통제) 잠정 반영. 폐기 계획·잠금 시험 완료 전 운영 생성 금지 |
| 승인 검사·실행 프로그램과 CU 인증 수단 보호 방식 | 미정. 실행자의 직접 우회 차단 방법 포함 |
| AWS 서명 quorum 정족수와 승인자 집합 | 작업자 Crypto Officer를 포함한 Key Custodians 중 2명 승인으로 확정. 실제 신원·CU 계정·승인키·구현·시험은 미정 |

CloudHSM quorum에서는 키 소유자도 연결 사용자 수에 포함되고 요청자가 자기 토큰에 승인할 수 있다. 이번 서명 규칙은 Crypto Officer의 자기승인을 허용하며 세 보유자 중 어느 두 명의 조합도 허용한다. 생성 계획 승인과 HSM 서명 승인은 각각 2 of 3이지만 별도 절차로 기록한다. [AWS quorum 고려사항](https://docs.aws.amazon.com/cloudhsm/latest/userguide/key-quorum-auth-chsm-cli.html)

## 7 검토 근거

공개 기능 조사와 대안·시험 항목은 [별도 조사 문서](../../../references/cloudhsm-key-generation-multiperson-control-2026-10-11.md)에 정리했다. 이 검토안은 프로젝트 설계 제안이며 표준 원문이나 구현 완료 증거가 아니다.

C2PA CP v0.2의 생성 다인 통제·지식 분할 및 키 단독 접근 방지 요구를 실제 통제에 연결하는 것이 목적이다. 원문은 [고정 CP](https://github.com/c2pa-org/conformance-public/blob/2466172859fad1215f7aaf7e3768b41a0ac29abc/docs/v0.2/C2PA%20Certificate%20Policy.md)의 `Key Pair Generation and Installation by CAs`, `Key Usage and Access Control`, `Separation of Duties`에서 확인한다.

2026-10-12 원문 재확인: 위 CP의 CA 생성 조항은 다인 통제·지식 분할을 요구하며 3명 전원 승인을 지정하지 않는다. 2 of 3은 이 요구에 맞춰 채택한 프로젝트 정책이다. 단독 접근·우회 방지와 승인 재료/권한 분리의 실제 검증은 별도로 필요하다.
