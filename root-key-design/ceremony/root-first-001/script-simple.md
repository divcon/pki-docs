# Root와 First ICA 세레모니 — 약식 스크립트

초안 · 행사 관리명 `root-first-001` · 행사 수행 승인 전

이 문서는 **영상 촬영 없이 독립 입회로 진행하는 4단계 절차**다. 기존 [script.md](script.md)의 S04 First CSR 생성은 제외한다. 같은 행사에서 생성한 First 공개키와 승인된 발급 정보를 직접 사용해 First 인증서를 발급한다. 키 생성·인증서 서명의 작업별 승인과 실제 결과 검증은 유지하고, 정해진 낭독·반복 보고·별도 인계 행사는 생략한다.

현재는 절차 초안이다. 실제 명령·도구·환경·담당자와 승인값을 확정하고, CSR 없이 발급하는 경로를 시험한 뒤 수행 승인본으로 고정한다. `{{항목}}`은 행사 전 확정값, `{{현장_항목}}`은 수행 중 기록값이다.

## 참여자와 진행 원칙

기존 5명 역할 배치를 유지한다. 참석·계정 확인은 시작할 때 한 번 하고, 작업별 승인은 실제 승인자만 수행한다.

| 역할 | 성명·소속 / 계정·승인키 참조 | 책임 |
|---|---|---|
| Administrator | {{성명_소속_참조}} | 진행, 실행과 분리된 검증, 기록 취합·보호 인수. 생성·서명 실행 및 quorum 승인에는 참여하지 않음 |
| Crypto Officer / Key Custodian 1 | {{성명_소속_CU_등록공개키참조}} | 생성·서명 실행, 본인 승인키로 작업 승인 가능. 명령 실행 자체를 승인 1명으로 세지 않음 |
| Key Custodian 2 | {{성명_소속_CU_등록공개키참조}} | 개인 승인키 보호·작업 승인 |
| Key Custodian 3 | {{성명_소속_CU_등록공개키참조}} | 개인 승인키 보호·작업 승인 |
| Independent Witness | {{성명_소속_독립성근거}} | 실제 수행·결과 확인을 독립적으로 관찰. 다른 행사 역할·실행·승인 업무를 겸하지 않음 |

- 생성 승인은 Key Custodian 1·2·3 중 서로 다른 2명 이상의 계획 서명을 앱이 검증한다. Root·First는 각각 별도 계획·작업 ID를 사용한다.
- 두 인증서의 서명은 각각 새 CloudHSM key-usage 토큰으로 같은 집합의 2명 이상이 승인한다. 본문·키·작업·세션·기한을 연결하며, 토큰 승인만으로 본문이 고정된다고 간주하지 않는다.
- 진행자는 아래 순서로 작업을 지시한다. 정해진 멘트 낭독, 호출별 완료 보고, 공용 진행판, 단계마다 기록지를 닫고 여는 절차는 사용하지 않는다.
- Administrator가 하나의 수행 기록에 결과를 취합한다. 승인·명령·검사 원문은 작업 ID로 연결하고 같은 값을 여러 양식에 다시 적지 않는다. 각 참여자는 마지막에 자신의 수행·관찰 범위를 확인 서명한다.
- Witness는 시작 확인부터 생성·발급·검증·접근 종료까지 관찰한다. 영상은 촬영하지 않는다. 화면·승인·실행을 관찰할 수 없게 되면 즉시 중단한다. 로그와 서명 기록은 남긴다.

## A1 시작 확인

Administrator가 다음을 한 번 확인하고 시작 여부를 기록한다.

1. 행사 수행 승인, 이 약식본과 적용 부속 자료, 사전 적격성·통제 시험·복구 준비의 검토 완료 여부를 확인한다. 자료 전체를 다시 설명하거나 현장에서 재심사하지 않는다.
2. 실제 참석자·역할·계정/등록키 연결, 승인자 집합과 Witness의 독립성·관찰 가능 여부를 확인한다.
3. 승인 환경과 현재 환경의 일치, 필요한 접근 제한, 로그·증거 저장 가능 상태, 생성 직후 보호·백업 책임을 확인한다. 변경·미해결 조건이 있으면 영향 판단 후 보류한다.

**기록:** 적용본·승인·사전검토 참조, 실제 참석자, 현재 환경 확인 결과, Witness 입회 시작 시각·방법, 시작/보류 판정·이유.

## A2 Root 생성·발급

| 순서 | 수행 내용 | 남길 결과·증거 |
|---|---|---|
| A2.1 생성 승인 | Crypto Officer가 Root 생성 계획·실행 입력을 제시한다. 실제 승인자 2명 이상이 개인 승인키로 서명하고 앱이 검증한다. Administrator가 계획·입력 일치와 유효 승인을 확인한 후, 사전 배정된 접근 통제 담당자가 필요한 생성 접근을 연다. | 계획·입력·승인자·승인 서명·앱 검증·접근 활성화 참조 |
| A2.2 생성·검증 | Crypto Officer가 승인된 명령으로 Root 키를 생성하고 응답·키 쌍 식별자·공개키·조회 결과를 저장한다. Administrator가 알고리즘·보호 속성·소유/공유·quorum·노드 상태와 공개키 연결을 대조한다. 접근 통제 담당자가 임시 생성 접근을 회수하고 Administrator가 회수 결과와 보호·백업 추적 상태를 확인한다. | 요청/응답·키 식별자·공개키 지문·설정 대조·접근 회수·보호 기록 |
| A2.3 인증서 승인·서명 | Crypto Officer가 승인 설정과 실제 Root 공개키로 자기서명 인증서 본문을 만든다. Administrator가 필드·프로파일·serial 중복을 검사한다. 실제 승인자 2명 이상이 같은 본문을 검토하고 해당 작업의 새 토큰에 서명한다. Administrator가 본문/토큰·키·세션·기한·승인을 확인하면 Crypto Officer가 명시적으로 서명 실행을 지시하고 응답을 저장해 인증서를 조립한다. | 본문·해시·serial·본문 승인과 토큰의 연결·유효 승인·실행/응답·인증서 |
| A2.4 결과 확인 | Administrator가 독립 검증 도구로 자기서명·본문 일치·공개키 연결·프로파일을 검사하고 발급 기록을 저장한다. Witness가 실제 관찰 범위와 일탈을 수행 기록에서 확인한다. | 발급 기록·검사 결과·증거 참조·일탈 또는 없음 |

검증·증거 저장과 키 보호가 확인되어야 A3으로 진행한다. 별도 단계 마감 낭독이나 확인 서명은 하지 않는다.

## A3 First 생성·직접 발급

**First CSR을 만들지 않는다.** First 생성 응답·키 쌍 식별자·HSM 조회에서 얻은 공개키와, 권한 있는 요청자의 발급 요청·승인값을 직접 발급 입력으로 사용한다. 임의로 전달받은 공개키 파일만으로 발급하지 않는다.

| 순서 | 수행 내용 | 남길 결과·증거 |
|---|---|---|
| A3.1 생성 승인 | Crypto Officer가 First 생성 계획·실행 입력을 제시한다. 실제 승인자 2명 이상이 별도 계획에 서명하고 앱이 검증한다. Administrator의 확인 후 배정된 담당자가 필요한 생성 접근을 연다. | First 계획·입력·승인자·승인 서명·앱 검증·접근 활성화 참조 |
| A3.2 생성·검증 | Crypto Officer가 First 키를 생성해 응답·키 쌍 식별자·공개키·조회 결과를 저장한다. Administrator가 승인 설정·소유/공유·quorum·노드 상태를 대조하고 Root와 다른 키인지 확인한다. 배정된 담당자가 임시 생성 접근을 회수하고 Administrator가 회수·보호·백업 추적 상태를 확인한다. | 요청/응답·키 식별자·공개키 지문·설정 대조·접근 회수·보호 기록 |
| A3.3 발급 입력 확인 | Crypto Officer가 First 공개키와 승인된 Subject·기간·serial·확장으로 인증서 본문을 작성한다. Administrator가 요청자 권한·발급 허가를 확인하고, **HSM 키 쌍 ↔ 생성 시 취득한 공개키 ↔ 본문의 SPKI**가 일치하는지 대조한다. First issuer=Root Subject, First AKI=Root SKI, 프로파일·serial 중복과 승인한 OCSP·caIssuers의 발급 전 준비 조건도 확인한다. | 발급 요청·권한/허가·승인값·키/공개키/본문 연결 검사·상태 서비스 준비 참조 |
| A3.4 승인·서명 | 실제 승인자 2명 이상이 같은 First 본문을 검토하고 Root 키의 새 key-usage 토큰에 서명한다. Administrator가 본문/토큰·Root 키·세션·기한·승인을 확인한다. Crypto Officer가 명시적으로 Root 서명 실행을 지시하고 응답을 저장해 First 인증서를 조립한다. | 본문·해시·본문 승인과 토큰의 연결·유효 승인·실행/응답·인증서 |
| A3.5 결과 확인 | Administrator가 독립 도구로 Root 서명·본문 일치·Root→First 연결·First 공개키·프로파일을 검사하고 발급 기록을 저장한다. Witness가 실제 관찰 범위와 일탈을 수행 기록에서 확인한다. | 인증서·발급 기록·검사 결과·증거 참조·일탈 또는 없음 |

First 개인키로 CSR에 서명하는 작업과 그 토큰·CRI·CSR 검사 증거는 생성하지 않는다. **CSR 제외는 First 키의 보호·사용 quorum이나 발급 요청의 승인 생략을 뜻하지 않는다.** 상태 서비스의 추가 키·인증서·구축 작업이 필요하면 별도 승인 절차로 준비하고, 이 약식본의 완료로 간주하지 않는다.

## A4 종료 확인·수행 서명

1. **결과 연결:** Administrator가 A2·A3의 검사 결과와 실제 Root·First 키/인증서·발급 기록·증거 목록의 연결을 확인한다. 개별 검사 결과를 참조하되 누락·불일치가 있으면 다시 검사한다. First 실제 serial의 상태 조회와 지속 운영 책임은 준비된 운영 확인 기록에 연결한다.
2. **보호·접근 종료:** Crypto Officer와 배정된 담당자가 임시 세션·토큰·접근을 종료한다. Administrator가 회수 결과·유지 권한, 개인 승인키의 계속 보호, 키·백업·기록의 보호 책임을 확인한다. 신규 키와 최종 권한의 백업 포함·off-site 사본·보호 및 증거 저장 결과를 확인한다.
3. **확인 서명:** 아래 수행 기록과 증거 목록을 고정하고, 각 참여자·Witness가 적용 스크립트대로 수행했는지와 일탈·관찰 제한을 확인해 본인 행에 서명한다. 정상 완료 시 이 확인 서명은 각자 한 번 한다. 작업별 전자 승인 서명은 별도로 유지한다.
4. **보관:** Administrator가 서명된 스크립트·수행 기록·연결된 증거와 종료 판정을 보호된 저장소에 보관·백업하고 결과를 추가 기록한다. 서명 후 추가한 보관 기록은 원래 서명 범위를 바꾸지 않고 별도 작성자·시각으로 연결한다.

백업·로그 수집 등 후속 확인이 남으면 **수행한 범위까지만 서명하고 ‘후속 확인 대기’**로 기록한다. 접근 종료와 보호 인계 후 입회는 마칠 수 있다. 담당자가 남은 항목을 확인해 추가 기록하되 전체 완료·제출 준비 완료로 미리 표시하지 않는다. 후속 보관 확인만을 위해 전원이 다시 입회하거나 기존 서명을 반복하지 않는다. 새 생성·서명이 필요하면 해당 작업의 승인·입회를 다시 갖춘다.

## 이상 발생 시에만 적용

승인 부족·입력/키 불일치·입회 단절·기록 저장 실패·결과 불명 시 후속 요청을 멈춘다. 마지막 확정 상태·원문·일탈을 보존하고, 열린 임시 접근을 회수하며 보호 책임자를 기록한다. Witness가 보지 못한 작업을 사후 입회로 채우지 않는다.

결과 불명에서는 임의 재생성·재서명·삭제하지 않는다. 저장된 서명 응답이 있으면 같은 응답으로 조립·검사만 복구한다. 원인·기존 결과·변경 영향과 필요한 작업 승인을 확인한 뒤, 미실행 작업은 입회 조건을 갖추어 재개한다. 보류·중단 시에도 실제 수행한 범위·일탈·보호 상태를 위 기록에 남겨 확인 서명한다.
