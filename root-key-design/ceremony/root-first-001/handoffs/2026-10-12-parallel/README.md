## 사용자의 목적과 문서 분리

사람이 행사 당일 자기 가이드만 보고 자신의 차례·확인·기록을 수행할 수 있는 세레모니 문서를 만든다. 일반 기록과 책임 확인, 다자 승인을 구분한다. 기술 구현 상세보다 타 부서와 협의할 정책·자료·역할·진행을 우선한다.

| 문서 | 역할 |
|---|---|
| `script.md` | 진행자의 호출·순서·담당·기록 위치 |
| `guides/` | 담당자별 수행·검토 방법·통과/보류 기준 |

| `records/` | 당일 실제 결과·판정·근거·작성자·시각·필요한 서명. 수행 지시는 넣지 않음 |

| `evidence-index.md` | 원문 증거·목록·보관 연결 |

`records/`는 단계별 원본 한 묶음을 여러 사람이 공유해 자기 칸에 직접 작성한다. 개인별로 갖는 것은 자기 가이드다. 개인마다 노트북이 있다고 가정하지 않는다. 자료 양식의 ‘제출’은 행사 검토자에게 제시한다는 뜻이며 외부 등록 신청이 아니다.

## 유지할 사용자 결정과 상태

### 역할과 다자 통제

기본 5명이다. Administrator는 진행·독립 검증·기록·운영 인수를 겸한다. Crypto Officer는 실행과 Key Custodian 1을 겸한다. Key Custodian 2·3, Independent Witness는 각각 별도 사람이다. Administrator와 실행자를 분리하며 Witness는 다른 행사 역할을 겸하지 않는다. 실명·소속·직책은 추후 결정이다. HSM 관리자 겸임은 기존 조건을 따르고 행사 Administrator 직함으로 HSM 관리자 권한을 자동 부여하지 않는다.

- Root·First 키 생성 각각: 같은 세 보유자 중 서로 다른 2명, **2 of 3**. 생성 계획에 개인 승인키로 서명하고 앱이 승인 명단·공개키·대상 계획을 검증한 뒤 제한된 실행 경로로 생성한다. 승인된 계획과 실제 생성 요청의 연결 및 우회 차단이 필요하다.
- 같은 개인 승인키의 공개키를 개인별 CloudHSM CU quorum 등록과 연결하는 설계다. 키 생성 요청 자체를 CloudHSM 네이티브 quorum이 승인한다고 표현하지 않는다. 이 내용은 사용자 채택 설계이며 실제 구현·지원 범위·시험 완료 증거가 아니다.
- S02/S04/S05 인증서·CSR 서명: 본문 검토와 해당 키의 새 key-usage 토큰에 대한 **2 of 3** 승인 후 CloudHSM 서명. 등록 토큰·생성 계획·키 사용 토큰의 서명을 혼동하거나 재사용하지 않는다.
- 1+2, 1+3, 2+3을 허용한다. Crypto Officer의 실행 자체는 승인 1명으로 세지 않는다.
- 관리자·키 관리 quorum 및 `modifiable=false`/`destroyable=false`는 **잠정 기본안**이다. 이번 문서 작업으로 최종 확정하지 않는다. 별도 AWS API·호스트·등록키/코드 변경 통제를 네이티브 quorum으로 대체하지 않는다.

### 키·인증서 결정

다음은 기존 프로젝트 결정 요약이며 공식 규격의 독립 근거가 아니다. 상세 조건은 settings를 확인하고 규격 주장을 추가할 때는 원문을 검증한다.

- Root·First는 서로 다른 P-384 키. 인증서/CSR 서명은 ECDSA + SHA-384.
- Root 유효기간 20년/pathLen 2, First 5년/pathLen 1. 실제 시각은 발급 전에 고정.
- DN은 추후 결정. Serial은 5-A(CSPRNG 기반 최대 159-bit 양수, 0 제외, 원장 예약·중복 차단).
- 확장은 6-A 정책. First에 C2PA 정책 OID, 추가 qualifier/EKU/임의 확장 없음. 구체 필수 확장은 settings 준수.
- First 상태 제공은 AIA + OCSP, AIA에 OCSP와 caIssuers, CDP 생략. 실제 URL·운영 주체·가동 시점은 추후 결정, **OCSP·URL 제공 기능 미구현**. Root 인증서의 AIA/CDP 조건과 혼동하지 않는다.
- First CSR에서 AIA/CDP 생략, 발급용 인증서 본문에 승인한 AIA 추가. 이미 발급한 인증서를 사후 수정하는 방식이 아니다.

- 도구·실제 명령·raw/digest·DER 변환·파일명·검증 명령 등 개발 상세는 후속 작성으로 미룬다. 행사 전 준비·시험이 필요하다는 조건은 유지한다.

## 단계별 전달과 통합

1. A와 B는 각 단계의 자료 ID·호출 ID·역할·항목 ID를 맞춘다. 기존 호출 번호를 불필요하게 변경하지 않는다. 번호 변경이 필요하면 이전/이후 대응표를 B 진행 파일에 남긴다.
2. A는 자료 묶음을 작성·검토한 후 버전/날짜와 경로·항목 ID·가이드 검토 기준 제안을 `materials-progress.md`에 ‘B 반영 가능’으로 올린다. 아직 없는 파일에 확정 링크를 만들지 않는다.
3. B는 그 묶음과 자기 흐름 점검을 연결하여 script·guides·records를 정리하고 반영 여부를 `flow-progress.md`에 남긴다. 추가/수정 자료가 필요하면 A 요청 항목을 분리한다.
4. 완료/요청 상태는 자기 진행 파일에서만 갱신한다. 상대 요청 ID를 참조해 응답을 남기고, 상대 파일은 고치지 않는다.
5. 두 작업의 단계 결과가 준비되면 통합 담당이 자료→검토→기록 연결을 대조하고 공통 evidence-index·승인본 목록·준비 현황·handoff를 갱신한다. 미반영 요청이 있으면 그 단계는 ‘양쪽 통합 완료’가 아니다.
