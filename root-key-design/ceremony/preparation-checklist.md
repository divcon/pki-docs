# Root와 First ICA 세레모니 준비 체크리스트

**먼저 적용 범위와 담당자를 정하고, 키·인증서 설정과 통제 방식을 확정한 뒤, 수행 스크립트를 완성해 테스트 키로 연습하세요.** 운영 키 생성은 그 준비가 끝난 다음입니다. 목표는 Root 키 생성 → Root 자기서명 인증서 발급 → First ICA 키 생성 → First CSR 생성 → Root의 First 인증서 서명까지 수행하고, 그 결과를 승인·검증·입회 기록으로 설명할 수 있게 만드는 것입니다. First ICA는 첫 번째 중간 CA, CSR은 해당 키로 서명한 인증서 발급 요청입니다.

검토 초안 · 2026-10-10. 체크박스는 준비 완료를 확인할 때 표시합니다. 이 문서의 순서·담당 역할·문서 묶음은 프로젝트 준비안이며, C2PA가 지정한 양식은 아닙니다. 아래에서 **원문 요구**, **기존 선택**, **결정 필요**를 구분합니다.

## 지금 시작할 일

첫 준비 회의에서는 아래 다섯 가지를 처리하면 됩니다. 모든 운영 문서를 한 번에 완성하려고 하지 않아도 됩니다.

- [ ] **총괄 담당자와 승인자를 지정합니다.** 보안·PKI 구현·운영·C2PA 신청 담당 역할도 실명으로 배정합니다.
- [ ] **범위를 한 장으로 정리합니다.** 이번 대상은 신규 Root와 공용 First ICA이며, 하위 Issuing ICA와 leaf 발급은 후속 작업입니다. 등록하려는 인증서와 CA/TSA Trust List를 따로 적습니다.
- [ ] **결정 대장의 D01–D06부터 검토합니다.** 적용 기준, 등록 범위, 일정·입회, 생성 환경, 키 값, 다인 통제가 이후 작업의 출발점입니다.
- [ ] **키·인증서 설정표를 채울 담당자와 기한을 정합니다.** 인증서 이름·기간·주소까지 승인해야 서명 직전에 값을 즉석에서 정하는 일을 피할 수 있습니다.
- [ ] **테스트 환경과 독립 입회자 확보를 시작합니다.** 정식 행사일은 통제 시험과 리허설 결과를 보고 확정합니다.

준비 현황은 이 체크리스트에서 관리합니다. [키 생성](key-generation.md)·[인증서 발급](certificate-issuance.md)의 기술 설정과 [CloudHSM 절차](cloudhsm-options.md)를 반영해 행사별 승인본을 작성하고, 설정 원본·부록·실제 명령의 버전과 해시를 고정합니다. 당일 실행 기준은 행사별 승인본입니다. [2026-10-10 감사 결과](audit-2026-10-10.md)의 미해소 항목도 행사 승인 전에 확인합니다.

## 현재 출발점

기존 설계는 **Root → 공용 First ICA → 하위 Issuing ICA → leaf**, Root·First 개인키의 Global CloudHSM 보관, 같은 담당자 그룹의 다인 통제, CRL 없이 OCSP 사용을 선택했습니다. 같은 HSM 클러스터 사용 여부와 실제 조직·계정·정족수는 아직 결정해야 합니다. 이는 프로젝트 선택이며 원문이 요구하는 유일한 구조는 아닙니다. [기존 범위](../requirements.md)

키 생성 옵션 표에는 두 키 모두 **P-384**가 입력되어 있지만, 같은 문서의 설명과 남은 결정에는 곡선이 미정으로 남아 있습니다. P-384를 현재 입력값으로 두고 최종 승인본에서 상태를 통일하세요. 임의로 다른 곡선으로 바꾸거나 승인 완료로 처리하지 않습니다.

기존 상세 스크립트는 두 키를 먼저 생성하는 구성입니다. 이번 준비안은 요청한 순서대로 Root 자기서명 이후 First 키를 생성합니다. 행사 승인본은 두 문서를 이 순서로 재배열하고, 각 키 생성 직후 해당 키의 검사 결과를 남겨야 합니다. 문서의 장 순서를 그대로 실행 순서로 사용하지 않습니다.

## 준비 순서와 다음 단계로 넘어가는 조건

| 순서 | 해야 할 일 | 끝났다고 판단할 기준 |
|---|---|---|
| 1. 범위와 책임 확정 | 적용 정책·버전, 등록 대상, 참여 역할과 독립 입회 방식 결정 | 범위·역할표 승인, 외부 확인 질문과 담당자 지정 |
| 2. 설정과 통제 설계 | 키·인증서 값, 생성·서명·관리자 통제, 백업·증거 보관 결정 | 설정표 승인, 실제 통제 구현과 시험 항목 확정 |
| 3. 도구와 수행 스크립트 준비 | 실행 코드, 검증 도구, 단계별 스크립트, 기록·중단·인계 양식 작성 | 모든 단계에 실제 명령·입력·기대 결과·중단 조건 존재 |
| 4. 전체 리허설 | 테스트 키로 생성부터 서명·검증·백업/복구·종료까지 연습 | 실패 사례 포함 시험 결과 검토, 중대 미비점 해소 |
| 5. 행사 승인 | 리허설 결과와 최종 문서·도구·설정 버전 고정 | 승인자·입회자·실행자에게 같은 버전 배포, 시작 승인 |
| 6. 운영 세레모니 | 승인 스크립트에 따라 실행, 결과·일탈·입회 기록 수집 | 키·인증서·증거 대조, 참여자·입회자 확인 서명 |
| 7. 인계와 제출 | 키·상태 서비스·기록 책임 인수, 내부 승인 및 C2PA 증거 제출 | 운영 준비 판정과 외부 등록 승인 각각 확인 |

입회자 섭외, C2PA 적용 범위 문의, 실행 도구 개발은 병행할 수 있습니다. 다만 미확정 정책에 의존하는 운영 키 생성·서명은 해당 결정과 검증이 끝날 때까지 보류합니다.

## 어떤 문서를 작성해야 하나요

아래는 **일곱 묶음**입니다. 반드시 일곱 파일을 새로 만들 필요는 없습니다. 기존 문서에 필요한 표와 양식을 보완하고, 승인된 행사 사본과 실제 수행 기록을 별도로 보관하면 됩니다.

| 문서 묶음 | 작성할 내용 | 작성 책임과 준비 시점 |
|---|---|---|
| 준비 계획과 결정 대장 | 범위, 적용 기준, 역할·겸임 가능 여부, 입회자, 일정, 미결정 사항, 시작·중단·재개·완료 승인권자 | 총괄 / 첫 회의부터. 이 문서를 사용 |
| 키와 인증서 설정표 | HSM 식별·키 속성·권한, 알고리즘, 인증서 필드·확장·주소, 프로파일 차이의 처리 | PKI 담당 + 보안 / 코드·리허설 기준 확정 전. 기존 두 실행 문서 사용 |
| 행사 수행 스크립트와 실행 코드 목록 | 단계별 명령·승인·검사·기록·중단 조건, 코드·설정·검증 도구의 버전과 해시 | PKI 담당 / 리허설 전. [템플릿](ceremony-script-template.md)을 복사하고 [가이드](script-writing-guide.md)에 따라 작성 |
| 환경과 통제 검증 보고서 | 모듈 적격성, 계정·권한, 생성/서명/관리/복구 우회 시험, 전체 리허설 결과와 미비점 | 보안 + 검증 담당 / 행사 승인 전. [통제 시험](../dual-control-options.md#검증-기준) 활용 |
| 실제 수행 기록과 증거 목록 | 단계별 실제 결과·시각·수행자, 키·CSR·인증서 식별, 로그, 일탈, 참여자·입회자 서명 | 기록 담당 + 입회자 / 빈 양식은 행사 전, 내용은 수행 중 작성 |
| 운영 정책과 인수서 | 공개 CPS 또는 합의한 공개 방식, 접근·변경관리, 백업/복구, 기록 보존, OCSP·폐지·사고·종료 책임 | 운영 + 보안 / 키 보호는 생성 전, 서비스는 운영 개시 전. [운영 모델](../operating-model.md) 구체화 |
| C2PA 신청과 제출 목록 | 신청 역할·계약·Intake, 등록 인증서와 체인, 프로파일 검사, 입회·서명된 스크립트, 보완 요청과 답변 | 신청 담당 / 범위 협의는 조기 시작, 실제 증거는 행사 후 취합 |

CP는 인증서 정책, CPS는 그 정책을 실제로 어떻게 이행하는지 설명하는 인증업무준칙입니다. CP는 상세 키 생성 스크립트에 역할·책임, 행사 승인, HSM과 활성화 재료, 구체 단계, 참여자·입회자의 확인 서명, 일탈 기록을 포함하도록 합니다. 비클라우드 HSM의 행사 장소와 행사 후 물리 보관 관련 항목은 조건부입니다. CloudHSM을 사용해도 자격증명·승인 키의 보호와 접근 통제는 준비해야 합니다. [CP Key Pair Generation and Installation by CAs][cp-generation] · [Activation Data][cp-protection]

## 행사 전에 확인할 체크리스트

### 범위와 사람

- [ ] 적용할 CP·Program·프로파일의 버전과 파일을 고정하고, 신청 시 인정되는 기준인지 확인했습니다.
- [ ] 등록하려는 First 인증서와 제출 체인의 Root를 구분했습니다. 미등록 상위 Root의 적용·증거 범위를 확인하거나, 해결 전에는 보수적으로 수집할 범위를 승인했습니다.
- [ ] 총괄, 실행자, 승인자, 검증자, 기록 담당자, 독립 입회자, 운영 인수자와 대체자를 지정했습니다. 겸임이 독립 입회·다인 통제를 무너뜨리지 않는지 확인했습니다.
- [ ] 신뢰 역할 임명 승인, 적용되는 적격성 확인·교육의 유효 상태, 확인자·일자를 확보했습니다. 민감한 신원조사 원본은 행사 증거에 포함하지 않습니다. [CP Personnel Controls][cp-personnel]
- [ ] 독립 입회자의 독립성, 관찰 범위, 원격/현장 방식, 확인 서명 대상과 수용 조건을 정했습니다. **등록 대상 키의 생성부터 입회**하도록 일정을 잡았습니다.
- [ ] 시작·중단·재개·완료 권한과 결원 시 취소 기준을 정했습니다. 입회자가 자리를 비우거나 기록이 끊겼을 때의 처리도 포함했습니다.

등록 대상 키에는 독립 입회한 생성과 서명된 스크립트가 요구됩니다. CP의 입회 및/또는 기록 문구만 보고 영상으로 등록 증거를 대체하지 않습니다. WebTrust for CA 보고서 대체는 ceremony와 script 적합성을 입증하는 조건이 충족될 때 확인합니다. [Program Certificate Policy][program-policy]

### 환경과 키 보호

- [ ] AWS 계정·리전·클러스터·HSM 모델·모드·버전·실행 호스트를 식별하고, 선택한 구성의 모듈 인증 범위가 적용 요건을 충족하는 자료를 확보했습니다. 제품명만으로 판정하지 않았습니다.
- [ ] IAM, HSM 관리자와 키 사용 계정(CU), 실행 호스트, 코드·설정 배포, 증거 저장소의 권한표를 만들었습니다. 개인 계정·MFA와 필요한 네트워크 경로를 점검했습니다.
- [ ] **키 생성의 다인 통제**를 실제로 검증했습니다. 생성 시 지정한 사용 quorum만으로 생성 명령 자체가 보호된다고 판단하지 않았습니다.
- [ ] Root 서명, First CSR 서명, 키 공유·속성 변경, 관리자 초기화, 승인자 교체, 백업 복구 경로의 단독 우회를 시험했습니다.
- [ ] Root·First의 키 식별·라벨·속성·소유/공유·정족수를 정했습니다. 승인자 개인키의 보관·분실·교체 방법도 정했습니다.
- [ ] B00 초기 설정 인계를 확인했습니다. 사람↔개인 CU/admin↔등록 승인키↔소유/공유를 대조하고 관리자 user/quorum 값, 허용 승인 집합, 지식 분리와 우회 거부 시험을 확인했습니다. 실행자의 자기승인을 고려해 본문 승인과 토큰 승인을 따로 정했습니다.
- [ ] S01/S03 각각 생성 접근 공동 활성화→생성 시 보호 설정→실제값·전체 노드 반영 검사→공개키 추출→생성 접근 회수를 리허설했습니다. 실패·부분 생성 시 자동 재생성하지 않습니다.
- [ ] 키 생성 직후부터의 보관 책임, 보호된 백업, off-site 사본의 범위·근거, 복구 권한·절차를 정하고 테스트 환경에서 복구를 확인했습니다.
- [ ] 신규 두 키와 최종 권한 설정이 포함된 백업의 확인 방법·대기·보류 인계를 정했습니다. 과거 백업 복구로 되살아나는 사용자·권한과 다른 계정 공유를 통제했습니다. 원장·설정·감사로그·승인·최종 증거도 백업 대상입니다. [CP Backup and Recovery][cp-backup]
- [ ] 로그 수집, 시간대·시각 기준, 증거 저장 실패 감지, 무결성·접근 통제·보존·조회 방법을 준비했습니다. 녹화·화면 캡처에 비밀번호나 승인용 비밀이 노출되지 않도록 했습니다.
- [ ] HSM별 관리 로그·AWS 관리·호스트·실행기 요청/응답·승인 기록을 행위별로 연결하고 사람/계정·시각 오차·수집 지연·검토 책임을 정했습니다. HSM 관리 로그가 모든 서명이나 결과 바이트를 보존한다고 가정하지 않습니다. [CP Audit Logging][cp-logging]
- [ ] 발급 인증서 기록의 serial·subject·기간·확장과 값·폐지 상태를 만료 후 최소 1년 보존하도록 정했습니다. 스크립트·로그·영상은 별도 정책의 기간·기산점·권한을 정했습니다. [CP Repositories][cp-repository]

AWS의 공개 quorum 지원 작업 목록에는 키 생성 명령 자체가 없습니다. CLI quorum 토큰은 한 작업·현재 로그인 세션에 한정되며 다른 애플리케이션에서 사용할 수 없습니다. 선택한 실행 경로에서 생성 통제와 서명 통제를 각각 구현·검증해야 합니다. [AWS 지원 작업][aws-services] · [AWS 토큰 제약][aws-use]

CA 백업에는 원본과 같은 다인 통제, 적어도 한 off-site 사본, 평문 반출 금지와 연간 계획 검토가 요구됩니다. off-site를 어떤 장애 영역으로 구성할지는 정책으로 정하며, 같은 클러스터의 복제나 자동 백업만 보고 충족을 선언하지 않습니다. [CP Controls for CA Keys][cp-protection]

### 인증서와 실행 도구

- [ ] Root·First 각각의 C/O/CN, 유효기간과 UTC 시각, serial 생성·중복 방지 규칙, 서명 알고리즘·해시를 승인했습니다. Root 20년·First 5년이라는 예시를 확정값으로 사용하지 않았습니다.
- [ ] SKI/AKI, KU/EKU 포함 여부, Basic Constraints, pathLen, 정책 OID, 확장별 critical 여부와 AIA/CDP를 값 또는 미포함으로 명시했습니다. Root AIA/CDP 금지, First의 OCSP 주소, CRL 미사용이어도 필요한 cRLSign 비트를 포함해 프로파일과 대조했습니다.
- [ ] Root AKI, First AKI 설명, AIA의 caIssuers 등 기존에 발견한 원문/schema 차이에 대해 적용 해석과 검사 결과 처리 방식을 정했습니다. 필요한 외부 수용 확인을 남겼습니다.
- [ ] First 발급 요청자의 권한과 발급 허가, 요청 정보의 확인 자료를 마련했습니다. First 공개키·CSR 서명 검증과 CSR 확장 허용 규칙을 구현했습니다.
- [ ] 승인자가 보는 인증서 내용과 실제 서명할 `TBSCertificate` 바이트·키를 연결했습니다. 승인 후 입력·키·설정이 바뀌면 서명을 차단합니다.
- [ ] First CSR의 `CertificationRequestInfo` DER도 서명 전에 고정했습니다. 세 번의 서명 각각 Q01–Q08의 본문 승인, 현재 CLI 세션·작업별 토큰, 개인별 서명, 승인 집합·기한 검사, 명시적 실행과 응답 보존을 실제 명령으로 연결했습니다.
- [ ] CSR/인증서 조립, ECDSA 서명 형식과 해시 처리, 별도 검증 도구의 서명·키·체인·프로파일 검사를 테스트 키로 확인했습니다.
- [ ] 중복 요청, HSM 응답 단절, 결과 저장 실패, 승인 만료 후 재개를 시험했습니다. 결과 불명 상태에서 자동 재생성·재서명하지 않습니다.
- [ ] 원장의 준비·요청 시작·응답 보존·조립·발급 저장·결과 불명 상태를 구분했습니다. 보존된 동일 응답의 재조립과 새 HSM 서명을 구분하고, 응답 없는 서명 결과를 로그에서 복구할 수 있다고 가정하지 않았습니다.
- [ ] First 인증서에 넣을 OCSP 주소와 운영 주체를 확정했습니다. 필요한 Root 위임 OCSP 응답자 키·인증서·서비스를 이번 행사에 포함할지 별도 준비할지 정했습니다.

필드 값은 [Root 원문 프로파일][root-profile]과 [First 원문 프로파일][first-profile]로 확인합니다. CA 발급에는 문서화한 절차·다인 통제·지식 분리가 필요하며, Root의 인증서 서명에는 신뢰 역할 담당자 최소 두 명과 한 명의 명시적 실행이 요구됩니다. [CP Certificate Issuance][cp-issuance]

### 리허설과 최종 승인

- [ ] 테스트 키로 아래 당일 순서를 끝까지 수행하고, 실제 사용할 스크립트·도구·검증·증거 양식을 함께 시험했습니다.
- [ ] 승인 부족, 입력 바꿔치기, 관리자 우회, 입회/로그 중단, 연결 단절, 백업 복구를 시험하고 결과를 검토했습니다.
- [ ] 운영/테스트 환경 차이와 남은 위험을 기록했습니다. 필수 통제 미달을 단순 위험 수용 서명으로 통과시키지 않았습니다.
- [ ] 문서·코드·설정·검증 도구의 버전과 해시, 참가자 명단, 실제 실행 순서를 고정했습니다. 승인 뒤 변경되면 영향 검토·필요한 재시험·재승인을 합니다.
- [ ] 증거를 읽고 인수할 사람까지 포함해 준비 완료를 확인하고 행사 수행을 승인했습니다.

## 당일에는 이 순서로 진행합니다

아래는 행사 스크립트의 목차입니다. 각 행의 명령과 판정값은 [스크립트 작성 안내](script-writing-guide.md)에 따라 채웁니다. Root 자기서명은 **Root 인증서를 만드는 작업**이고, First CSR은 **First 키로 서명한 인증서 발급 요청**이며, First 인증서는 **Root 키로 서명**합니다.

| 단계 | 수행과 확인 | 반드시 연결할 결과 |
|---|---|---|
| S00 시작 확인 | 참석·독립성·권한·환경·문서 해시 대조, 기록/입회 시작, 시작 승인 | 참석표, 환경 점검, 승인 기록 |
| S01 Root 키 생성 | 승인된 옵션으로 HSM 내부 생성, 속성·권한·공개키 검사 | Root 키 식별자, 공개키 지문, 생성 로그 |
| S02 Root 자기서명 | 최종 본문 승인, Root 키 사용 승인과 명시적 서명, 자기서명·프로파일 검사 | Root DER/PEM, 본문·승인·서명·검사 기록 |
| S03 First 키 생성 | 별개 키 생성, 속성·권한·공개키 검사, 생성 직후 보호 확인 | First 키 식별자, 공개키 지문, 생성 로그 |
| S04 First CSR 생성 | First 키 사용 승인·CSR 서명, 공개키 일치·CSR 서명·요청 권한 확인 | CSR, 검사·요청·승인 기록 |
| S05 First 인증서 발급 | 최종 본문 승인, Root 키 사용 승인과 명시적 서명, 체인·프로파일 검사 | First DER/PEM, 체인, 본문·승인·서명·검사 기록 |
| S06 전체 결과 확인 | 키→CSR→인증서→로그 대조, 백업 확인, 일탈 처리, 참여자·입회자 확인 서명 | 증거 목록과 해시, 수행 기록, 일탈·서명 |
| S07 인계와 종료 | 운영 인수, 임시 권한 회수, 세션·사용 가능 승인 종료, 자료 봉인 | 인수서, 접근 종료·보관 기록 |

S01과 S03의 키 생성 증거는 각각 수행 시점에 확보합니다. S06의 서명으로 없었던 입회나 통제를 사후에 만들 수 없습니다. 단계가 중단되면 생성된 키·발급된 인증서의 상태를 먼저 확인하고 재개 여부를 결정합니다.

## 무엇을 누구에게 제출하나요

**행사 승인 자료, 내부 완료 증거, C2PA 신청 자료는 제출 시점과 받는 사람이 다릅니다.** 공개 인증서와 달리 내부 로그·서명자 정보·계정 구조는 접근을 제한하고, 제출 목적에 필요한 범위를 정합니다.

| 받는 사람과 시점 | 제출할 묶음 | 확인받을 내용 |
|---|---|---|
| 내부 승인자 / 행사 전 | 범위·역할·결정 대장, 키/인증서 설정, 최종 스크립트·코드 목록, 환경·통제 시험과 리허설 결과, 백업·증거 계획 | 운영 키 생성과 행사 수행 승인 |
| 입회자 / 행사 전과 직후 | 승인 스크립트·관찰 범위·검사 기준·서명 양식, 이후 실제 수행 기록·일탈·증거 목록 | 실제 관찰한 생성과 승인 스크립트 준수 여부의 확인 서명 |
| 내부 보안·운영 / 행사 후 | 키 목록, 공개키·CSR·인증서·체인, 검사·승인·로그, 서명된 수행 기록, 백업·접근 종료·운영 인수 자료 | 행사 완료와 보관 책임 인수, 별도 운영 개시 판정 |
| C2PA Program / 신청·심사 | 아래 직접 제출 항목 및 관리자 요청 보완 자료 | 등록 대상·프로파일·키 생성 증거·계약상 준수 심사 |

### C2PA 직접 제출 항목

- [ ] **Expression of Interest와 CA 역할 계약**: 신청 법인·역할·대표 권한을 준비하고 안내된 계약 절차를 완료합니다. TSA만 단독으로 신청할 수 없다는 조건을 반영합니다.
- [ ] **Intake와 인증서 set**: 추가할 CA/TSA 인증서 set에 맞는 Intake를 준비합니다. 등록 인증서와 상위 체인의 각 PEM 인증서를 원문 안내에 따라 빈 줄로 구분합니다. 시험용 CA/TSA entry를 제출하지 않습니다.
- [ ] **프로파일 검증 증거**: 등록 희망 Root 및/또는 ICA 인증서별 적용 프로파일·검사 결과와 처리한 차이를 제출합니다.
- [ ] **독립 입회한 키 생성 증거와 서명된 스크립트**: 등록할 인증서의 공개키가 실제 입회한 생성 키와 연결되도록 키 지문·수행 기록·서명을 묶습니다. 조건부 WebTrust 대체 경로를 택했다면 해당 보고서의 범위와 수용 여부를 확인합니다.
- [ ] **보완 요청 대응**: 관리자·승인자의 질문, 제출 버전, 답변과 시정 결과를 기록합니다. Notice와 해당 Trust List 공개 record까지 확인해야 등록 완료로 표시합니다.

위 절차와 직접 요구는 [Program Certificate Policy][program-policy], [Application과 Intake][program-intake], [CA Evidence Request와 승인][program-evidence]에 근거합니다. 법적 계약으로 CP 준수를 확약하므로, 제출 항목만 갖추고 운영 의무를 생략할 수는 없습니다.

### 추가 요청에 대비해 보관할 자료

CPS 또는 합의한 공개 업무관행, 모듈 인증·설정, 다인 통제·권한 시험, 백업/복구·off-site 근거, 로그·기록 정책, 폐지·OCSP·사고 대응, 내부 승인과 운영 인수 자료를 준비합니다. 이 모두를 항상 같은 형식으로 업로드하라는 공개 제출 목록으로 해석하지 않습니다. 신청 당시 계약·관리자 요청에 따라 제출 범위를 정합니다.

**제출하지 않을 것:** CA 개인키, 승인자 개인키, 비밀번호, 복구용 비밀·인증 토큰, HSM 백업 원본. 요청 증거는 이러한 비밀 없이 통제와 결과를 입증하도록 구성합니다. 원본 증거와 제출용 사본·가림 처리 내역은 구분해 관리합니다.

## 아직 결정해야 할 사항

각 행에 담당자·기한·결정·승인 근거를 기입하세요. 기존 선택을 다시 열기보다 비어 있는 실행 값과 모순부터 닫습니다. **D01–D06은 첫 회의**, D07–D12는 스크립트·리허설 확정, D13–D16은 인계·제출 준비에 연결하되 표의 마감 시점을 따릅니다.

| ID와 주제 | 결정할 질문 | 늦어도 필요한 시점 |
|---|---|---|
| D01 적용 기준과 Root 범위 | 어떤 CP·Program·프로파일 버전인가? 미등록 Root에 적용할 조항·증거는 어디까지인가? | 생성 승인 전 |
| D02 등록 대상과 용도 | First를 CA TL/TSA TL 중 어디에 올릴 것인가? 공용 First 하나라는 목표가 각 목록에서 수용되는가? 상위 Root 제출은 어떤 의미인가? | 생성 계획 전, 수용 확인 담당 지정 |
| D03 행사와 입회 | 한 행사로 할 것인가? 장소·원격 방식·입회자의 독립성·서명 형식은 무엇인가? 분리하면 키 custody와 증거를 어떻게 연결하는가? | 입회 계약·일정 확정 전 |
| D04 환경과 모듈 | 같은 클러스터를 쓸 것인가? 실제 모델·모드·인증 범위·리전·호스트·시간 기준은 무엇인가? | 구현·시험 기준 확정 전 |
| D05 키 값 | 현재 입력한 P-384를 최종 승인하는가? 라벨·식별·용도·속성·소유권·공유 대상은 무엇인가? | 리허설 전 |
| D06 다인 통제 | 생성은 어떻게 통제하는가? 사용/관리의 N/M과 실행자 승인 포함 여부, 관리자·복구 우회 차단, 승인 키 보호는 무엇인가? | 구현·시험 후 생성 승인 전 |
| D07 인증서 값 | DN·기간·serial·해시·확장·정책 OID·주소는 무엇인가? Root AKI·First AKI·schema 차이를 어떻게 처리하는가? | 리허설·발급 승인 전 |
| D08 실행 도구 | 누가 어떤 CLI/앱을 실행하는가? 세션 유지, 본문 승인 연결, 검증 도구, 원장·결과 저장 책임은 누구인가? | 리허설 전 |
| D09 실패와 재개 | 결과 불명·중복·잘못된 인증서·입회 중단 때 누가 조사·재개·폐기·재생성을 승인하는가? | 리허설 전 |
| D10 백업과 복구 | 신규 키·최종 권한 포함을 어떻게 확인하는가? 백업 대기·off-site·비키 데이터·과거 권한 복구 통제·복구 목표·퇴역 기준과 연간 검토자는 누구인가? | 생성 승인 전 |
| D11 기록과 서명 | 인증서 기록 만료+1년 이상과 다른 기록의 보존기간·권한은 무엇인가? 로그 원천·완료 판정·서명 범위·후속 증거 봉인은 어떻게 연결하는가? | 생성 승인 전 |
| D12 역할과 대체자 | 누가 시작·중단·재개·완료·인수를 승인하는가? 역할 임명·적격성·교육을 누가 확인하며 겸임·퇴사·분실·결원에도 정족수를 유지하는가? | 리허설·행사 승인 전 |
| D13 OCSP 준비 | First 상태를 누가 제공하는가? Root 위임 응답자 준비를 별도 행사로 할 것인가? 주소·가동 시점·장애·폐지 책임은 무엇인가? | 주소는 발급 전, 서비스는 운영 개시 전 |
| D14 공개 정책과 인계 | CPS 또는 C2PA와 협의한 공개 방식은 무엇인가? 생성 직후와 행사 후 운영 책임·사고 연락·종료 계획은 누구에게 있는가? | 생성 관행은 생성 전, 운영 준비는 개시 전 |
| D15 신청 담당과 제출 방식 | 법인 계약 서명자·신청 담당자·연락 창구·제출 언어/형식·보안 전달 방법·보완 응답자는 누구인가? | 입회·증거 형식은 행사 전, 제출본은 신청 전 |
| D16 향후 교체 | Root/First 교체와 만료 전 재생성 시점, 신뢰 앵커 배포·복구 책임을 누가 맡는가? | 기간 승인 전 책임·방향 결정, 상세 계획은 운영 인계 |

결정 기록은 다음 한 줄 형식으로 시작할 수 있습니다.

> D06 / 담당: ___ / 기한: ___ / 결정: ___ / 승인자·일자: ___ / 적용 문서·버전: ___ / 시험 또는 외부 회신: ___ / 상태: 미정·검토 중·승인

우선 외부 확인할 질문은 **미등록 Root의 범위**, **공용 First의 CA/TSA 목록별 수용**, **선택한 입회·서명 방식**, **실제 사용할 프로파일과 schema 차이의 처리**입니다. 담당자가 초기에 확인하고, 답변이 필요한 결정을 임의로 승인 처리하지 않습니다.

## 완료와 보류를 어떻게 판단하나요

- [ ] **세레모니 완료**: 두 키·두 인증서·First CSR의 연결, 신규 키와 최종 데이터의 백업, 로그 수집과 검사를 확인하고 수행 기록·일탈·참여자 및 입회자 서명·보관·접근 종료를 완료했습니다. 백업/증거 대기는 완료와 구분합니다.
- [ ] **운영 준비 완료**: 키·백업·기록 인수와 폐지·OCSP·사고 대응·공개 정책 등 적용되는 운영 조건을 충족했습니다.
- [ ] **등록 완료**: 신청 증거가 수용되고 Notice와 해당 Trust List record를 확인했습니다.

필수 통제·입회·검사·증거가 빠졌으면 해당 단계의 시작 또는 완료·배포·제출을 보류합니다. 문서 색인만 빠진 경우에는 원래 증거로 보완할 수 있지만, 생성 당시 없었던 통제는 사후 서류로 대체할 수 없습니다. 재생성 필요성은 결함과 인정 가능한 증거를 확인한 뒤 판단합니다.

잘못 발급한 인증서를 같은 키로 다시 만들기 전에 적용 정책을 확인해야 합니다. CP는 동일 키의 갱신과 이미 인증서를 발급한 키 쌍에 대한 새 인증서 발급을 금지합니다. 그래서 **서명 전 최종 필드 승인**과 실패 시 상태 확인이 중요합니다. [CP Certificate Renewal과 Modification][cp-renewal]
