# 004가 002·003보다 나아진 점

기준: C2PA CP v0.2·Conformance Program v0.2 (commit `2466172`), [003 심사](../root-first-003/c2pa-review-2026-10-13.md), 002 재평가(2026-10-13). 아래 평가는 문서 설계 기준이며, 리허설과 실제 수행으로 확인한 결과가 아니다.

## 002보다 나아진 점

1. **키 생성 통제를 실제로 구현할 수 있게 됐다.** 002는 "승인 앱 서명 → 임시 생성 접근 열기"라는 구조만 있고, 앱과 접근 수단이 모두 미정이었다. 게다가 A1에서 실행자가 미리 로그인해 두면 접근 통제가 의미가 없었다. 004는 키를 만드는 명령에서 사용·관리 Quorum 2를 지정해, 키가 생긴 순간부터 KC 2명의 승인 없이는 쓰거나 바꿀 수 없게 한다. 독립 입회자가 이를 확인한다. C2PA는 이 방식을 다인 통제로 인정한다고 답변했다(2026-10-13). 별도 개발물 없이 CloudHSM 기본 기능만으로 성립한다.
2. **HSM을 처음부터 세우는 절차가 들어왔다.** 클러스터 초기화, 활성화, admin·CU 생성, Quorum 등록이 행사 안에서 입회 하에 수행되고 기록된다. 002는 이 과정을 전제로만 두어서, 승인키가 어떻게 등록됐는지에 대한 증거가 없었다.
3. **승인키와 토큰 서명 방식이 정해졌다.** 002는 `{{승인_서명_명령}}`과 승인키 보관이 비어 있었다. 004는 KC별 KMS 키(본인만 서명 가능, MFA 필수)로 서명한다. 서로 다른 사람이 승인했다는 사실을 CloudTrail로 독립적으로 증명할 수 있다.
4. **FAIL 처리 규칙이 생겼다.** 002는 서명을 반복하지 않는 규칙만 있었다. 004는 "같은 키에 인증서를 다시 발급하지 않고, FAIL이면 새 키로 다시 생성한다"를 명시했다. 잠금 속성(`destroyable=false`)을 빼서 이 규칙과 충돌하지 않게 했다.
5. **만들어야 할 것이 줄었다.** 승인 앱, 접근 열기/닫기 수단, serial 원장이 필요 없어졌고 접근 담당자 역할도 없어졌다. 002의 "아직 정해지지 않은 것"이 절반 가까이 줄었다.
6. **Root 노출이 줄었다.** 백업과 off-site 사본을 확인한 뒤 HSM을 삭제한다. 이후 Root 키를 쓰려면 HSM 재생성(IAM-Op), CO 로그인, KC 2명 승인이 모두 필요하다.
7. **직무 분리가 강해졌다.** 002는 실행자가 KC1을 겸할 수 있어 2인만으로 Root 서명이 가능했다. 004는 승인자 3명이 모두 실행자와 독립이다.

## 003보다 나아진 점

1. **C2PA 심사에서 바로 떨어지는 항목을 해소했다.** Root AKI 누락과 ICA의 AIA+CDP 병행은 부록 A로 고쳤다. 리허설에서 같은 설정으로 만든 테스트 인증서가 공식 schema를 통과해야 행사를 시작할 수 있다(4.6 ④).
2. **Root 서명과 키 사용이 실제로 2인 통제된다.** 003은 OpenSSL PKCS#11 경로로 서명한다. 그런데 AWS 문서에 따르면 Quorum 토큰은 CloudHSM CLI 안에서만 쓸 수 있고 다른 애플리케이션에서는 쓸 수 없다. 따라서 사용 Quorum이 걸린 키는 OpenSSL로 서명할 수 없고, 003대로 하려면 Quorum을 빼야 해서 Root 자체서명을 CO 혼자 하게 된다. 004는 `crypto sign --approval` 경로를 쓰므로, HSM이 토큰 없는 서명을 직접 거부한다(4.6 ②로 확인).
3. **CP 위반 절차를 없앴다.** 003의 "FAIL 시 키는 유지하고 인증서만 재발급"을 금지 규칙으로 바꿨다.
4. **키를 잃을 위험을 막았다.** 003은 "최신 백업 READY"만 보고 HSM을 삭제했다. 004는 다음을 모두 확인한 뒤에만 삭제한다.
   - 백업이 키 생성 이후에 만들어졌는지
   - 만료 방지 설정이 됐는지
   - 다른 리전에 사본이 있는지
5. **Quorum 설정의 순서 오류와 우회 여지를 고쳤다.**
   - 순서: 003은 Quorum 값을 설정한 뒤 CU를 만들어, 사용자 생성에 admin 승인이 필요해지는 순서였다. 004는 사용자를 모두 만든 뒤 Quorum 값을 설정한다.
   - 우회: `quorum` 서비스 값도 2로 설정하는 것을 필수로 했다.
   - 일관성: Root 3-of-5 예시와 KC 3명 사이의 불일치를 2-of-3으로 통일했다.
6. **Script가 결정적이 됐다.** 다음과 같은 미결 표시와 선택 단계를 본문에서 모두 없애고, 미결 항목은 부록 D에 모았다.
   - "[템플릿 전용]", "[리허설 확인]"
   - "불가 시 ~로 대체"
   - "[권장]" 단계
   - `<5479~7305>` 같은 범위 값
7. **심사원이 묻는 증거가 갖춰졌다.**
   - IW 독립성 기준
   - 신뢰 역할 적격성 확인
   - 활성화 자재 목록과 봉투 일련번호
   - 반입 단말 목록과 MFA
   - CMVP 번호 기재 위치
   - 준수 여부를 표시하는 참여자 서명
8. **CSR과 유효기간이 승인된 결정과 일치한다.** CSR에 요청 확장을 포함하고, 유효기간은 20년/5년이다.
9. **근거 인용이 정확해졌다.** 003의 "CP §6.1.1", "CP 8.6"처럼 CP v0.2에 없는 번호 대신 조항 제목으로 인용한다.

## 대신 잃거나 남은 것

| 항목 | 내용 |
|---|---|
| 002의 계획 승인 서명 | 002는 생성 계획 자체에 승인자의 전자서명을 남겼다. 004는 생성 시 Quorum 지정과 입회로 대체한다. 생성 승인의 암호학적 증거는 없어지고, 키 속성 조회 결과와 입회 증거가 남는다. C2PA가 이 방식을 인정했다 |
| 002의 OCSP 준비 확인 | 범위 밖으로 뺐다. ICA는 OCSP 주소를 갖고 발급되지만, 응답자 인증서는 후속 Root 행사에서 발급한다 (README 결정 6, 001 검토 C04가 여전히 열림) |
| 003의 단순한 도구 구성 | OpenSSL만으로 끝나던 구성 대신 TBS 도구와 검사 도구를 개발해야 한다. 일정을 가장 크게 좌우하는 항목이다 |
| 003의 룸 녹화 | 뺐다. CP는 입회만으로 충족하지만 증거의 양은 줄어든다 |
| KC 2명의 공모 | KC 2명은 각자의 `cu_kcN` 계정으로 CO 없이 키를 사용할 수 있다. CP의 2인 요건은 충족하며, 오프라인화 이후에는 IAM-Op도 필요하다 |
| 미검증 명령 | CloudHSM CLI·AWS 명령 일부는 실행해 보지 않았다 (부록 D의 D2~D5, D11) |
