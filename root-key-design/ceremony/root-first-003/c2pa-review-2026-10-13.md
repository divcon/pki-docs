# root-first-003 행사 Script의 C2PA v0.2 적합성 심사

- 심사일: 2026-10-13 (행사 예정일 2026-10-15)
- 대상: [`script.md`](script.md) (KGC-C2PA-2026-001, 템플릿 v0.1, 미커밋 상태)
- 기준: C2PA Conformance Program v0.2, Certificate Policy(CP) v0.2, cert-profiles(YAML·schema). 공식 저장소 고정본 commit `2466172859fad1215f7aaf7e3768b41a0ac29abc` (로컬 `conformance-public/`)
- 관점: Trust List 등록 심사에서 C2PA 심사원이 "독립 입회한 키 생성 행사와 서명된 Script"(Program §Certificate Policy) 및 "CP 프로파일에 대한 인증서 검증"을 확인한다고 가정
- 한계: 문서 심사와 소프트웨어 키 dry-run만 수행했다. 실제 CloudHSM·KMS·Quorum 동작은 시험하지 않았다.

## 판정

**불합격 (현 상태로 행사 수행 불가).** Script 구조(역할·승인·HSM·단계·서명·편차)는 CP의 Script 필수 요소를 갖추고 있고, 알고리즘·Basic Constraints·Key Usage 등 핵심 프로파일 선택도 맞다. 그러나 아래 Critical 5건 중 2건은 **Script대로 발급하면 공식 schema 검증에 실패하는 인증서**가 나온다는 것을 dry-run으로 재현했고, 1건은 실패 시 대응 절차 자체가 CP의 SHALL NOT을 위반한다. 다인 통제는 핵심 메커니즘이 "[리허설 확인]"으로 남아 있어 입증할 수 없다.

| 등급 | 건수 | 의미 |
|---|---|---|
| Critical | 5 | 그대로 수행하면 비적합 산출물 또는 CP SHALL 위반. 행사 전 반드시 수정 |
| Major | 9 | 심사에서 증거 부족·부적합 지적 대상. 행사 전 수정 권고 |
| Minor | 7 | 개선 사항 |

## Dry-run 증거

부록 A의 `root.cnf`/`ica.cnf`와 5.5.3·5.6.3·5.6.5 명령을 OpenSSL 3.0.13 + 소프트웨어 P-384 키로 그대로 실행한 뒤, 공식 schema의 확장 제약(`rootCA.cert.schema.json` `c2paRootCaConstraints/allOf/4`, `intermediateCA.cert.schema.json` `c2paFirstIntermediateCaConstraints/allOf/4~7`)으로 검사했다. 디코더는 확장 부분만 schema 입력 형식으로 변환한 간이 구현이다.

| 대상 | 결과 | 원인 |
|---|---|---|
| Root (script의 `authorityKeyIdentifier = keyid`) | **FAIL** `allOf/4` | OpenSSL 3은 자체서명 인증서에서 `keyid`만 지정하면 AKI를 넣지 않음. Root schema는 AKI 존재를 요구 |
| Root (`keyid:always`로 변경) | PASS | AKI = SKI 포함 |
| ICA (script의 OCSP AIA + CDP) | **FAIL** `allOf/5` | schema가 `oneOf`라 두 분기 모두 만족하면 실패 |
| ICA (CDP 제거, OCSP·caIssuers AIA만) | PASS (`allOf/4~7`) | |
| ICA CSR (5.6.3 명령) | Requested Extensions 없음 | First CSR schema `allOf/2`의 필수 요청 확장(BC·KU·CP) 누락 |
| Serial | 20 octet 양수 난수 | 프로파일 충족 |
| `openssl verify` 체인 | OK | |

## Critical

### K1. ICA에 OCSP AIA와 CDP를 함께 넣어 First schema 실패 — 부록 A `ica.cnf`

> **코멘트:** 심사원이 공식 schema로 인증서를 검사하면 바로 떨어지는 항목이다. YAML/CP 문구만 보면 병행이 금지되지 않은 것처럼 읽히지만, Program이 검증 기준으로 제공하는 schema가 `oneOf`다. 또한 프로젝트가 2026-10-12 확정한 U04(방식 A: AIA에 OCSP·caIssuers, **CDP 생략**, `root-first-001/settings.md`)와도 어긋난다. 003에서 CDP가 다시 들어간 경위가 기록돼 있지 않다.

- 조치: `crlDistributionPoints` 줄 삭제. 5.5.4 기대 출력과 verify_profile.py에 "CDP 부재" 검사 추가.
- 근거: First YAML(AIA/CDP 조건), `intermediateCA.cert.schema.json` `allOf/5`.

### K2. Root AKI가 생성되지 않아 Root schema 실패 — 부록 A `root.cnf`

> **코멘트:** CP의 Root YAML은 AKI를 OPTIONAL로 두지만 Root schema는 존재를 요구한다. 두 기준을 모두 만족하려면 AKI를 넣어야 하는데, 현재 설정은 OpenSSL 3 기본 동작 때문에 AKI가 빠진다. 5.5.4의 기대 출력에도 AKI 확인 항목이 없어 행사 중에 발견되지 않는다.

- 조치: `authorityKeyIdentifier = keyid:always`. 5.5.4 기대 출력에 "SKI 존재, AKI keyid = SKI" 추가. CloudHSM PKCS#11 provider 경로에서도 같은 결과가 나오는지 리허설에서 확인.

### K3. "FAIL 시 키는 유지하고 인증서만 재발급" — 5.7 하단

> **코멘트:** 근거 원문(CP v0.2 고정본 `C2PA Certificate Policy.md` 575행, *Certificate Life-Cycle Operational Requirements* › *Certificate Renewal*):
> "Certificate renewal (with the same key) is not permitted, and the CA SHALL NOT issue a new certificate for a key pair for which it had previously issued a certificate."
> 보조 근거(583행, *Certificate Modification*): "Certificate modifications SHALL NOT be permitted by CAs operating in conformance with this CP." 5.7의 상황은 같은 키에 확장값을 고친 인증서를 내는 것이므로, RFC 3647 용어로는 renewal보다 modification에 더 가깝다.
>
> **적용 범위 주의:** 두 조항 모두 문언에 subscriber 한정이 없다. 바로 옆의 *Certificate Re-key*(579행)는 "subscriber certificate re-key"로 한정한 것과 대비된다. 따라서 문언상 Root 자체서명 인증서와 Root가 발급한 ICA 인증서에도 적용된다. 반면 CP *Overview*는 이 CP를 Claim Signing 인증서 발급 요건으로 소개하고, 해당 장(*Certificate Life-Cycle Operational Requirements*)도 대부분 subscriber 절차를 다룬다. 따라서 **CA 인증서에 적용되는지를 C2PA가 명시적으로 밝힌 것은 아니며, 이는 해석 사항이다.** 이 검토는 문언 그대로 적용하는 보수적 해석을 택했다. 서명했지만 배포하지 않은 인증서가 "issue"에 해당하는지도 CP가 정의하지 않는다.
>
> 위 K1·K2처럼 프로파일 결함이 있는 Script에서는 이 경로가 실제로 쓰일 가능성이 높아 위험이 크다. 이전 검토(001)에서는 "동일 키 즉시 재발급 금지·결과 불명 시 중단"이 설계에 있었는데 003에서 반대로 바뀌었다. 해석 논란을 피하는 가장 확실한 방법은 FAIL이 나지 않도록 서명 전에 검증하는 것이다.

- 조치:
  1. 서명 **전에** 검증: 리허설에서 같은 설정 파일로 테스트 키 인증서를 만들어 공식 schema + verify_profile.py로 PASS를 확인하고, 행사 당일에는 설정 파일 해시만 대조(4.7)한다.
  2. 행사 중 FAIL이면: 중단하고 8장 기록 → 해당 인증서는 폐기·비공개 처리 → **키 파기 후 새 키로 재생성**(별도 승인). 문구를 이에 맞게 교체.

### K4. CA 키 생성·사용의 다인 통제가 확정되지 않음 — 5.4.10~5.4.11, 템플릿 주석, 5.5.1, 5.5.3, 5.6.5

> **2026-10-13 후속:** C2PA가 다음 방식을 키 생성 다인 통제로 인정한다고 답변했다. 생성 명령은 CloudHSM CU 1명이 실행하고(생성 자체에는 Quorum이 걸리지 않음), 생성할 때 키 속성으로 사용·관리 Quorum을 지정하며, 독립 입회 하에 수행하는 방식이다. 따라서 아래 (a)의 생성 부분은 이 방식으로 충족할 수 있고, 2번 "CU 비밀번호 분할"은 필수가 아니다. 다만 (b)~(d)의 키 사용 통제와 1번·3번(키 사용 Quorum 경로, key share)은 여전히 확정이 필요하다. **1번은 AWS 문서로 결론이 났다:** "You can only use a CloudHSM token within the CloudHSM CLI. You can't use it to authenticate in a different application." ([AWS](https://docs.aws.amazon.com/cloudhsm/latest/userguide/key-quorum-auth-chsm-cli-crypto-user.html)) 따라서 사용 Quorum이 걸린 키는 OpenSSL PKCS#11 경로(5.5.3·5.6.5)로 서명할 수 없고, `cloudhsm-cli crypto sign --approval` 경로가 필요하다. 반영안은 [root-first-004](../root-first-004/script.md)에 있다.

> **코멘트:** 심사의 핵심이다. CP는 (a) 키 생성을 다인 통제·지식 분할 하에 수행하고(*Key Pair Generation by CAs* 3.2), (b) 한 사람이 Root/Intermediate 서명키에 단독 논리 접근을 할 수 없도록 하며(*Key Usage and Access Control* 1), (c) Root 서명은 신뢰 역할 2인 이상이 수행하고(*Certificate Issuance* 1, *Separation of Duties* 3), (d) CA 인증서 발급은 다인 통제·지식 분할을 따르도록(*Certificate Issuance* 2) 요구한다. Script는 admin Quorum(사용자 관리)은 잘 설계했지만, **실제 키를 쓰는 CU 쪽 통제가 정해지지 않았다.**

구체적 공백:

1. **키 사용 Quorum 적용 방법이 "[리허설 확인]"이고 대체 경로가 "cloudhsm-cli crypto sign으로 대체하거나 CU 비밀번호 분할로 보완"으로 열려 있다.** 승인·서명된 Script는 결정적이어야 한다. 어느 경로로 할지에 따라 5.5.3·5.6.5의 명령과 참여자가 달라진다.
2. **cu_root/cu_c2pa 비밀번호를 누가 어떻게 설정하는지가 5.4.10에 없다.** 6장은 "CO/CU 비밀번호 분할본"을 전제하지만 실행 단계에 분할 입력·봉인 절차가 없다. 5.6.5만 "cu_root 분할 로그인"을 언급하고 5.5.1·5.5.3은 언급하지 않는다. CO 혼자 cu_root 비밀번호를 알면 CO 단독 접근이 된다.
3. **cu_kc1/cu_kc2에 Root·ICA 키를 `key share`하는 것은 키 사용 Quorum이 실제로 적용될 때만 안전하다.** Quorum이 적용되지 않으면 KC1이 자기 cu_kc1 비밀번호만으로 Root 키를 사용할 수 있어, 오히려 단독 접근자가 늘어난다. 대체 경로(비밀번호 분할)를 택할 경우 key share를 하면 안 된다.
4. OpenSSL PKCS#11 경로에서 CU PIN을 어떻게 입력하는지(프롬프트, 환경변수, 설정 파일) 정의가 없다. 파일·환경변수로 넘기면 활성화 데이터가 디스크·로그에 남는다.

- 조치: 리허설 결과로 하나의 경로를 확정해 Script에 고정한다.
  - 경로 A(키 사용 Quorum): 옵션 문법·SDK 버전·PKCS#11 경로 동작을 확정하고, 승인 토큰이 없으면 서명이 **거부되는** 음성 시험 결과를 리허설 결과서에 첨부.
  - 경로 B(CU 비밀번호 분할): cu_root/cu_c2pa 비밀번호를 KC 2인이 반씩 설정·입력, key share 금지, 봉투 봉인 단계 추가.
  - 어느 경로든 5.5.1·5.5.3·5.6.1·5.6.5의 "담당"에 2인 이상과 각자의 행위를 명시.

### K5. Script가 승인·서명 가능한 확정본이 아님 — 문서 전반

> **코멘트:** Program은 "signed key generation script" 증거를 요구한다. 심사원은 서명된 Script가 실제 수행 내용과 일치하는지, 그리고 Script가 수행 전에 확정·승인됐는지를 본다. 현재 문서는 제목부터 "(Template)"이고, 확정되지 않은 분기와 값이 남아 있다. 이 상태로 서명하면 "무엇에 서명했는지"가 불명확해진다.

- 남은 미확정 요소: `[템플릿 전용 — 리허설 후 확정 문장으로 교체 또는 삭제]`, `[리허설 확인]` 2곳, 5.8 `[권장, 리허설 검증 후]`(선택 단계), `<Org>`, `<M>`/`<M_root>`/`<N>`, `-days <5479~7305>`, `v<x>`, OCSP/AIA URL, 3.3 해시 공란.
- 문서 손상: 표 행 사이 빈 줄로 Markdown 표가 깨짐, 코드 펜스가 `\`\`\``로 이스케이프됨, `&gt;`, `verify_[profile.py](http://profile.py)`·`curl -m 5 [https://example.com](...)` 같은 자동 링크 변환. 명령은 복사·실행 가능한 원문이어야 하므로 실행 단계 명령이 손상된 것은 그 자체로 결함이다.
- 조치: 리허설 후 모든 값을 채운 확정본을 만들고, 확정본의 SHA-256을 1장에 기록한 뒤 승인 서명. 행사 중에는 해당 해시의 인쇄본만 사용.

## Major

### M1. ICA CSR에 필수 요청 확장 없음 — 5.6.3

> **코멘트:** 공식 First CSR schema(`intermediateCA.csr.schema.json` `allOf/2`)는 BC(critical, cA, pathLen=1)·KU(critical, keyCertSign·cRLSign만)·Certificate Policies(C2PA OID)를 요청 확장으로 요구한다. 프로젝트 settings.md에도 같은 방침이 있다. 최종 인증서는 `-extfile`로 확장을 붙이므로 영향이 없지만, 심사원이 CSR도 공식 schema로 볼 경우 지적된다.

- 조치: 5.6.3에 `-addext "basicConstraints=critical,CA:TRUE,pathlen:1" -addext "keyUsage=critical,keyCertSign,cRLSign" -addext "certificatePolicies=1.3.6.1.4.1.62558.1.1"` 추가(또는 req 설정 섹션), 5.6.4에 요청 확장 확인 추가. AIA/CDP는 CSR에서 생략(settings.md 방침).

### M2. 유효기간이 승인된 결정과 다름 — 5.5.3, 5.6.5

> **코멘트:** CP는 Root·First 기간을 의무로 정하지 않는다(YAML은 "e.g., 20 years / 5 years typical"). 그러나 프로젝트는 2026-10-12 U02로 Root 20년·First 5년을 확정했는데, Script는 Root 9131일(25년), ICA 5479~7305일(15~20년)이다. 심사원 관점에서 이는 기간 자체보다 **승인된 설정과 Script가 다르다는 변경관리 문제**(CP *Change Management*)다. 또 ICA는 범위로 적혀 있어 확정값이 아니다.

- 조치: 결정을 바꾼 것이면 settings.md의 U02를 갱신하고 승인 근거를 남긴다. 아니면 Script를 7305일/1826일(또는 승인된 정확한 notBefore/notAfter)로 고친다. ICA 만료가 Root 만료를 넘지 않는지 함께 확인.

### M3. Quorum 구성 불일치·우회 여지 — 3.1, 3.2, 4.5, 5.4.9

> **코멘트:** Root 클러스터 예시는 3-of-5인데 Custodian·KMS 키는 3명/3개뿐이다. 3-of-3으로 가면 Custodian 1명 상실 시 Root 키를 영구히 쓸 수 없다(가용성). 또 `quorum` 서비스 Quorum 값을 "권장"으로만 두었는데, 이 값이 1로 남으면 admin 1명이 `user` 서비스 Quorum 값을 다시 낮출 수 있는지가 문제다. 다인 통제의 우회 경로가 될 수 있으므로 "권장"이 아니라 필수로 둬야 한다.

- 조치: Root/C2PA 각각 M·N과 명단 확정(M ≥ 2, N = 등록 Custodian 수). `quorum` 서비스(및 SDK가 지원하는 관리 서비스)의 Quorum 값을 필수로 설정하고, 리허설에서 단일 admin의 Quorum 값 변경이 거부되는지 음성 시험.

### M4. 오프라인화 전 백업 시점 미확인, off-site 사본 없음 — 5.8, 5.9, 6장

> **코멘트:** 5.8.1은 "최신 백업 READY"만 확인한다. 그 백업이 **Root·ICA 키 생성과 Quorum 설정 이후**에 만들어진 것인지 확인하지 않으면, HSM 삭제(5.8.2~5.8.3)로 CA 키를 잃을 수 있다. 또 CP *Key Backup and Recovery* 3은 "At least one copy of the CA private key SHALL be stored off-site"인데, Script는 원 리전 백업만 두고 6장에서 CopyBackupToRegion을 제한한다. off-site를 어떻게 충족하는지 설명이 없다.

- 조치:
  - 5.8.1 기대 출력: 백업 `CreateTimestamp` > 5.6.8 시각. 조건을 만족하지 않으면 HSM 삭제 금지(필요하면 대기). 리허설에서 이 백업으로 복원한 클러스터에 키·사용자·Quorum이 그대로 있는지 확인.
  - 백업 보존: 보존 정책/`NeverExpires` 설정을 Script 단계에 넣는다.
  - off-site: 다른 리전으로 `copy-backup-to-region`(동일한 승인 절차 하에)하거나, 같은 리전 백업이 off-site라는 판단 근거를 문서화.
  - 5.8의 `[권장]` 표기 제거. 수행 여부를 확정.
  - 연간 검토되는 백업·복구 계획(CP *Key Backup and Recovery* 1)은 Script 밖이지만 심사 시 함께 요구되므로 참조 문서 번호를 1장 또는 6장에 기재.

### M5. 독립 입회자의 독립성·자격 정의 없음 — 2장, 4.2, 7장

> **코멘트:** Program의 증거 요구는 "independently witnessed key generation ceremony"다. IW 역할은 잘 정의돼 있지만, 누가 독립적인지(소속·보고 라인·이해관계, 외부 감사인 여부) 기준이 없다. 심사원은 IW가 CA 운영 조직과 독립적인지를 묻는다. 또 클라우드 HSM 행사에서 IW가 실제로 무엇을 볼 수 있는지(CO 화면 미러링, CloudTrail 콘솔 등)가 정의돼 있지 않다.

- 조치: 2장에 IW 독립성 요건과 확인 방법, 관찰 수단을 명시. 7장에 IW 전용 입회 진술(독립성, 관찰 범위, Script 준수 여부·편차 확인)을 추가.

### M6. 신뢰 역할 자격 확인이 사전 조건에 없음 — 4장

> **코멘트:** CP *Clearances*(채용 시·5년마다 검증), *Training and Awareness*, *Generation by CAs* 3.2(신뢰 역할 인원)는 참여자가 신뢰 역할로 지정·검증·교육됐을 것을 전제한다. 4.2는 신분 확인만 한다.

- 조치: 4장에 "참여자 전원 신뢰 역할 지정서·배경 확인·교육 이수 기록 확인(CA-Admin/IW)" 항목 추가.

### M7. 활성화 데이터 처리가 실행 단계에 없음 — 5.2.1, 5.4.1, 5.4.2, 5.4.10, 6장

> **코멘트:** CP *Activation Data*는 HSM·CA 키 활성화 데이터의 보호를 요구한다. Script는 "KC1·KC2 분할 입력"만 적고, 각 분할본을 어디에 적어 어떤 봉투(일련번호)에 넣고 누가 보관하는지는 6장 요약에만 있다. hsm-owner 패스프레이즈, 초기 admin, kc1~kc3 admin, cu_* 비밀번호가 모두 대상이다.

- 조치: 각 비밀 생성 직후 "봉투 일련번호 기록·봉인·IW 확인" 단계를 넣고, 3장 자재 목록에 봉투·봉인 테이프·금고를 추가. 3장에는 CP Script 요건(4.3 "activation materials")에 맞춰 활성화 자재 목록도 둔다.

### M8. FIPS 판본 문구 차이 미해결, CMVP 번호 누락 — 3.1, 부록 A

> **코멘트:** 001 검토 C01과 같다. CP의 생성 조항은 FIPS 140-3 Level 2 이상을 허용하지만 *Key Storage* 1은 "FIPS 140-2 Level 2 or higher"만 적는다. hsm2m.medium(FIPS 140-3 Level 3)이 저장 조항을 충족한다는 C2PA 측 해석 근거가 아직 없다. 또 3.1은 CMVP 번호를 "부록 A"에 둔다고 하지만 부록 A에는 OpenSSL 설정만 있다.

- 조치: 3.1에 CMVP 인증서 번호·펌웨어 버전·FIPS 모드 근거를 직접 기재. C2PA 측 해석 확인은 행사와 별도로 신청 전까지 진행.

### M9. 단말·접속 경로와 MFA 정의 없음, 반입 금지와 충돌 — 4.2, 5.1, 5.4.5

> **코멘트:** CP *Computer Security Controls* 2는 CA 시스템 접근에 MFA를 요구한다. Script에는 CO가 쓰는 관리 단말(EC2인지 노트북인지)과 그 접속 방식(SSM, bastion 등)·MFA가 없다. 또 4.2는 무선기기 반입을 금지하는데 5.4.5는 KC가 "자기 단말, MFA"로 KMS에 서명한다. KC 단말과 MFA 장치(휴대폰 OTP 등)를 반입 예외로 둘지 정해야 한다.

- 조치: 3장에 단말 목록(용도·소유·네트워크 경로·인증 방식) 추가. 반입 예외 장비를 명시하고 4.2에서 IW가 목록과 대조.

## 관찰 사항 (결함 아님)

- **공용 Platform Root:** Root가 C2PA 전용이 아니라 플랫폼 공용이다. Trust List에 Root를 올리면 그 Root 아래의 모든 하위 CA가 C2PA CP 범위(*Key Pair and Certificate Usage*, *Certificate Issuance*, 키·로그 통제 등)로 들어온다. 등록 대상을 Root로 할지 First ICA로 할지 먼저 정하고, Root 아래 비C2PA 하위 CA 발급도 같은 통제를 따른다는 점을 CPS에 반영하는 것을 권고한다.
- **First 상태 서비스:** ICA는 OCSP AIA를 넣으므로 발급 시점에 OCSP 주소가 실제로 응답 가능해야 하는지(CP *Certificate Status Services*, *Lifecycle Security Controls* 3) 001 검토 C04가 여전히 열려 있다.
- **hsm-owner 키:** C2PA 체인 밖이지만 클러스터 신뢰 앵커이므로 CA 키에 준해 보호한다는 방침은 적절하다. 다만 5.2는 HSM 밖 소프트웨어 키라는 점을 감안해, 생성 단말과 `shred`의 실효성(SSD·EBS)을 고려한 폐기 방식을 정한다.

## 행사 전 필수 조치 (우선순위)

1. **K1·K2:** `ica.cnf`에서 CDP 삭제, `root.cnf` AKI를 `keyid:always`로. 5.5.4·verify_profile.py 기대값 갱신. 공식 schema로 테스트 인증서 PASS 확인.
2. **K3:** 5.7 FAIL 처리 문구를 "중단 → 키 파기 → 재생성(별도 승인)"으로 교체. 프로파일 검증을 리허설로 앞당김.
3. **K4·M3:** 리허설로 키 사용 다인 통제 경로를 하나로 확정하고 음성 시험(단독 사용 거부, 단독 Quorum 변경 거부) 결과를 첨부. CU 비밀번호 처리와 key share 여부를 그 결과에 맞춤.
4. **M4:** 백업 시점 검증과 off-site 방안을 확정하기 전에는 5.8(HSM 삭제)을 수행하지 않음.
5. **K5:** 모든 값과 분기를 확정한 Script 확정본을 만들고 해시를 기록한 뒤 승인 서명. 손상된 명령 복구.
6. M1·M2·M5~M9, Minor 반영.

10월 15일 일정 기준으로 1·2·5는 문서 수정으로 가능하다. 3·4는 리허설 결과가 필요하므로, 리허설 결과서(4.6)에 해당 시험이 들어 있지 않다면 일정 조정을 검토해야 한다.

## 재현 방법

```sh
# 부록 A 설정 그대로, 소프트웨어 P-384 키로
openssl req -new -x509 -key root.key -config root.cnf -extensions root_ca_ext -days 9131 -sha384 -out root.crt
openssl x509 -in root.crt -noout -ext authorityKeyIdentifier      # 출력 없음 → AKI 누락
openssl req -new -key ica.key -subj "/C=KR/O=TestOrg/CN=Samsung C2PA Intermediate CA G1" -sha384 -out ica.csr
openssl x509 -req -CA root.crt -CAkey root.key -in ica.csr -extfile ica.cnf -extensions first_ica_ext -days 7305 -sha384 -CAcreateserial -out ica.crt
# 이후 확장을 schema 입력 형식으로 변환해 c2paRootCaConstraints/allOf/4, c2paFirstIntermediateCaConstraints/allOf/5 검사
```
