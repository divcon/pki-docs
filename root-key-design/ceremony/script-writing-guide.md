# Root와 First ICA 세레모니 스크립트 작성 가이드

**샘플은 완성된 문서의 모양을 보는 용도이고, 템플릿은 실제 행사 스크립트를 작성하는 출발점입니다.** 작성 방법과 판단 기준은 이 가이드에서 확인합니다. 세 문서는 행사 정보 → 참여자 → 설정 → 실행 작업 → S00–S07 → 중단·재개 → 수행 기록 → 확인 서명 순서로 대응합니다.

| 문서 | 담는 내용 | 사용하는 방법 |
|---|---|---|
| [스크립트 샘플](ceremony-script-sample.md) | 가상 행사 한 건의 설정·참여자·진행·모의 결과가 채워진 예시 | 항목의 구체성과 기록 연결을 확인 |
| [스크립트 템플릿](ceremony-script-template.md) | 실제 행사에 필요한 필드, 기본 수행 절차, 빈 기록·서명란 | 행사별로 복사하고 실제 값·명령·담당자를 채움 |
| 이 가이드 | 샘플의 가정, 필드 작성법, 승인·기록·검토 기준 | 작성·검토 때 참조 |

준비할 일과 미결정 사항은 [준비 체크리스트](preparation-checklist.md)에서 관리합니다. 스크립트 문서와 실제 실행 코드는 버전·해시로 연결하며, 스크립트 작성 완료와 실행 도구 구현·검증 완료를 구분합니다.

## 샘플을 읽는 방법

샘플의 `DEMO-*` 인물·HSM·도구·승인·증거·서명은 모두 가상입니다. 모의 수행 표의 통과와 완료는 **작성 예시의 내용**이며, 실제 키 생성·제품 검증·모듈 적격성·외부 승인 결과가 아닙니다. 증거 파일과 도구가 이 저장소에 구현되어 있다는 뜻도 아닙니다.

샘플의 실행 작업은 가상 CA 도구에서 수행하는 동작과 입출력을 구체화한 것입니다. `CMD-*`는 작업 식별자이며 실행 가능한 셸 명령이 아닙니다. 실제 작성에서는 이 자리에 리허설한 명령이나 실행 절차 파일·버전·해시를 연결합니다. 샘플의 본문·공개키·파일 해시는 가상 증거 목록을 참조하며 임의의 해시 문자열을 실제 값처럼 제시하지 않습니다.

다음 값은 샘플을 완성하기 위한 선택입니다. 프로젝트의 확정 정책으로 복사하지 않습니다.

| 샘플 선택 | 실제 행사에서 정할 내용 |
|---|---|
| 본문은 A/B가 승인, HSM 토큰은 O/A/B가 각각 승인하는 3-of-3, O가 실행, 역할 겸임 없음 | 본문 승인과 HSM 정족수 각각의 N/M, 실행자 승인 포함, 겸임·대체자·독립성, 실제 HSM 권한 |
| Root 10년·First 5년, ECDSA SHA-384 | 승인 유효기간·해시·서명 입력 형식과 도구 호환성 |
| Example DN·주소, 고정 serial 예시 | 실제 조직·고유 이름·운영 주소·serial 생성과 중복 방지 |
| Root AKI 포함, First AKI는 Root SKI 참조 | 적용 프로파일과 원문/schema 차이 처리·외부 수용 근거 |
| 별도 장애 영역, 당일 백업 증거 미완료로 S06 보류 후 다음 날 확인·후속 서명 | off-site 판단, 실제 백업 구성·통제·복구 실증, 생성된 키 보호를 유지하는 보류·재개, 보존 기간과 접근 권한 |
| 임시 생성 접근을 공동 활성화하는 시나리오 | 생성 계정·호스트·코드·관리자 경로에서 단독 우회를 차단하는 실제 구현과 시험 |

기존 입력값인 P-384와 Root→First→하위 Issuing ICA 구조는 반영했지만, 샘플에 값을 적은 사실이 운영 승인이나 C2PA 수용을 대신하지는 않습니다.

샘플의 3-of-3은 실행자 O의 토큰 승인도 별도로 기록하는 가상 선택입니다. 프로젝트 정족수를 확정하거나 실제 경로의 단독 사용 방지를 검증한 결과가 아닙니다. 사용자·승인 키 등록, 실행자 자신의 토큰 승인, 관리자 변경과 복구를 포함해 실제 사람과 계정의 조합으로 시험해야 합니다.

인증서 필드는 [Root 원문 프로파일](https://github.com/c2pa-org/conformance-public/blob/2466172859fad1215f7aaf7e3768b41a0ac29abc/docs/v0.2/cert-profiles/rootCA.cert.yaml)과 [First 원문 프로파일](https://github.com/c2pa-org/conformance-public/blob/2466172859fad1215f7aaf7e3768b41a0ac29abc/docs/v0.2/cert-profiles/intermediateCa.cert.yaml)을 대조합니다. 원문·schema·검사 도구의 판정이 다르면 해당 필드, 각 기준의 버전·요구값, 실제 출력, 해석 근거, 외부 확인 담당자와 회신을 기록합니다. **내부 해석 승인이나 검사 오류의 제외 처리는 C2PA 수용이 아닙니다.** 외부 확인이 필요한 차이가 남아 있으면 그 차이에 의존하는 발급을 보류하고, 검사 보고서에는 제외한 실패와 미확인 상태를 그대로 남깁니다. 등록 대상의 프로파일 검증 증거 요구는 [Program][program]을 따릅니다.

## 템플릿을 사용하는 순서

1. 템플릿을 행사별 파일로 복사하고 행사 ID·버전을 부여합니다. 공용 템플릿 원본에는 실제 운영 기록을 쓰지 않습니다.
2. 행사 전 확정 필드를 채우고, 역할·정족수에 맞춰 참여자 표와 단계의 승인자를 함께 조정합니다.
3. 키·인증서 설정을 승인 원본에서 가져오고 실제 명령·도구·검사 방법을 연결합니다.
4. 테스트 키로 성공·실패·중단·재개·인계까지 리허설합니다. 변경 사항을 반영한 뒤 승인본과 해시를 고정합니다.
5. 행사별 수행 사본에서 실제 시각·키 식별·승인·검사·일탈을 기록합니다. 승인 원본을 덮어쓰지 않습니다.
6. 참여자·입회자가 수행 기록과 고정된 증거 목록을 확인 서명하고, 인수·접근 종료와 최종 판정을 기록합니다.

템플릿의 `{{항목명}}`은 행사 전에 확정하는 값입니다. `{{현장_항목명}}`은 행사 중 또는 종료 시점에 확인할 값이므로 미리 성공으로 채우지 않습니다. 같은 필드가 여러 번 나오면 같은 값을 사용합니다. 적용되지 않는 필드는 단순 삭제하지 말고 적용 제외 근거를 남깁니다.

## 항목별 작성 기준

| 템플릿 항목 | 작성할 내용 | 검토할 사항 |
|---|---|---|
| 행사 정보 | 목적·범위·환경·일시, 정책·프로파일 원문 식별, 승인본 목록과 행사 승인 | 미등록 Root와 등록 대상 First의 적용 범위, 운영/테스트 구분 |
| 참여자 | 실제 사람·개인 계정·책임·겸임·대체자·독립성·정족수 | 한 사람이 다른 계정으로 인원을 채우지 않는지, 입회자와 승인자 구분 |
| 승인 설정 | 알고리즘·키 속성·권한, DN·기간·serial 규칙·모든 확장과 critical 여부 | 기존 승인 원본과 일치하는지, 생략할 필드도 명시했는지 |
| 환경과 보호 | HSM 실제 모델·모드·인증 범위, 호스트·도구·접근·생성 통제·백업·로그 | 제품명이나 승인 티켓만으로 통제 완료라고 판단하지 않는지 |
| 실행 작업 | 실제 명령/절차, 실행 위치·입출력·도구 버전·해시·종료 상태와 실패 처리 | 승인한 입력을 서명하는지, 결과 불명·저장 실패 시 자동 재실행하지 않는지 |
| S00–S07 | 담당자별 행동·승인·검사, 명시적 서명 실행, 통과·중단 기준, 증거 ID | 키·CSR·인증서 서명 주체와 순서, 단계별 입회·기록 |
| 중단과 재개 | 누가 중단·조사·보호·재검사·재개·폐기/재생성을 결정하는지 | 생성 키 조회와 보존된 서명 응답 복구를 구분하고, 응답 없는 결과 불명을 보류하는지 |
| 수행 기록 | 실제 시각·명령·입력·키·승인·결과·검사·증거·일탈 | 수행하지 않은 검사나 미확인 사실을 통과로 기록하지 않는지 |
| 확인 서명 | 서명 대상 스크립트·수행 기록·증거 목록·일탈, 개인별 범위·판단·제한 | 행사 승인과 실제 수행 확인을 구분했는지 |
| 최종 판정 | 세레모니 완료, 운영 준비, 외부 제출/등록 상태 각각 | 행사 완료를 운영 개시나 등록 승인으로 확대하지 않는지 |

`serial`의 생성 규칙은 행사 전에 고정하고 실제 값은 최종 본문 승인 전에 확인합니다. 생성된 공개키·CSR·인증서 해시는 행사 중 얻는 결과입니다. 템플릿의 현장 상세 기록에 각 값과 승인 참조를 남깁니다.

공개키 지문은 SPKI DER의 SHA-256처럼 대상을 명확히 정합니다. CSR·인증서·본문의 해시는 파일 형식과 바이트를 식별해야 합니다. 인증서 SKI와 별도의 증거용 공개키 지문은 구분합니다.

## 사람과 통제를 실행 가능한 수준으로 적습니다

참여자 표에는 신뢰 역할 임명 승인과 자격 유효성 확인을 연결합니다. 인사·보안 책임자가 적용 정책, 적격성 확인 완료·유효 여부, 교육 이수·갱신 상태, 확인자·확인일을 기록하고 S00에서 확인합니다. 신원조사 원본과 민감한 개인정보는 행사 자료에 넣지 않습니다. CP는 신뢰/비신뢰 역할의 적격성 확인 정책, 신뢰 역할 상근 직원의 채용 시 및 5년마다 확인, 정기 교육과 중요 변경 시 재교육을 요구합니다. 행사 참석자로 지정한 사실만으로 이 조건을 충족했다고 판단하지 않습니다. [CP Personnel Controls][cp-personnel]

다인 통제 표는 다음처럼 **행위별로** 작성합니다. 기존 운영 문서에 내용이 있으면 승인본의 정확한 절·버전·해시를 참조하고 당일 확인 단계를 연결합니다.

| 작성할 항목 | 적어야 할 내용 |
|---|---|
| 통제할 행위 | 키 생성, 서명, 공유·quorum 변경, 사용자·승인 키 교체, 백업 복구를 각각 구분 |
| 필요한 사람과 계정 | 실행·승인·관리 권한을 가진 실제 사람, IAM/HSM/호스트 계정, 겸임과 대체자 |
| 각자 보호할 재료 | 개인 승인 키·접근 자격증명·복구 재료의 관리자와 보호 위치 참조. 비밀 값은 제외 |
| 다인 통제와 지식 분리 | 한 사람이 확보할 수 있는 권한·재료의 범위, 그 조합으로 단독 수행이 불가능한 이유, 채택한 지식 분리 방식의 검토 근거 |
| 우회 경로와 시험 | 관리자·호스트·배포·사용자 교체·복구 경로별 시도, 기대 거부, 실제 결과와 증거 |
| 현장 확인 | 조회 명령·기대값·담당자·실행 단계, 불일치 시 중단 조건 |

CP는 CA 생성·발급의 다인 통제와 지식 분리, CA 키에 대한 한 사람의 단독 물리·논리 접근 방지를 요구합니다. 승인 서명 두 개만으로 이행을 설명하지 말고 실제 권한·재료·우회 시험으로 연결합니다. 특정 비밀 분할 방식이나 샘플의 인원 수 자체를 CP 의무로 적지는 않습니다. [CP 생성][cp-generation] · [CP 발급][cp-issuance] · [CA 키 보호][cp-protection]

## 단계와 서명 키를 확인합니다

| 단계 | 작업 | 생성 또는 사용할 키 | 다음 단계로 넘길 증거 |
|---|---|---|---|
| S00 | 시작 확인 | 해당 없음 | 참석·환경·입회·시작 승인 |
| S01 | Root 키 생성 | 신규 Root | 키 식별·공개키·속성·생성 증거 |
| S02 | Root 자기서명 | Root로 Root 인증서 서명 | 최종 본문·승인·Root 인증서·자기서명 검사 |
| S03 | First 키 생성 | 신규 First | 키 식별·공개키·속성·생성 증거 |
| S04 | First CSR 생성 | First로 CSR 서명 | CSR·요청 권한·공개키 및 서명 검사 |
| S05 | First 인증서 발급 | Root로 First 인증서 서명 | 최종 본문·승인·First 인증서·체인 검사 |
| S06 | 전체 검사·확인 서명 | 신규 생성·서명 없음 | 최종 대조·백업·일탈·참여자/입회자 서명 |
| S07 | 인계·접근 종료 | 신규 생성·서명 없음 | 인수·세션/권한 종료·최종 판정 |

Root가 신뢰 저장소에 들어 있다는 이유만으로 자기서명이 검사된 것은 아닙니다. S02에는 자기서명 자체를 검사하는 명령·판정 기준을 둡니다. S05에는 승인 본문·Root 서명·First 공개키·CSR 연결을 함께 확인합니다.

CloudHSM CLI quorum을 사용한다면 세 번의 서명 작업을 각각 처리합니다. 토큰은 한 작업과 현재 로그인 세션에 한정되고 다른 애플리케이션에서 사용할 수 없습니다. 사용 토큰 승인이 본문 바이트까지 고정한다고 가정하지 말고 실제 입력을 대조합니다. 생성 명령의 통제는 별도로 구현·검증합니다. [AWS 토큰 제약][aws-use] · [AWS 지원 작업][aws-services]

[CloudHSM 공통 절차](cloudhsm-options.md)의 `B00`, `G01–G05`, `Q01–Q08`, `B01`, `X01`도 행사 승인본에 포함합니다. 이 ID는 프로젝트의 절차 식별자이며 AWS CLI 명령 이름이 아닙니다. 행사 스크립트의 각 호출에서 **절차 ID·파일 버전/해시, 담당자, 대상 키, 입력, 명령 참조, 기대 결과, 현장 증거 위치**를 지정합니다. Root와 First 생성은 각각 `G01–G05`, Root 자기서명·First CSR·First 인증서 서명은 각각 별도의 `Q01–Q08` 기록을 남깁니다. 공통 절차를 한 번 확인했다고 다른 키나 서명의 승인까지 완료한 것으로 처리하지 않습니다.

실제 명령 참조에는 실행 호스트·CLI 버전·세션 유지 방식·옵션·입출력·성공/실패 판정을 고정합니다. 복사한 설명이나 `CMD-*` 이름만 있는 상태로는 실행 준비 완료로 표시하지 않습니다. 절차·코드·설정을 바꾸면 해당 경로를 다시 시험하고 승인본을 갱신합니다.

## 기록과 서명을 묶는 방법

증거 목록에는 행사·단계·대상 키/인증서, 파일 위치·형식·해시, 수집 시각·담당자·접근 등급·보존 정책을 연결합니다. 상세 로그를 스크립트에 모두 붙이는 대신 증거 ID로 찾을 수 있게 합니다. 해시 목록 자체도 서명 또는 변경 통제로 보호합니다.

참여자는 수행한 범위, 입회자는 실제 관찰한 범위를 확인합니다. 확인할 수 없었던 부분은 제한으로 기록하고, 당시 없었던 통제나 입회를 사후 서명으로 대체하지 않습니다. 서명 형식·본인 확인·외부 제출 수용 조건은 행사 전에 정합니다.

S06에서 서명한 목록과 기록은 그대로 보존합니다. S07에서 인수·접근 종료 증거를 추가하면 새 최종 목록을 만들고 기존 목록을 연결합니다. 추가 기록은 해당 담당자가 별도로 확인 서명합니다. 백업 대기 때는 S00-R로 남은 검사만 재개하고, 첫날 생성·입회 서명과 임시 종료의 별도 목록·서명을 후속 목록에 모두 연결합니다. 재개 작업 참여자는 자신의 추가 범위에 서명하며, 불참한 입회자의 서명 범위를 넓히지 않습니다. 마지막 확인 서명·종료·최종 판정까지 보호 보관·복제·조회한 증거를 남깁니다. 이 마감 기록 자체를 보관하는 방법도 정하며 목록에 자기 해시를 넣는 순환 구조를 만들지 않습니다.

비밀번호·개인키·승인용 비밀·복구 비밀·HSM 백업 원본은 증거 묶음에 넣지 않습니다. 보호 저장소의 관리 기록을 참조합니다. 외부 제출본과 내부 원본, 가림 처리 내역을 구분하고 [제출 목록](preparation-checklist.md#무엇을-누구에게-제출하나요)에 맞춰 취합합니다.

### 기록 종류별 보존과 복구

보존기간 하나를 모든 자료에 적용하지 말고 다음을 구분합니다. 각 행에는 저장 위치, 읽기·변경·삭제 권한, 보존 기산점과 종료일, 백업 참조, 조회·복구 담당자도 적습니다.

| 기록 종류 | 작성·검토 기준 |
|---|---|
| 발급 인증서 원장 | serial·subject·기간·확장과 값·폐지 상태를 보관하며 **해당 인증서 만료 후 최소 1년**이라는 CP 하한을 반영 |
| 승인 스크립트·실제 수행·서명·일탈·증거 목록 | 행사 식별·버전과 연결하고 승인된 기록 정책의 기간·기산점 적용 |
| 감사로그·영상·화면 기록 | 원천·수집 범위·민감정보 처리·보존기간을 구분하고 삭제 전에 적용 의무 확인 |
| 실행 코드·설정·검증 도구 | 실제 수행본을 재구성할 버전·해시와 복구 위치 연결 |

CP가 명시한 만료 후 1년 하한은 발급 인증서 기록에 적용되며, 모든 로그·영상의 기간을 같은 값으로 정했다는 뜻은 아닙니다. 다른 기록의 종류·기간·안전한 저장·조회 방법도 정책으로 정해야 합니다. [CP Repositories][cp-repository] · [Records Archival][cp-archival]

백업 계획에는 CA 키뿐 아니라 인증서 원장, 설정, 감사로그 등 중요 자료를 포함합니다. S06/S07에는 이번 행사에서 실제 생성된 자료의 백업 식별·수집 완료 시각·무결성·조회 확인과 복구 시험 참조, 인수자를 남깁니다. 백업이 주기적으로 만들어진다는 설정만 확인하고 최종 발급·서명 기록이 포함됐다고 표시하지 않습니다. 중요 자료 백업과 운영 복구 계획은 CP 의무이고, 각 증거 파일의 묶음과 확인 표는 이를 이행하기 위한 프로젝트 양식입니다. [CP Backup and Recovery][cp-backup] · [키 백업 통제][cp-protection]

### 행사 기록과 감사로그 대조

행사 기록의 성공 판정 외에도 접근 성공·실패, 권한·공유·quorum 변경, 승인자 등록·교체, 코드·설정 변경을 확인할 로그를 정합니다. 다음 표를 채우고 S00에서 수집 준비, S06/S07에서 실제 수집 범위와 검토 결과를 확인합니다.

| 행위·단계 | 로그 원천·조회 방법 | 사람과 시스템 계정 연결 | 시각 기준·수집 범위 | 완료·무결성·검토 |
|---|---|---|---|---|
| 생성·서명·접근·권한 변경 등 각 행위 | HSM·클라우드·호스트·실행 도구 등 실제 제공 원천과 제한 | 요청자·실행자 개인 계정, 시스템 계정, 작업 ID 대응 | 시간대·허용 오차, 시작/종료, 수집 지연과 누락 판정 | 수집 완료 증거, 보호·보존 참조, 검토자·시각·이상 여부 |

특정 로그 한 종류가 모든 행위나 승인 본문을 기록한다고 가정하지 않습니다. 실행 도구의 작업 ID와 HSM·클라우드 로그를 실제로 대조해 사람·시각·키·작업이 연결되는지 확인하고, 필요한 원천이 빠지면 종료 판정을 보류합니다. CP는 관련 시스템·사용자 활동과 접근 시도, 요청자·시스템·인원 식별, 시각·행위·관련 파라미터, 변경·삭제 보호와 정기 검토를 요구합니다. 위 대응표와 행사 종료 시 대조는 이를 확인하기 위한 프로젝트 절차입니다. [CP Audit Logging][cp-logging]

## 승인 전에 검토할 사항

- [ ] 행사 전 확정 필드에 미정 값·가상 이름·DEMO 참조가 남아 있지 않습니다. 현장 기록란은 빈 상태입니다.
- [ ] 모든 실행 작업에 실제 명령 또는 실행 절차가 있으며 선택한 환경에서 리허설했습니다.
- [ ] 공통 절차의 ID·버전·해시와 각 생성·서명 작업의 입력·승인·증거 기록을 연결했습니다.
- [ ] 행위별 사람·계정·보호 재료와 지식 분리 근거를 정하고 생성·키 사용·관리자·복구 우회, 승인 후 입력 변경·중복 실행·저장 실패를 시험했습니다.
- [ ] 참여자·정족수·독립 입회·서명 형식, 시작·중단·재개·완료 권한과 신뢰 역할의 적격성·교육 유효 상태를 확인했습니다.
- [ ] 키·CSR·인증서·승인·증거 연결과 단계별 통과 기준을 확인했습니다.
- [ ] 키 생성 직후 보호, 키와 중요 자료의 백업·복구, 기록 종류별 보존 하한·기산점·인수·접근 종료 준비가 끝났습니다.
- [ ] 감사로그 원천·사람과 계정의 대응·시각 범위·수집 완료 판정·검토 담당자를 정하고 실제 수집을 시험했습니다.
- [ ] 미해결 프로파일·schema·검사 도구의 차이, 적용 범위·외부 수용 문제를 기록하고 발급에 필요한 확인을 완료했습니다.

이 가이드의 보강은 작성 기준을 구체화한 것입니다. 실제 명령 구현·CloudHSM 리허설·입회 방식의 수용·C2PA 심사 통과는 각각 증거를 확보한 뒤 별도로 완료 표시합니다.

## 원문 요구와 프로젝트 양식

이 세 파일의 역할 기호·단계 ID·표 구성·샘플 값은 프로젝트 양식입니다. CP가 지정한 고정 인원 구성이나 공식 신청 양식이 아닙니다.

CP는 생성 스크립트에 역할·책임, 행사 승인, HSM과 활성화 재료, 구체 단계, 참여자·입회자의 확인 서명, 일탈 기록을 요구합니다. 비클라우드 HSM의 장소·행사 후 물리 보관 항목은 조건부이지만 클라우드의 자격증명·활성화 재료 보호를 생략하는 근거는 아닙니다. Root 인증서 서명에는 신뢰 역할 담당 최소 두 명과 한 명의 명시적 실행을 반영합니다. [CP 생성][cp-generation] · [CP 발급][cp-issuance] · [키 보호와 활성화 재료][cp-protection]
