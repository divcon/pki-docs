# Root·First 키 생성

Root와 공용 First ICA의 키를 Global CloudHSM 안에 각각 생성한다. 결과물은 **키 쌍과 키 생성 기록**이다. 이 문서는 [전체 ceremony](README.md)의 키 생성 부분이며, 인증서는 [인증서 발급 절차](certificate-issuance.md)에서 만든다.

현재는 수행 스크립트 초안이다. 키 생성 통제·운영 파라미터·담당자·도구 검증이 남아 있다. 확정 범위는 [요구사항](../requirements.md), 통제 구현은 [다인 통제](../dual-control-options.md), 앱 기능은 [CA 앱](../ca-software-requirements.md)을 따른다.

## 진행 절차

### 1. 생성 계획을 승인한다

1. 운영 담당자는 Root·First 키의 생성 옵션을 작성한다.

   <a id="key-generation-options"></a>

   **C2PA 기준과 선택값**

   [Root 프로파일][root-profile]·[First 프로파일][first-profile]과 [CP 키 생성][generation]·[키 보호][keys]를 기준으로 작성한다. First에는 해당 C2PA 요구를 적용하고 Root에는 공통 키 보호 기준으로 채택한다. 미등록 플랫폼 Root의 CP 전체 적용 범위를 확정한 것은 아니다.

   `확정`은 기존 결정, `제안`은 승인 전 후보, `미정`은 실행 전에 채울 값이다. Root와 First는 각각 별개의 키다. 두 키 모두 EC를 사용하며 곡선은 미정이다.

   | 설정 항목 | C2PA 요구 또는 허용 범위 | Root 선택값 | First 선택값 |
   |---|---|---|---|
   | 키 알고리즘 | RSA 또는 EC. CA 프로파일 기준이며 leaf 알고리즘 목록과 구분 | EC | EC |
   | EC 곡선 | P-384 또는 P-521 | p-384 | p-384 |
   | 생성·보관·사용 위치 | 적격 암호 모듈 내부 생성·사용. 개인키는 모듈 밖에 평문으로 존재할 수 없음 | Global CloudHSM | Global CloudHSM |
   | 개인키 접근 통제 | 한 사람의 단독 접근을 막는 다인 통제 | 같은 담당자 그룹. 인원·권한 구현 미정 | Root와 같은 담당자 그룹. 인원·권한 구현 미정 |

   CloudHSM의 구체적인 설정은 수행 절차 확정 후 [CloudHSM 키 생성 추가 옵션](cloudhsm-options.md)에서 검토한다.

   생성 환경·통제·입회·백업 조건은 아래 [생성 전 확인](#생성-전-확인)에서 확인한다.

2. 운영 담당자는 [인증서 발급 설정](certificate-issuance.md#certificate-settings)을 작성한다.
3. 운영 담당자는 이 문서와 [인증서 발급 문서](certificate-issuance.md)의 담당자·명령·입력값·기대 결과·중단 조건을 채운다.
4. 승인자는 적용 정책, 역할 분담, 생성·서명 통제와 증거 수집 방법을 확인한다.
5. 승인자는 생성 계획과 행사 수행을 승인한다.

- 준비할 것: 위 키 생성 옵션 표, [인증서 설정표](certificate-issuance.md#certificate-settings), 참여자 역할표, 스크립트.
- 남길 것: 승인된 문서 버전과 행사 수행 승인.

### 2. 테스트 키로 전 과정을 연습한다

1. 실행자는 운영과 구분된 테스트 환경을 준비한다.
2. 실행자는 테스트 키로 이 문서의 키 생성 절차와 [인증서 발급 절차](certificate-issuance.md)를 연습한다.
3. 실행자는 승인 부족, 본문 변조, 직접 HSM 접근, 관리자 우회, 연결 단절과 저장 실패를 시험한다.
4. 담당자는 시험에서 발견한 문제를 해결한다.
5. 담당자는 운영 환경의 도구·설정을 고정한다.

- 준비할 것: HSM 연결, 발급 도구, 권한 설정, 로그·증거 저장소.
- 남길 것: 환경·모듈 확인 자료, [통제 시험](../dual-control-options.md#검증-기준)과 [앱 기능 시험](../ca-software-requirements.md#기능-검증)의 결과.

### 3. 당일 참여자를 확인한다

1. 시작 판정 담당자는 실행자·승인자·독립 입회자의 참석을 확인한다.
2. 시작 판정 담당자는 참여자의 역할·권한과 입회자 독립성을 확인한다.

- 준비할 것: 개인별 계정, 참여자 역할표, 입회자 독립성 확인 자료.
- 남길 것: 참석·역할·권한 확인 결과.

### 4. 실행 환경을 확인한다

1. 실행자는 승인된 스크립트·설정과 실제 환경을 대조한다.
2. 시작 판정 담당자는 필수 통제와 기록 준비 상태를 확인한다. 빠진 항목이 있으면 중단한다.

- 준비할 것: 승인된 스크립트·설정, HSM·실행 환경, 로그·증거 저장소.
- 남길 것: 환경·통제·기록 준비 점검 결과.

### 5. 행사를 시작한다

1. 독립 입회자는 입회를 시작한다.
2. 기록 담당자는 로그 수집을 시작한다.
3. 시작 판정 담당자는 키 생성 시작을 승인한다.

- 준비할 것: 참여자·환경 점검 결과, 입회·기록 수단.
- 남길 것: 시작 승인, 입회·로그 기록.

### 6. Root 키를 생성한다

**선행 조건:** 키 생성의 다인 통제 방법을 확정하고 검증해야 한다. 현재 구현 방법은 미정이며, [생성 전 확인](#생성-전-확인)을 마치기 전에는 운영 키 생성을 시작하지 않는다.

1. 실행자는 CloudHSM에 Root 키 생성을 요청한다.
2. HSM은 Root 키를 생성한다.

- 필요한 기능: 키 생성·식별.
- 남길 것: Root 생성 로그, 공개키 지문·HSM 키 식별자·속성.

### 7. First 키를 생성한다

**선행 조건:** Root 생성과 마찬가지로 키 생성의 다인 통제 방법을 확정하고 검증해야 한다.

1. 실행자는 CloudHSM에 Root와 별개의 First 키 생성을 요청한다.
2. HSM은 First 키를 생성한다.

- 필요한 기능: 키 생성·식별.
- 남길 것: First 생성 로그, 공개키 지문·HSM 키 식별자·속성.

### 8. 생성 결과를 확인한다

1. 검증 담당자는 두 키의 실제 설정을 승인한 생성 옵션과 대조한다.
2. 검증 담당자는 Root와 First가 별개의 키인지 확인한다.
3. 검증 담당자는 생성 로그와 공개키 지문이 일치하는지 확인한다.
4. 참여자·입회자는 실제 생성 결과와 절차 이탈을 기록한다.
5. 운영 담당자는 생성 직후부터 키·기록·백업의 보호 책임을 맡는다.

- 필요한 기능: 키·설정 대조, 생성 증거 취합, 일탈 기록, 보관 책임 확인.
- 남길 것: Root·First별 키 식별자·공개키·지문·속성·검사 결과, 생성·입회 로그, 보호 책임 기록.

필수 통제·검사·증거가 충족되면 [인증서 발급](certificate-issuance.md)으로 넘긴다. 생성 당시 증거는 그 시점에 남긴다. 참여자·입회자의 최종 확인 서명은 인증서 발급 문서의 [전체 수행 결과 확인](certificate-issuance.md#sign-off)에서 취합한다.

## 생성 전 확인

CP §6.1.1은 안전한 생성 환경, 신뢰 역할 담당자의 다인 통제·지식 분리, 적격 암호 모듈, 입회 및/또는 기록, 생성 로그와 상세 스크립트를 요구한다. 등록 대상 First에는 Program의 **독립 입회한 키 생성과 서명된 스크립트** 증거도 준비한다. 녹화만으로 등록 증거를 대신하지 않는다. WebTrust 보고서 대체는 해당 보고서가 ceremony·스크립트의 적합성을 입증하는 조건에서만 검토한다. [CP 키 생성][generation] · [Program][program]

| 준비 항목 | 실행 전에 고정·확인할 내용 |
|---|---|
| 적용 기준 | CP·Program·프로파일 버전, Root/First별 적용 조항, 등록할 신뢰 목록. 미등록 상위 Root의 적용 범위는 별도 확인 |
| HSM·실행 환경 | 모델·모드·인증 범위, 클러스터, 호스트·네트워크, 도구 버전, 테스트/운영 구분, 로그·시간 설정 |
| 키 생성·사용 통제 | 개인별 계정, 생성용 자격증명과 호스트 접근 통제, 키별 소유·공유 권한, N-of-M, 관리자 우회 차단, 개인별 승인 키 보호 |
| 행사 운영 | 실행·승인·기록·검증 역할, 독립 입회자, 시작·중단·재개·완료 판정자, 스크립트와 활성화 재료 목록 |
| 생성 직후 보호 | 키·활성화 재료의 접근 통제, 증거 저장·변경 권한·보존 기간, 백업 식별·보관·인수 책임 |

생성 모듈의 CP 기준은 FIPS 140-2 Level 2 이상, FIPS 140-3 Level 2 이상 또는 적절한 CC PP/ST EAL 4 이상이다. 보관·사용 조항의 기준은 별도로 대조한다. CloudHSM 제품명만으로 적격성을 판단하지 않는다. [CP 키 보호][keys]

**키 생성 명령 자체의 CloudHSM quorum은 지원 목록에 없다.** 생성 때 지정하는 quorum은 이후 키 사용·관리의 통제다. 생성용 계정·실행 환경의 통제안과 우회 시험을 먼저 완료해야 한다. [AWS 지원 작업][aws-services]

백업·복구는 원본과 같은 다인 통제, 백업 식별·보호, off-site 사본과 평문 반출 금지를 적용하고 공식 계획을 매년 검토한다. 실제 구성·담당·복구 검증은 [운영 모델](../operating-model.md#backup)에서 정한다. [CP 키 보호][keys]

## 증거 보관과 중단 처리

공통 작업 ID에 승인된 키 생성·인증서 발급 문서의 버전, 생성 설정·도구 버전, 참여 역할, 단계별 수행자·시각·결과, HSM·키 식별자, 공개키 지문, 입회·로그 참조와 일탈 처리를 연결한다. 비밀번호·개인키·승인용 비밀은 기록하지 않는다. 보존·변경 권한은 [기록 정책](../operating-model.md#records)을 따른다.

| 상황 | 처리 |
|---|---|
| 생성 권한·통제·입회·기록 준비 부족 | 생성 시작 보류, 원인 기록 |
| 승인 후 키 설정·환경 변경 | 기존 승인 무효화, 재검토 |
| 생성 결과 불명, HSM 성공 후 저장 실패 | 기존 키·로그·원장 대조 전 자동 재생성 금지 |
| 키 생성 후 중단 | 생성한 키의 사용을 제한하고 재사용·폐기 판단을 기록 |
| 생성 당시 통제·입회를 입증할 수 없음 | 당시 자료와 인정 가능한 대체 증거 확인. 해소할 수 없으면 재생성·ceremony 재수행 필요성 판단 |
| 보고서·색인만 미완성 | 원래 증거로 보완. 문서 누락만으로 자동 재생성하지 않음 |

생성 당시 없었던 통제·입회 사실을 사후 문서로 만들 수는 없다. 재생성 가능성은 이 제약에서 도출한 위험 판단이며, 모든 서류 누락에 대한 자동 재생성 규정은 아니다. 개인키 노출·부적격 환경은 [사고·복구 절차](../operating-model.md#backup)를 따른다.

## 남은 결정

| 항목 | 정할 내용 |
|---|---|
| 키·생성 환경 | EC 곡선, 같은 클러스터 사용 여부, 실제 모듈 적격성, 실행 호스트·도구 |
| 다인 통제 | 생성용 계정·환경·관리자 우회 차단, 키 사용·관리 N/M, 실행자 승인 포함 여부, 개인별 승인 키 보호 |
| 행사·증거 | 담당자·입회 방식·일정, 명령·입력값, 증거 보존, 시작·중단·재개·재생성 판단 책임 |
| 보관·백업 | 생성 직후 보호·백업 책임과 실제 구성·복구 검증 |

CloudHSM 옵션의 구체적인 값은 수행 절차 확정 후 [구현 옵션](cloudhsm-options.md)에서 검토한다. 스크립트 필수 항목의 조항별 대조는 [Conformance 분석](../conformance-analysis/03-ceremony-script-requirements.md)에 있다.
