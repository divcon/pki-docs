# Root와 First ICA 세레모니 — 실행 절차 샘플

조건부 가상 절차이며 실행 가능한 명령 파일은 없습니다. [설정](settings.md)을 입력으로 사용하고, 수행 결과는 [회차별 기록](records/session-01.md)과 [증거 목록](evidence-index.md)에 연결합니다.

## 명령을 작성할 때

각 작업의 실행 위치·개인 계정·입출력·도구 버전/해시·기대값·중단 조건·증거를 고정합니다. 실제 작성에서는 아래 가상 정의를 검증된 명령 파일로 대체합니다.

## 실행 작업

이 사례의 실행 정의는 `approved/runbook.md` v1.0 / H(approved/runbook.md)입니다. **아래는 가상 도구의 절차 정의이며 실행 가능한 셸 명령이 아닙니다.** 실제 행사에서는 검증된 명령 파일과 CLI 정확한 버전·해시로 대체합니다.

모의 도구는 `DEMO-CA-RUNNER 1.0`(실행), `DEMO-VERIFY 1.0`(독립 검사), `DEMO-CLI-BUILD-01`(CloudHSM CLI 빌드의 가상 식별자)입니다. 각각 `approved/tool-lock.json`에 실행 파일 H·버전·위치를 기록하는 설정입니다. O는 DEMO-HOST-O에서 CLI 로그인 세션을 서명 완료까지 유지하고, V는 DEMO-HOST-V에서 독립 검사합니다. A/B/O의 승인 서명은 각 개인 단말에서 생성합니다. 비밀은 명령 기록에 넣지 않습니다.

모든 행은 위 runbook·tool-lock의 승인 버전/해시에 묶입니다. 모의 성공 판정도 출력 존재만으로 끝내지 않고 독립 검사·원장·증거 저장을 요구합니다. 승인 후 입력·키·코드·설정 변경, 결과 불명, 저장 실패는 중단하며 자동 재시도하지 않습니다.

## 공통 서명 절차 Q01부터 Q08

승인된 [CloudHSM 실행 부록](../cloudhsm-options.md)의 Q01–Q08과 아래 작업별 입력을 사용합니다. 부록·명령 파일의 승인 버전과 해시: `approved/cloudhsm-options.md` 모의 사본 1.0 및 `approved/runbook.md` 1.0 / 각 H, DEMO-PACK-01 v2.0.

| 단계 | 서명 키 | 고정할 서명 대상 | 실행 작업 |
|---|---|---|---|
| S02 | Root | TBSCertificate DER, E02/root-tbs.der | CMD-02 → Q01–Q08 / CMD-03·04 |
| S04 | First | CertificationRequestInfo DER, E04/first-cri.der | CMD-06a → Q01–Q08 / CMD-06b·07 |
| S05 | Root | TBSCertificate DER, E05/first-tbs.der | CMD-08 → Q01–Q08 / CMD-09·10 |

1. **Q01 — O/V/A/B:** 작업 ID·발급 serial 예약과 중복 검사를 원장에 남깁니다. 정확한 DER·내용표·증거용 SHA-256·서명용 알고리즘·raw/digest 선택·키 지문·프로파일·기한을 고정하고 A/B가 본문 승인을 기록합니다. CSR에는 serial 대신 CSR 작업 ID를 사용합니다.
2. **Q02 — O/V:** 대상 계정·클러스터·키 소유/공유·사용 quorum·승인키 등록을 확인합니다. O가 현재 CLI 로그인 세션을 유지하며 기록용 세션 식별자를 작업과 연결합니다.
3. **Q03 — O:** 해당 키의 key-usage 토큰을 생성합니다. service·key-reference·토큰 식별 해시·생성/만료시각·세션·작업 ID를 기록하고 승인된 전달 경로로 보냅니다.
4. **Q04 — O/A/B 각 승인자:** 받은 토큰과 본문 승인 묶음의 작업·키·기한을 대조한 뒤 본인에게 등록된 별도 승인키로 토큰에 서명합니다. O가 승인 서명을 취합합니다. 실제 서명 입력 변환은 고정 명령 파일을 따릅니다.
5. **Q05 — V:** 승인자 개인 계정·등록 공개키·허용 집합·필요 수와 만료/세션 유효성을 검사합니다. 같은 사람의 복수 계정이나 허용하지 않은 자기승인으로 수를 채우지 않습니다. 조건 미달은 실행을 거부합니다.
6. **Q06 — O/V:** 현재 DER·digest·서명 키가 승인값과 같은지 재대조합니다. O의 명시적 실행 지시와 `요청 시작`을 내구 저장한 뒤 승인 토큰을 `--approval`로 전달해 해당 ECDSA 작업을 실행합니다. 원본 응답의 보존 실패를 감지합니다.
7. **Q07 — O/R:** 반환한 서명값을 포함한 응답을 통제된 저장소에 즉시 보존하고 응답 해시·명령 상태·세션·토큰의 사용/실패 상태를 기록합니다. 성공 토큰을 재사용하지 않으며 실패 응답만으로 재사용 가능하다고 판단하지 않습니다.
8. **Q08 — O/V/R:** raw r||s와 ASN.1 DER 서명 형식 변환 후 고정 본문으로 인증서/CSR을 조립합니다. 독립 도구로 서명·본문 바이트·키·프로파일을 검사하고 산출물과 원장·증거를 확정 저장합니다. 원본 응답이 이미 있으면 이 단계부터 복구하며 HSM 서명을 반복하지 않습니다.

본문 승인과 토큰 승인은 별도 기록이며 작업 ID로 연결합니다. 토큰 서명만으로 본문 바이트의 불변성이 보장된다고 간주하지 않습니다. 어느 단계든 연결 단절·만료·입력 변경·기록 실패는 중단하고 아래 상태표로 판정합니다.


## 작업 원장과 장애 판정

모의 원장은 `ledger/DEMO-CER-001`입니다. 실행 서비스만 상태를 추가하고 R은 증거를 연결하며 V는 읽어 대조합니다. 작업 ID와 issuer+serial에 중복 잠금을 두고, `요청 시작`이 내구 저장된 뒤에만 HSM에 보냅니다. 조회 절차는 runbook §LEDGER, 접근 정책·장애 시험은 `approved/recovery.md` v1.0 / H(approved/recovery.md)입니다.

| 상태 | 남길 증거 | 실패 시 허용할 처리 |
|---|---|---|
| 준비·승인 | 작업 ID, 예약 serial/CSR ID, DER·키·프로파일·A/B 승인 | 요청 전임을 입증한 뒤 입력 변경·재승인 가능 |
| 요청 시작 | 실제 호출 참조·입력·세션·토큰 메타데이터, 전송 전 intent | 전송/응답의 확정점이 없으면 결과 불명 |
| 응답 보존 | 원본 서명값을 포함한 응답·H·내구 저장 확인 | 동일 응답으로 Q08만 재개, HSM 재서명 없음 |
| 조립·검증 | 고정 본문·서명·SPKI·프로파일 결과 | 같은 응답에서 같은 인증서/CSR을 재조립, 불일치 시 배포 보류 |
| 발급 저장 | 인증서·issuer/serial·키·상태·승인·검사·증거의 확정 기록 | 기존 결과를 조회해 같은 결과의 저장을 완료, 새 발급과 구분 |
| 결과 불명 | 마지막 확정점·요청/응답·조사 결과·복구 불가 범위 | 격리·보호·조사, A/B와 P의 별도 결정 전 재서명·재생성 금지 |

T06 모의 장애 시험은 ①요청 전 실패는 미실행 확인 후 재승인, ②전송 후 응답 유실은 결과 불명 유지, ③응답 저장 후 조립 실패는 같은 응답에서 Q08 복구, ④원장 저장 실패는 같은 결과 조회·저장, ⑤중복 요청은 잠금 거부를 보여줍니다. 응답이 없는 구간은 로그만으로 해소하지 않습니다. 실제 장애 시험 결과가 있다는 뜻은 아닙니다.
