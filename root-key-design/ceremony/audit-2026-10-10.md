# Root·First ICA 세레모니 문서 감사 — 2026-10-10

**감사 전 문서는 행사 구성의 예시로는 사용할 수 있었지만, 실제 운영 행사 승인본으로 사용하기에는 중요한 수행 절차와 증거 연결이 부족했습니다.** 세 서브에이전트가 C2PA conformance, CloudHSM 동작, 실행자·기록자 관점을 각각 감사했습니다. 중복을 합친 13개 지적을 문서에 반영했고, 보강본 재감사에서 발견한 재개·서명·마감 기록 문제도 수정했습니다.

**문서 보강 완료와 운영 준비 완료는 다릅니다.** 실제 계정·권한·명령 구현, HSM 리허설, 신규 키 백업 포함 확인 방법, 외부 수용 회신은 아직 확보하지 않았습니다. 따라서 지금 문서를 복사해 이름만 채우고 운영 키를 생성해서는 안 됩니다. 반대로 이번 감사만으로 C2PA 심사 탈락을 확정할 수도 없습니다. 아래의 남은 증거를 갖춘 뒤 행사 승인 여부를 판단해야 합니다.

가장 먼저 닫을 문제는 다음 네 가지입니다.

- **생성·사용·관리·복구를 각각 통제하는 실제 권한 설계:** quorum 숫자와 서명 두 개만으로 단독 우회 차단을 입증할 수 없습니다.
- **세 번의 서명에 대한 실행 가능한 명령:** 본문 고정부터 CLI 토큰·개인 승인·실제 입력 대조·응답 보존·조립·검사를 연결해야 합니다.
- **불확실한 결과와 대기 상태의 처리:** 응답 없는 서명을 로그에서 복구할 수 있다고 가정하거나, 새 키 백업이 당일 바로 생긴다고 가정해서는 안 됩니다.
- **수행 당시 증거와 최종 보관:** 개인별 승인·실제값·입회·일탈·후속 서명과 마지막 종료 기록까지 재구성할 수 있어야 합니다.

## 감사 범위와 판정 방법

대상은 [샘플](ceremony-script-sample.md), [템플릿](ceremony-script-template.md), [작성 가이드](script-writing-guide.md), [준비 체크리스트](preparation-checklist.md), [CloudHSM 절차](cloudhsm-options.md), 문서 색인입니다. 기존 키 생성·인증서 발급·다인 통제 설계는 연결과 일관성만 확인했습니다. `root-key-design/`와 `c2pa-design/`의 주장을 규격 근거로 사용하지 않았습니다.

C2PA 근거는 `conformance-public`의 commit `2466172859fad1215f7aaf7e3768b41a0ac29abc`, `docs/v0.2` 원문을 Git 객체에서 추출해 대조했습니다. AWS는 2026-10-10 확인한 공식 문서를 사용했습니다. 신청 시 인정되는 C2PA 버전과 배포할 CloudHSM 모델·모드·CLI 버전은 행사 전에 별도로 확정해야 합니다.

| 관점 | 확인한 질문 | 결과 식별자 |
|---|---|---|
| C2PA conformance | 원문 의무가 현장 확인·증거·보존으로 연결되는가? 프로젝트 권고를 규격 의무로 과장했는가? | C01–C05 |
| CloudHSM | 제시한 승인 집합·토큰·세션·키 속성·백업·복구가 실제 제품 동작과 맞는가? | H01–H09 |
| 실행자·기록자 | 문서 순서대로 진행하면 누가 무엇을 실행·검사·기록할지 알 수 있는가? 실패하면 어디서 재개하는가? | EX01–EX06 |

**높음 7건**은 기존 서술대로 승인본을 만들 경우 운영 시작 전에 막아야 할 결함입니다. **중간 6건**은 환경 확인·증거·수용 판단을 보완해야 하는 결함입니다. 심각도는 이번 준비 작업의 우선순위이며 C2PA가 부여한 등급이 아닙니다. 아래 13건은 문서에 반영했지만 각 행의 실증·승인 증거는 미확보 상태입니다.

## 1. 실제 수행을 막는 지적

### A01 · 높음 · “사용 승인 확보” 뒤의 실제 quorum 실행이 빠졌습니다

**현장 질문:** “어느 세션에서 누가 토큰을 만들고, 승인자는 무슨 파일에 서명하며, 만료되면 어디부터 다시 하나요?”

감사 전 S02/S04/S05는 사용 승인 확보와 서명을 요약했지만 토큰 생성·전달·개인 서명·취합·승인 집합 검사·`--approval` 전달·소모 상태 기록이 없었습니다. AWS CLI 토큰은 한 작업·현재 로그인 세션에 한정되며 다른 앱으로 가져가 사용할 수 없습니다. [AWS CU 사용 절차][aws-use]

**반영:** 템플릿·샘플에 Q01–Q08을 두고 Root 자기서명, First CSR, Root의 First 인증서 서명이 각각 별도 작업·키·본문·토큰을 사용하도록 했습니다. CloudHSM 부록에는 승인 입력 변환, 기한·세션·실패 처리도 연결했습니다.

**남은 증거:** 실제 명령 파일·버전·해시, 승인자 장치와 전달 경로, 승인 부족·만료·연결 단절·다른 세션·중복 사용·잘못된 키 시험. 담당: PKI 구현자와 검증자. 원 지적: H01, EX02.

### A02 · 높음 · 역할표의 승인자가 실제 HSM 승인 집합과 달랐습니다

**현장 질문:** “A/B 두 명 승인이라고 썼는데 O 자신의 승인과 A의 승인만으로 실행되면요?”

AWS CU는 자기 토큰에도 승인할 수 있습니다. 따라서 O 소유·A/B 공유에서 단순 quorum 2는 A와 B 두 사람이 반드시 참여한다는 의미가 아닙니다. 실제 사람·계정·승인키 등록·키 공유·정족수를 함께 봐야 합니다. [AWS CU 주의점][aws-notes] · [생성 인자와 관련 사용자][aws-ec]

**반영:** 샘플은 가상 선택을 명확히 바꿨습니다. 본문은 A+B, HSM 토큰은 O+A+B의 3-of-3이며 O가 실행합니다. 템플릿은 프로젝트 N/M을 미정으로 유지하고 사람↔CU/admin↔승인 공개키↔소유/공유·허용 집합 표를 추가했습니다.

**남은 증거:** 실제 N/M 승인, 동일인의 복수 계정·O 자기승인·등록/교체키·미공유 CU·직접 CLI 경로를 포함한 승인 행렬 시험. 샘플 3-of-3을 운영 정책으로 확정한 것이 아닙니다. 담당: 보안 설계자와 HSM 관리자. 원 지적: H02.

### A03 · 높음 · 생성 통제와 지식 분리가 실행 단계로 내려오지 않았습니다

**현장 질문:** “공동으로 생성 접근을 켠다는 게 어떤 명령인가요? O가 보호 없는 다른 키를 만들면 무엇이 막나요?”

키 생성 명령은 AWS quorum 지원 서비스 목록에 없습니다. 생성 인자의 use/manage quorum은 생성된 키의 후속 작업 조건입니다. CP는 생성·발급의 다인 통제와 지식 분리, CA 키 단독 접근 방지를 요구하므로 승인 티켓·입회만으로 기술적 차단을 주장할 수 없습니다. [AWS 서비스 범위][aws-services] · [CP 생성][cp-generation] · [CP 발급][cp-issuance] · [CP 키 보호][cp-protection]

**반영:** S01/S03 각각 G01 공동 접근 활성화 → G02 보호 설정을 포함한 생성 → G03 실제값·반영 상태 확인 → G04 공개키 추출 → G05 생성 접근 회수를 연결했습니다. 행위별 사람·계정·보호 재료·단독 수행 불가 근거와 우회 시험을 쓰도록 했습니다.

**남은 증거:** CU 자격·호스트·네트워크·코드·AWS 관리자·복구 경로의 실제 통제, 생성 시 보호 설정, 다른 호스트·직접 CLI·교체 코드에서의 우회 거부, 접근 회수 실증. 지식 분리 방식의 수용 근거도 필요합니다. 특정 비밀 분할 알고리즘을 새 의무로 정한 것은 아닙니다. 담당: 보안·인프라·PKI 구현자. 원 지적: H03, C01, EX01.

### A04 · 높음 · 관리자 초기 설정과 설정 변경의 통제값이 없었습니다

**현장 질문:** “user quorum만 2로 올리면 설정 자체를 관리자 한 명이 바꿀 수 없나요?”

AWS의 관리자 `user`와 `quorum` 서비스는 별도입니다. 초기 설정 예시의 중간 상태를 최종 상태로 복사해서는 안 됩니다. 승인키 등록·교체, MFA, 호스트·복구 권한도 검사 대상입니다. [AWS 초기 설정][aws-admin] · [quorum 값 변경][aws-quorum-change]

**반영:** B00 초기 설정 인계와 S00의 실제 값 조회·등록·우회 시험 대조를 넣었습니다. IAM 권한과 HSM 내부 권한, 최초 자격 회수, 서비스별 최종값을 구분합니다.

**남은 증거:** 실제 user/quorum 및 적용 서비스 값, 개인별 관리자·승인키 인계, 단독 값 완화·사용자/승인키 교체·실행 환경 변경·복구 우회 시험. 담당: HSM·AWS 관리자와 독립 검증자. 원 지적: H04.

### A05 · 높음 · 승인 본문과 HSM 입력·출력 사이가 가상 도구에 맡겨져 있었습니다

**현장 질문:** “SHA-256과 SHA-384 중 무엇을 서명하나요? 반환 서명값을 인증서에 어떻게 붙이나요? CSR 본문은 언제 고정하나요?”

AWS ECDSA 명령은 raw/digest 입력을 구분하고 Base64의 raw `r||s` 서명을 반환합니다. 인증서/CSR 완성본이 아닙니다. 인증서는 DER TBSCertificate, CSR은 DER CertificationRequestInfo를 서명하므로 승인한 바이트와 실제 입력·조립 결과를 연결해야 합니다. [AWS ECDSA][aws-ecdsa] · [RFC 5280 §4.1.1.3][rfc5280] · [RFC 2986 §4.2][rfc2986]

**반영:** CMD-06a/06b로 CSR 준비와 서명을 분리하고 CRI DER도 고정합니다. Q절차에 증거 해시와 서명 해시, raw/digest, 정확한 키 선택, 원본 응답, ASN.1 변환·조립·별도 검사를 포함했습니다. HSM 토큰이 본문 바이트를 자동 고정한다고 가정하지 않습니다.

**남은 증거:** 공개키 추출·서명·변환·조립·검사 코드, ECDSA 정수 부호/길이와 알고리즘 식별자, 승인 후 입력/키 변경·중복 해시·다른 프로파일의 거부 시험. 담당: PKI 구현자·검증자. 원 지적: H05, EX05.

### A06 · 높음 · 서명 응답 유실을 “조회 후 재개”로 해결할 수 없었습니다

**현장 질문:** “HSM은 서명했는데 결과 저장 전에 프로세스가 죽었습니다. 어느 로그에서 서명값을 되찾나요?”

AWS 관리 감사로그를 해당 본문의 모든 서명 성공·미실행이나 원본 서명값 회수 수단으로 취급할 근거가 없습니다. 로그가 없다는 이유로 미실행이라고 판단하면 중복 서명이 발생할 수 있습니다. CP의 동일 키 갱신·새 인증서 발급 제한 때문에 발급 경계도 정해야 합니다. [AWS 감사로그 범위][aws-audit] · [CP Renewal/Modification][cp-renewal]

**반영:** 원장을 준비/승인 → 요청 시작 → 응답 보존 → 조립/검증 → 발급 저장으로 나눴습니다. 응답이 보존됐으면 동일 응답으로 Q08만 재개합니다. 실행 여부나 결과 바이트가 불명이면 `결과 불명`으로 보류하고 자동 재서명·재생성을 금지합니다.

**남은 증거:** 내구 저장·잠금·serial 예약·중복 방지·발급 확정 시점, 요청 전/전송 후/응답 전/저장 중 장애 주입, 회수 불가능한 경우의 정책·책임자. 문서 상태표가 불확실한 장애 구간을 제거하지는 않습니다. 담당: PKI 구현자·보안 승인자. 원 지적: H06, EX04.

### A07 · 높음 · 신규 키의 실제 백업과 최종 자료의 복구를 입증할 수 없었습니다

**현장 질문:** “READY 백업이 어제 것인데 방금 만든 키도 들어 있나요? 백업이 안 생기면 오늘 행사를 끝내도 되나요?”

AWS는 주기적으로 백업하며 일반적인 즉시 백업 지시를 제공하지 않습니다. 이전 백업 READY는 새 키 포함 증거가 아닙니다. 복구하면 옛 사용자·설정도 돌아오므로 과거 권한을 되살리는 경로를 통제해야 합니다. CP의 백업 대상에는 키뿐 아니라 인증서 DB·설정·감사로그 등 중요 자료도 있습니다. [AWS 백업][aws-backup] · [복구][aws-restore] · [CP Backup and Recovery][cp-backup] · [키 백업 보호][cp-protection]

**반영:** B01과 S06에 신규 두 키·최종 사용자/공유/quorum 포함 근거, backup ID·시각·상태·off-site·복구 권한을 넣었습니다. 샘플은 첫날 백업 대기, 다음 날 남은 검사만 재개하는 행사로 바꿨습니다. 원장·로그·승인·종료·마지막 서명도 보호 보관하도록 했습니다.

**남은 증거:** 실제 백업 포함 확인 방법, 확인 도구·리허설, 과거 백업·타 계정 공유·복구 환경의 접근 통제, 비키 자료 복구·조회, 대기 중 custody. 운영 HSM을 즉흥적으로 추가/제거해 백업을 유발하는 절차는 채택하지 않았습니다. 담당: 운영·보안·AWS 관리자. 원 지적: H07, EX03, C04.

## 2. 증거와 운영 판정을 약하게 만드는 지적

| ID·원 지적 | 감사 전 부족한 점과 영향 | 반영한 내용 | 행사 전 남은 증거·담당 |
|---|---|---|---|
| A08 · 중간 · H08 | 로그아웃·접근 회수·키 삭제가 구분되지 않음. 사용 quorum만으로 소유자의 삭제까지 보호된다고 오해 가능 | X01과 S07에 유지할 CU/소유/공유, 회수할 임시 접근·세션·토큰, 별도 삭제/속성 잠금 절차 | 회수 후 직접 접속·잔존 세션·owner 삭제·클러스터/백업 삭제 통제 시험, 폐기 계획 / 보안·운영 |
| A09 · 중간 · H09 | 대상 클러스터·전체 노드·public/private 식별·복제 상태 검사 부족. 다른 클러스터나 부분 생성 상태로 진행 가능 | B00·G03/G04에 account/region/cluster, 모델·모드·CLI, 두 키 식별자·coverage·SPKI 추출·중단 기준 | 실제 조회·공개키 추출·동기화 지연/부분 실패 결과, 모듈 적격성 / HSM 관리자·검증자 |
| A10 · 중간 · C02 | 역할 이름을 적는 것과 trusted role의 유효 자격 확인이 혼동됨 | 임명 승인·적용 정책·적격성·교육 유효 상태·확인자/일자를 S00과 준비에 연결 | 인사/보안의 유효 확인. 신원조사 원본은 증거에서 제외 / 인사·보안 |
| A11 · 중간 · C03 | 인증서 기록 보존을 자유 기입으로 두어 장기 CA 만료 전에 삭제될 수 있음 | 인증서 기록 만료 후 최소 1년, 필수 필드·기산점·권한; 다른 기록은 별도 정책 | 인증서별 보존 종료일·저장 정책·삭제 통제·복구/조회 검사 / 기록·운영 |

A08–A09의 제품 근거는 [AWS 삭제][aws-delete], [속성][aws-attributes], [EC 생성 결과][aws-ec], [키 가용성][aws-durability]입니다. A10–A12의 원문 근거는 [CP 인원 통제][cp-personnel], [인증서 기록][cp-repository], [기록 보관][cp-archival], [감사로그][cp-logging]입니다. A13의 구체 양식은 프로젝트 선택이며, 수행·일탈·서명 증거 요구는 [CP 생성][cp-generation]과 [Program][program]에 근거합니다.

인원 확인의 5년 주기는 CP에 명시된 신뢰 역할 상근 직원 범위로 설명했습니다. 모든 행사 참석자에게 같은 주기가 적용된다고 쓰지 않았습니다. 만료 후 1년 하한 역시 발급 인증서 기록에 대한 원문 요구이며 모든 영상·로그의 일괄 보존기간으로 확대하지 않았습니다.

## 3. 보강본 재감사에서 수정한 연결 문제

세 에이전트가 수정된 샘플·템플릿·가이드·CloudHSM 부록을 다시 읽었습니다. 다음은 최초 지적을 고치는 과정에서 남았던 문제입니다.

| 재감사 항목 | 발견한 문제 | 후속 반영 |
|---|---|---|
| R01 제한 재개 | 다음 날 S00 재점검이 Root 생성 시작 선언·전체 참여자를 다시 요구 | S00-R 신설. P/C/V/R과 필요한 조회 담당자가 남은 검사만 재개하고 새 생성·서명을 금지 |
| R02 서명 범위 | S06 전원 서명 조건과 다음 날 일부 참여자의 후속 서명 예시가 충돌 | 첫날 생성·입회 서명 보존, 후속 수행자는 추가 범위에만 서명. W의 관찰 범위를 사후 확대하지 않음 |
| R03 임시 종료 증거 | 첫날 서명 후 E06a-HOLD가 후속 봉인 목록에 빠짐 | 별도 HOLD 목록·C/V 서명, 다음 날 목록에서 이를 명시 연결 |
| R04 최종 기록 백업 | S06 백업 이후 생긴 서명·E07·최종 목록이 빠질 수 있음 | S07에서 후속 묶음 보관·복제·조회, 마지막 판정/보관 확인 자체의 보호 저장. 미확정이면 완료 보류 |
| R05 샘플 연결 | “아래 상태표” 부재와 첫날 서명 시간대 불일치 | 샘플 상태표 추가, 보존 응답/새 요청/결과 불명 분기, 수행표와 개인별 시각 일치 |

문서 색인도 바꿨습니다. 당일 기준은 **행사별 승인본과 그 승인본이 버전·해시로 고정한 부록**입니다. 기존 키 생성·인증서 발급 문서는 기술 참고이며, CloudHSM 설정을 수행 절차 확정 뒤에 검토하도록 안내하던 문구는 제거했습니다.

## 4. 운영 행사 승인 전에 해소할 항목

아래는 문서를 더 길게 쓰는 것으로 닫을 수 없는 항목입니다. 담당 실명·기한·증거 ID를 준비 체크리스트 D01–D16과 행사 승인본에 기록합니다.

| 우선순위 | 승인 전에 필요한 결정·증거 | 닫는 기준 |
|---|---|---|
| 1 | 실제 CloudHSM 모델·모드·버전, 대상 계정/클러스터, 개인별 계정·정족수·승인키·관리자 통제 | B00 조회 결과와 승인 설정 일치, 허용/거부 조합 시험 검토 |
| 2 | 생성·관리·복구를 포함한 다인 통제와 지식 분리 | 실제 구현·권한표·보호 재료·우회 시험으로 단독 수행 불가 설명 |
| 3 | 공개키 추출, DER 준비, CLI 승인·서명, 조립·독립검사, 원장·응답 저장 도구 | CMD/G/Q/B/X 각각 실제 명령·입출력·버전·해시·실패 판정, 전체 리허설 |
| 4 | 신규 키 백업 포함 확인·대기/복구, 로그 수집 완료, 최종 자료 보존·복제 | 테스트 복구와 이번 행사 확인 방법 검증, 실제 수행 때 ID·시각·내용·조회·인수 증거 확보 |
| 5 | 인원 자격·입회 계획·서명 방식·보존 정책과 제출 형식 | 정책 승인, 유효 확인, 실제 관찰·서명·원본/제출본 연결 가능 |
| 6 | 미등록 Root 범위, 공용 First의 목록별 수용, 프로파일/schema 차이, 인정 버전 | 필요한 C2PA 관리자 회신·계약/기준 확인. 내부 예외 승인으로 대신하지 않음 |

명령의 지원 여부, 불확실한 결과 처리, 입력 변경 차단, 생성·관리자·복구 우회 중 하나라도 확인되지 않으면 그 경로에 의존하는 운영 생성·서명을 승인하지 않습니다. 백업·로그가 행사 후 대기 상태면 키 보호와 당시 기록을 인계하고 세레모니 완료·운영 개시를 구분합니다.

## 5. 추가 결함으로 세지 않은 내용과 검증 한계

- 독립 입회 요구, 조건부 WebTrust 대체, 서명된 수행 스크립트, Root/First의 키→CSR→인증서 연결은 이미 문서에 있었습니다. 영상·공증·특정 입회자 자격을 원문에 없는 일률적 의무로 추가하지 않았습니다. [Program][program]
- OCSP 준비와 세레모니·운영 개시·Trust List 등록을 구분하고 있었습니다. 이번 감사는 OCSP 서비스 구축이나 전체 CPS·CA 운영 적합성 감사가 아닙니다.
- 샘플은 처음부터 가상 행사였으며 모의 통과를 허위 운영 증거라고 판정하지 않았습니다. 다만 실제 작성자가 놓치기 쉬운 단계는 샘플에서도 구체화했습니다.
- 실제 AWS 계정/HSM에 접속하거나 운영 키를 생성·서명·복구하지 않았습니다. 실행 코드도 이번 감사에서 구현하지 않았습니다. 문서 검토 결과를 제품 시험 통과나 외부 심사 승인으로 읽어서는 안 됩니다.

최종 확인에서는 보강한 8개 문서의 로컬 링크·앵커 70개, 참조 정의, 샘플의 빈 기입란 잔존 여부, CMD/S단계 대응과 공백 오류를 검사했습니다. 실행·conformance 담당 에이전트가 재감사 수정과 보고서의 대응도 확인했습니다. 기존 `key-generation.md`의 P-384 입력 수정은 변경하지 않았습니다.
