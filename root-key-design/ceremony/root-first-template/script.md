## 당일 사용할 설정과 실행 절차

- 키·인증서·HSM 환경은 [승인 설정](settings.md#승인-설정), 권한과 정족수는 [사람과 권한의 연결](settings.md#사람과-권한의-연결)을 확인합니다.
- CMD-00–12, G01/G05, B01, X01의 실제 호출은 [실행 작업](runbook.md#실행-작업)에 연결합니다. 매 서명은 [Q01–Q08](runbook.md#공통-서명-절차-q01부터-q08)을 적용합니다.
- P는 [준비 현황과 승인본 목록](preparation.md)을 확인하고 승인된 문서·설정·명령·도구 버전이 일치할 때만 S00을 시작합니다.
- R은 [수행 기록 양식](records/record-template.md)을 회차별 사본으로 만들고, 단계마다 E00–E07을 [증거 목록](evidence-index.md)에 연결합니다. 서명한 기록은 덮어쓰지 않습니다.

## S00 시작 확인

1. **R/W**는 행사 ID·기록 시간대·입회 시작·관찰 범위를 기록합니다. **P**는 개인 신원·역할 임명·적격성/교육의 유효 확인, 독립성·겸임·정족수를 점검합니다.
2. **O/V**는 CMD-00과 B00 인수 기록으로 계정·리전·클러스터·각 HSM 상태·모델·모드·CLI·호스트·코드·설정 해시를 대조합니다. 승인된 노드 coverage와 지연 허용 기준을 적용합니다.
3. **V**는 실제 관리자 user/quorum 및 해당 서비스 값, 승인자 등록키, 생성·관리·삭제·복구·실행기 변경 권한을 인수 기록과 대조합니다. 초기 설정 중간값을 완료값으로 사용하지 않습니다.
4. **R/V**는 HSM별·AWS 관리·호스트·실행기·승인 로그 원천, 실명/계정 연결, 시각 오차, 도착 지연·누락 검사와 증거/원장 쓰기·조회 시험을 확인합니다. 기록 원천마다 무엇을 입증할 수 있는지 확인합니다.
5. **A/B/C**는 준비 시험·설정·요청 허가·백업 포함 확인 및 대기 계획을 확인합니다. **C**가 생성 직후 보호 책임을 인수한 뒤 **P**가 시작 승인하고 R이 기록합니다.

> 행사 {{행사_ID}}의 승인본·환경·역할·통제·입회·기록 준비가 일치함을 확인하여 Root 키 생성을 시작합니다.

- **통과 조건:** 승인된 모든 사전 통제와 B00 인수·증거 수집 준비 충족.
- **증거 E00:** 참석·역할 유효 확인, 실제 설정 조회, 로그 원천·저장 시험, 시작 승인.
- **중단:** 승인본·권한 불일치, 부트스트랩/시험 미완료, 필수 역할·입회·로그·저장 부족.

## S01 Root 키 생성

1. **O**는 키별 승인 설정과 생성 작업 ID를 제시하고 **A/B**가 승인합니다. **W**는 관찰 상태를 확인합니다.
2. **O/A/B**는 G01의 승인된 명령으로 생성 접근만 활성화합니다. **V**는 허용 호스트·계정·실행 코드·생성 파라미터 외의 경로가 열리지 않았는지 확인하고 활성화 증거를 남깁니다.
3. **O**는 원장에 생성 요청 시작을 기록하고 G02/CMD-01를 실행합니다. 영구 보관·소유/공유·사용/관리 quorum·키 속성을 승인값대로 생성 시 적용합니다. 사후에 보호를 붙일 목적으로 무보호 키를 생성하지 않습니다.
4. **V**는 G03/G04로 공개키와 개인키 식별자, 실제 속성·공유·quorum·노드 coverage·공개키 추출과 지문을 확인합니다. 새로운 Root 키의 공개키를 식별합니다. 부분 생성·부분 복제는 통과 처리하지 않습니다.
5. **R/C**는 생성 응답·시각·공개키·속성·로그를 보존하고 생성 직후 보호와 B01 백업 추적을 시작합니다.
6. **O/A/B**는 G05로 임시 생성 접근을 회수하고 **V**가 회수·잔여 접근을 검사합니다. 이후 서명에 필요한 지속 계정·키 소유/공유는 임의 삭제하지 않습니다. 세션이 끊겼다면 Q02에서 새 세션을 사용합니다.

- **통과 조건:** 생성 순간 보호, read-back·coverage·지문 일치, 생성 접근 회수 및 보호 인계.
- **증거 E01:** 활성화 승인·검사, 생성 요청/응답·키 식별·속성 검사, 접근 회수·검증, 백업 추적.
- **중단:** 통제·옵션·권한 불일치, 부분 성공·결과 불명, 필수 증거 누락, 접근 회수 실패. 재생성 전 상태를 확정합니다.

## S02 Root 자기서명 인증서 발급

1. **O/V**는 CMD-02로 Root TBSCertificate DER·내용표·해시를 고정하고 serial 예약·중복 발급 여부, Subject=Issuer, 공개키=S01을 검사합니다.
2. **O·A/B·V·R**은 공통 Q01–Q08을 순서대로 수행합니다. 서명 대상은 Root 본문, 서명 키는 Root이며 이 작업 전용 토큰·승인·세션 기록을 사용합니다. **O**는 Q06 직전에 “S02의 승인 본문 해시와 Root 키 지문을 대조했고, 이 본문에 자기서명을 실행합니다”라고 명시적으로 지시합니다.
3. **V**는 CMD-04로 자기서명 자체·승인 본문 바이트·공개키·필드·확장·프로파일을 검사합니다. 신뢰 저장소 검사 성공만으로 자기서명 검사를 대신하지 않습니다.
4. **R**은 원본 HSM 응답, 변환·조립 결과, Root DER/PEM과 해시, 승인·토큰 메타데이터·독립 검사·원장 저장을 연결합니다.

- **통과 조건:** Q01–Q08, 자기서명·프로파일 검사와 내구 저장 완료.
- **증거 E02:** 작업·본문 승인·토큰 승인·실행·응답·인증서·검사·원장 기록.
- **중단:** 승인집합·세션·토큰·본문·키 불일치, 결과 불명, 검사·저장 실패.

## S04 First CSR 생성

1. **O**는 CMD-06a로 S03 First 공개키·Subject·허용 요청 확장을 사용한 CertificationRequestInfo DER와 내용표·해시를 고정합니다. 요청 허가와 연결하고 승인 이후 재구성하지 않습니다.
2. **V/A/B**는 요청 권한·정보·공개키·서명 대상 바이트·알고리즘을 검사하고 승인합니다.
3. **O·A/B·V·R**은 공통 Q01–Q08을 수행합니다. CSR 작업 ID와 First 키를 사용하며 별도 토큰을 발행합니다. CMD-06b는 승인된 CRI에 서명하고 CSR을 조립합니다.
4. **V**는 CMD-07로 CSR 서명·공개키·요청 정보를 검사하고 완성 CSR에서 추출한 CRI DER가 고정본과 같은지 대조합니다. 요청 확장을 인증서에 그대로 복사하지 않습니다.
5. **R**은 CRI·본문 승인·토큰 승인·원본 응답·CSR·독립 검사·저장 결과를 연결합니다.

- **통과 조건:** First 키의 Q01–Q08과 CRI 바이트·CSR 서명·권한 검사 및 저장 완료.
- **증거 E04:** CRI·해시·승인, 작업/세션/토큰 기록, CSR·요청 허가·검사.
- **중단:** CRI·승인·공개키·서명·요청 정보 불일치, 결과 불명, 검사·저장 실패.

## S05 First 인증서 발급

1. **O/V**는 CMD-08로 검사된 CSR과 승인 프로파일에서 First TBSCertificate DER·내용표·해시를 고정합니다. serial 예약·중복 검사, 기간·issuer·확장·First 공개키 연결을 확인합니다.
2. **O·A/B·V·R**은 공통 Q01–Q08을 수행합니다. 서명 대상은 First 인증서 본문, 서명 키는 Root이며 이 작업 전용 토큰을 사용합니다. **O**는 Q06 직전에 “S05의 승인 본문 해시와 Root 키 지문을 대조했고, First 인증서 서명을 실행합니다”라고 명시적으로 지시합니다.
3. **V**는 CMD-10으로 Root의 서명·Root→First 연결, First 공개키·승인 본문·필드·확장·프로파일을 검사합니다. 검사 예외는 조항·실제 결과·해석/외부 회신과 연결합니다.
4. **R**은 응답·변환·First DER/PEM·체인·해시, 승인·검사·원장 기록을 내구 저장합니다.

- **통과 조건:** Q01–Q08, 서명·본문·CSR/키 연결·프로파일 검사와 내구 저장 완료.
- **증거 E05:** 작업·본문/토큰 승인·실행·응답·인증서/체인·검사·원장 기록.
- **중단:** 승인·세션·토큰·본문·키·프로파일 불일치, 결과 불명, 검사·저장 실패. 동일 키의 즉시 재발급으로 처리하지 않습니다.

## S06 전체 결과와 수행 확인 서명

1. **V**는 `CMD-11`로 다음 연결을 최종 대조합니다.
   - Root 생성 공개키 = Root 인증서 공개키 = S02/S05 서명 키의 공개키.
   - First 생성 공개키 = First CSR 공개키 = First 인증서 공개키.
   - 승인 본문·키·프로파일 = 실제 서명·발급·검사·원장 기록.
2. **C/V**는 B01로 두 신규 키와 최종 사용자·공유·quorum 설정의 백업 포함 여부를 확인합니다. backup ID·생성/완료 시각·상태·확인 방법, 선택한 off-site 사본 ID·완료·보호·복구 권한을 기록합니다. 과거 백업의 READY만으로 통과하지 않습니다.
3. **C/V**는 원장·설정·감사로그·승인 기록·증거 목록도 백업하고 ID·최종 데이터 포함·무결성·조회/복구 검사·인수자를 기록합니다. 과거 사용자/승인키/정책이 복구로 되살아나는 경로를 현행 원장과 대조하는 절차를 확인합니다.
4. 백업·로그 수집이 미완료이면 **P**가 `백업/증거 대기`로 보류합니다. 그 시점의 수행·입회 기록을 확인 서명하고 C에게 보호를 인계한 뒤 X01로 임시 접근을 종료합니다. 다음 일정에 아래 S00-R 재개 확인 후 S06의 미완료 검사만 수행하며 키 생성·서명을 반복하지 않습니다.
5. **R**은 E00–E05와 백업 확인 자료를 증거 목록에 연결하고 파일 해시를 고정합니다. 일탈이 없으면 `없음`, 있으면 일탈 ID·조치·잔여 제한을 적습니다.
6. **P**는 실제 수행 기록·증거 목록·일탈을 참여자·입회자에게 제시합니다. 각자는 자신의 수행·관찰 범위를 확인 서명란에 기록합니다.
7. **P·O·A·B·V·R·W·C**는 각자의 수행·관찰 범위에 확인 서명을 남깁니다. 계획된 보류 시 이미 서명한 생성·입회 기록은 보존합니다. 후속 검사만 재개하면 그 검사 수행자·검증자·기록자·판정자가 추가 범위에 서명하며, 기존 참여자나 W가 관찰하지 않은 후속 작업을 사후 서명하지 않습니다. 재개 범위가 승인된 관찰 조건을 바꾸면 먼저 입회 계획을 다시 승인합니다.

- **통과 조건:** 결과·증거 연결, 백업 확인, 일탈 처리 및 참여자·입회자 서명 완료.
- **증거 E06:** 최종 검사·백업 확인, 증거 목록, 일탈 목록, 서명된 수행 기록.
- **중단:** 증거 연결 불가, 필수 검사·입회·서명 누락, 미해결 일탈.

## S07 운영 인계와 접근 종료

1. **C**는 키 보관·백업·기록, First 상태 서비스와 폐지·사고 대응의 책임을 인수합니다. 미가동 서비스는 담당자·기한·운영 개시 제한을 기록합니다.
2. **O/C**는 X01/CMD-12로 세션·토큰·임시 AWS/호스트/네트워크 접근·승인 장치 인계를 정리합니다. **V**는 회수 후 접근 거부와 의도적으로 유지한 HSM 계정·소유/공유를 목록별로 확인합니다. 삭제·속성 잠금은 별도 승인 절차 없이 수행하지 않습니다.
3. **R**은 인수·종료 기록을 E07로 추가하고 최종 증거 목록을 고정합니다. S06 서명 대상은 그대로 보존하고 추가 인수·종료 기록에 담당자가 별도로 확인 서명합니다.
4. **C/V**는 S06 이후의 확인 서명, 보류 시 임시 종료 기록, E07과 최종 목록·후속 서명까지 포함한 묶음을 보호 저장소에 백업하고 버전·완료 시각·해시·조회 결과를 남깁니다. S06 시점 백업만으로 최종 자료 보관을 완료 처리하지 않습니다.
5. **P**는 이 보관 확인을 근거로 최종 판정에 서명합니다. 최종 판정·백업 확인 기록 자체도 승인된 보존·복제 경로에 저장하고 **R/V**가 저장 성공을 확인해야 완료입니다. 원래 서명한 목록에 후속 자료를 끼워 넣거나 목록이 자기 해시를 포함하도록 만들지 않습니다. 저장·복제 완료가 불명이면 `최종 기록 보관 대기`로 C에게 인계합니다.

- **통과 조건:** 키·백업·증거 인수와 접근 종료, 후속 자료까지 보호 보관·조회 완료, 최종 판정과 그 저장 확인.
- **증거 E07:** 인수서, 접근 종료 검사, 최종 증거 목록, 완료 판정.
- **중단:** 인수 책임자 부재, 접근 종료 실패, 필수 기록 누락.

## S00-R 백업·증거 대기 후 제한 재개

1. **P/C/V/R**은 이전 서명 목록·대기 사유·custody·임시 접근 종료 기록과 미완료 항목을 대조합니다. 새 키 생성이나 HSM 서명을 포함하지 않는 재개인지 확인합니다.
2. **V/C**는 필요한 환경·권한·데이터의 동일성, 대기 중 변경과 사고 여부, 백업·로그 수집·기록 저장 상태를 확인합니다. 역할별 유효 자격과 승인된 관찰 범위를 확인하고, 실제 조회에 O나 다른 담당자가 필요하면 그 사람의 참여·최소 접근을 기록합니다. A/B·W의 재참석 필요 여부는 재개 작업과 승인된 입회 조건으로 판단합니다.
3. **P**는 “이전 생성·서명 기록을 유지하고 S06의 남은 백업·증거 검사와 S07 종료만 재개합니다”라고 승인합니다. S00의 Root 생성 시작 선언이나 S01–S05를 반복하지 않습니다. 범위가 달라지면 제한 재개를 취소하고 별도 변경 승인을 받습니다.
4. **R**은 회차·참석·조회 접근·검사 범위·재개 승인을 E00-RESUME에 기록합니다. 후속 수행자들은 추가 기록에 자신의 범위만 확인 서명합니다.

## 중단과 재개

1. 발견자는 단계와 사유를 알리고 O는 후속 생성·서명 요청을 중단합니다. R은 시각·마지막 명령·현재 결과를 기록합니다.
2. V/O는 생성 키 조회와 서명 결과 복구를 구분합니다. 서명은 [원장 상태표](runbook.md#작업-원장과-장애-판정)와 내구 저장된 실행기 요청·응답을 확인합니다. HSM/CloudWatch 관리 로그만으로 해당 본문의 서명 성공·미실행 또는 서명값 복구를 단정하지 않습니다. 상태 확인 전 재실행·삭제하지 않습니다.
3. C는 키·백업·증거 보호를 유지하고 사고 의심 시 {{사고_절차}}로 넘깁니다.
4. 저장된 동일 응답은 Q08만 재개하며 새 HSM 서명을 요청하지 않습니다. 요청 전 미실행이 입증된 작업은 필요한 새 승인·세션·토큰을 확보하고 {{재개_승인권자}}가 실행을 승인합니다. 결과 불명은 별도 정책 판단으로 넘기고 백업·증거 대기는 S00-R을 적용합니다.
5. 해소되지 않으면 중단 상태로 인계합니다. 유지·폐기·재생성은 {{판단_책임자와_절차}}에 따라 별도 승인합니다.

## 기록·확인 서명·최종 판정

S06의 수행·관찰 확인과 S07의 인수·종료·최종 판정은 [회차별 기록](records/record-template.md#확인-서명과-최종-판정)에 남깁니다. 승인 스크립트·설정·실행 절차는 그대로 보존하고, 후속 기록은 이전 목록과 서명을 참조하는 새 목록에 연결합니다. 세레모니 완료, 운영 준비, 제출·등록 상태는 각각 판정합니다.
