## 기록·확인·증거 요점

- 진행자가 각 작업 직후 수행 결과를 적는다. 성공·실패·보류·미실행을 구분한다.
- 파일을 저장한 뒤 증거 목록에 등록한다. 표에는 파일 번호와 로그 위치를 적는다.
- 승인 부족, 검사 실패, 기록 누락을 확인하면 다음 생성·서명을 멈춘다.
- 종료 시 실제 참여자와 입회자 전원이 `signoff.md`에 서명한다. 접근 담당자가 겸임이면 본인 서명 범위에 포함하고, 별도 인원이면 서명 행을 추가한다. 작업별 승인 서명은 별도로 보관한다.

### 일탈·미완료 칸은 어떻게 작성하는가

**일탈**은 승인한 절차나 설정과 달랐던 사실이고, **미완료**는 아직 끝내거나 확인하지 못한 일이다. 문제가 없으면 `없음 / 확인자 성명`을 적는다. 문제가 있으면 다음처럼 적는다.

> 예시: 백업에 신규 키가 포함됐는지 미확인 / 추가 조회 예정 / 담당: 성명 / 기한: 날짜·시각 / 확인자: 성명

## Appendix B. 증거를 어떻게 남기는가

### 1. 파일을 저장한다

실행자는 사용한 승인 파일과 작업 결과 파일을 행사 폴더의 `evidence/`에 보관한다. 명령과 화면 출력은 세션 로그로 남긴다. 파일 이름은 `A3.3-first.csr.der`처럼 단계와 내용을 알 수 있게 붙인다. 단계마다 새 폴더를 만들 필요는 없다.

화면 출력만 따로 저장했다면 전체 세션 로그에서 가져온 위치를 적는다. 실패 메시지도 남긴다. 개인키·암호·HSM 백업 원본은 이 폴더에 넣지 않는다.

### 2. 증거 목록에 번호를 붙인다

파일 하나마다 증거 목록에 한 행을 추가한다. **파일 번호, 단계, 내용, 실제 경로, 파일 전체의 SHA-256**을 적는다. 같은 파일을 여러 단계에서 사용하면 다시 등록하지 않는다.

계속 기록 중인 세션 로그는 ID·경로를 먼저 적고 해시 칸에 `기록 중`을 적는다. 단계별 로그 위치는 그대로 기록한다. A4에서 두 로그를 닫은 뒤 최종 SHA-256을 기입한다.

- **증거 파일 ID:** `E001`처럼 직접 붙이는 파일 번호다. 증거 목록에서 경로와 해시를 찾을 때 사용한다.
- **승인 파일 ID:** 위 번호 중 승인 문서·승인 서명·서명된 토큰을 가리키는 번호다. 별도의 승인번호나 토큰 값이 아니다.
- **대상 키/파일:** 작업에 사용한 키 ID나 본문·CSR·인증서 파일명이다. 파일 번호와 구분한다.

### 3. 수행 결과 표에 파일 번호와 로그 위치를 적는다

다음은 CSR 파일과 로그를 적는 방법의 예시다. 번호와 경로는 실제 저장한 자료에 맞춰 적는다.

| 적을 곳 | 기입 예시 |
|---|---|
| 증거 목록 | `E021 / A3.3 / First CSR / evidence/A3.3-first.csr.der / 실제 SHA-256` |
| A3.3 결과 칸 | `성공 / First 키 ID / CSR 본문 해시 / CSR 파일: E021` |
| A3.3 로그 위치 | `E003, 120–148행` — E003으로 등록한 로그에서 이 작업의 명령·응답이 있는 부분 |
| A3.3 승인 칸 | `본문 승인: 성명 2명, E016 / First 토큰 서명: 성명 2명, E017` |

로그는 줄 번호 대신 `E003, 10:20:00–10:21:10 KST`처럼 시간 범위를 적어도 된다. 시각만 적지 말고 어느 로그 파일인지 함께 적는다. 승인 파일·서명 본문·HSM 응답도 각각 증거 목록에 등록한다.

### 4. 단계에 맞는 원문이 있는지 확인한다

**A1 — 시작 자료**

- 보관: 행사 승인본, 승인된 명령·설정·도구 버전, 환경·통제 사전 검토, 실제 환경 조회, 참여자·입회 확인.
- 로그: 환경을 조회하고 기록 저장을 확인한 부분.
- 문제 예: 승인본 불일치, 필수 참여자 부재, 로그 저장 실패.

**A2.1·A3.1 — 생성 승인**

- 보관: Root와 First 각각의 계획, 실제 승인 서명, 앱 검증 결과, 접근을 연 기록.
- 로그: 계획 검증과 접근 활성화 결과.
- 문제 예: 승인 부족, 다른 계획 사용, 계획 해시 불일치.

**A2.2·A3.2 — 키 생성**

- 보관: 생성 응답, 공개키, 키 속성·소유자·공유 사용자·quorum·노드 조회, 접근 회수 기록.
- 로그: 키 생성 요청과 응답, 생성 후 조회, 임시 접근 회수.
- 문제 예: 생성 결과 불명, 설정 불일치, 접근 회수 실패.

**A2.3·A3.3·A3.5 — 서명**

- 보관: 서명할 DER 본문과 내용표, 본문 승인, 실제 사용한 서명된 토큰 원문, HSM 서명 응답, 완성 파일. 토큰은 HSM 작업 성공 후 보관하고 중단 시에도 원문을 보존한다. 세션 종료·보관본 확인 후 작업용 사본만 삭제한다. 인증서 발급에는 serial 예약/중복 검사, First 발급에는 상태 서비스 확인도 남긴다.
- 로그: 어느 키로 어떤 본문을 서명했는지 보여 주는 명령과 응답.
- 문제 예: 승인 후 본문 변경, 다른 키 사용, 토큰 만료, 응답 유실, 파일 조립 실패.

**A2.4·A3.4·A3.6 — 검사**

- 보관: 검사한 파일·해시, 도구/기준 버전, 검사 시각과 항목별 판정. 인증서는 서명 검사와 CP 프로파일 검사를 모두 남긴다.
- 추가 기록: A3.4는 요청자 신원·권한 확인과 발급 허가, A2.4·A3.6은 발급 원장 위치.
- 로그: 해당 파일의 검사 명령과 결과. 문제 예: 검사 실패, 일부 항목 미검사, 권한 미확인, 발급 허가 보류.

**A4 — 종료 자료**

- 보관: 로그아웃·접근 종료, 보호 인수, 최종 키·권한 조회, 신규 키·최종 권한 포함 백업·off-site 사본·보호/복구 확인, 관련 HSM 감사 로그, OCSP·Root 배포 확인. 파일명과 확인 순서는 실행 부록 A4 3)을 따른다.
- 백업 기록: 원본·사본 ID와 대응 관계, 마지막 키·권한 변경 시각, 백업 시각·상태, 포함 판정 근거와 보호 설정 대조 결과를 적는다. 복구 준비는 적용 가능한 사전 시험 증거를 참조한다.
- 로그: 종료·접근 회수·백업 조회 결과와 감사 로그의 대상 시간 범위.
- 문제 예: 백업 포함 미확인, 감사 로그 전달 대기, 입회 공백. 남은 일에는 담당자와 기한을 적는다.

### 5. 기록을 확정한다

진행자는 두 세션 로그가 닫힌 뒤 최종 해시를 등록하고 모든 증거의 경로·해시를 대조한다. 불일치한 값을 임의로 갱신하지 않고 원인을 확인한다. 대조가 끝나면 수행 기록을 확정하고 signoff에 서명한다. 수행 기록과 최종 서명본 자체는 이 증거 목록에 넣지 않는다. signoff가 스크립트·실행 부록·수행 기록의 해시를 식별한다.

서명 후 추가 사실은 원본을 수정하지 않고 별도 후속 기록으로 남긴다. 백업·감사 로그 확인이 남았다면 새 증거·해시·확인자·시각을 기록하고 원래의 미완료 항목과 연결한다. 진행자는 미완료 항목이 모두 해소된 후 완료 판정·성명·시각을 남긴다.
