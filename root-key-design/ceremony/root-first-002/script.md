# Root와 First ICA 세레모니

초안 · 행사 관리명 `root-first-002` · 행사 수행 승인 전

Root·First 키를 생성하고 Root 자기서명 인증서, First CSR, First 인증서를 발급하는 절차다. 영상 촬영 없이 독립 입회, 실행 기록, 참여자 서명으로 수행한다.

진행자는 A1부터 A4까지 순서대로 진행한다. 작업이 끝날 때마다 [수행 기록](templates/record.md)의 해당 행을 작성하고, 종료 시 참여자들이 [수행 확인서](templates/signoff.md)에 서명한다. 설정은 문서 뒤의 부록, 실행 명령은 [실행 명령](commands.md)에 두고 행사 전에 확정·시험·승인한다.

`{{항목}}`은 행사 전 채울 값, `{{현장_항목}}`은 실제 수행 중 채울 값이다.

## 누가 무엇을 하는가

| 문서에서 부르는 이름 | 행사 역할 | 담당 |
|---|---|---|
| 진행자 | Administrator | 순서 지시, 실행 결과 검증, 수행 기록 작성. 키 생성·서명 실행과 quorum 승인에는 참여하지 않음 |
| 실행자 | Crypto Officer / Key Custodian 1 | 키 생성·서명 명령 실행, 출력과 생성 파일 저장. 본인 승인키로 승인 가능 |
| 승인자 | Key Custodian 1·2·3 중 실제 승인하는 사람 | 생성 계획과 서명할 내용을 확인하고 개인 승인키로 승인 |
| 입회자 | Independent Witness | 실제 작업을 독립적으로 관찰하고 종료 시 확인 서명. 실행·승인·접근 관리 역할을 겸하지 않음 |
| 접근 담당자 | {{성명_계정}} / {{겸임역할_또는_별도인원}} | 승인된 절차에 따라 임시 생성 접근을 열고 회수 |

참여자 성명·소속·CU 계정·승인 공개키와 입회자의 독립성은 수행 기록에 적는다. 키·백업·기록을 인수할 담당자도 시작 전에 정한다.

접근 담당자가 기존 참여자를 겸하면 본인의 종료 서명 범위에 접근 작업을 포함한다. 별도 인원이면 수행 확인서에 서명 행을 추가한다. 겸임 여부는 승인된 권한 분리에 따라 정한다.

### 작업 전에 받을 승인

- **키 생성:** Root와 First 각각의 생성 계획에 Custodian 3명 중 서로 다른 2명 이상이 서명한다. 승인 앱이 서명을 검증한 뒤 접근 담당자가 생성 접근을 연다.
- **HSM 서명:** Root 자기서명, First CSR, First 인증서마다 새 key-usage 토큰을 사용한다. Custodian 3명 중 서로 다른 2명 이상이 본문을 확인하고 토큰에 서명한다. 실행자가 명령을 실행했다는 사실만으로 승인 1명으로 세지 않는다.
- **실행 직전:** 진행자가 승인한 본문, 실제 사용할 키, 토큰, 로그인 세션, 유효 기한과 승인자를 확인한다. 승인 없이 직접 실행할 수 있는 경로를 허용하지 않는다.

### 작업 결과를 남기는 방법

행사 자료를 보관할 폴더 하나를 정하고 그 안에 `record.md`와 `evidence/`를 둔다. 별도의 단계별 폴더를 만들 필요는 없다.

1. **실행자는 명령과 결과를 남긴다.** CLI에서 실행한 명령과 출력이 로그 파일에 저장되도록 기록을 시작한다. 작업에 사용한 승인 파일, 서명할 본문, HSM 응답, 완성된 CSR·인증서도 `evidence/`에 보관한다. 파일명에는 단계와 내용을 붙인다.
2. **진행자는 파일을 확인하고 표에 적는다.** 저장된 파일을 열어 해당 작업의 결과인지 확인한다. 수행 기록의 증거 목록에 파일명·경로·SHA-256을 적고 `E001`처럼 번호를 붙인다. 계속 기록 중인 로그는 ID·경로만 등록하고 해시 칸에 `기록 중`을 적는다. 로그 해시는 A4에서 기록을 끝낸 뒤 확정한다. 단계별 기록에는 파일 번호와 결과를 적는다.
3. **입회자는 실제 수행을 관찰한다.** 관찰하지 못한 구간이나 절차와 달랐던 점은 진행자에게 알리고 기록에 남긴다. 단계마다 별도 입회 서명을 받지는 않는다.

예를 들어 First CSR을 만들었다면 `evidence/A3.3-first.csr.der`를 보관한다. 이 파일을 증거 목록에 `E021`로 등록했다면 A3.3 행에 `CSR 생성 성공 / E021`을 적는다. 승인 파일·서명 응답도 각각 등록한다. 같은 행에 `E003, 120–148행`처럼 해당 명령과 결과가 있는 로그 위치를 적는다. **이 파일명과 번호는 예시이며 실제 보관한 파일을 기준으로 작성한다.**

출력이 화면에만 있으면 해당 내용을 그대로 파일에 저장하고, 전체 세션 로그의 어느 부분에서 가져왔는지 적는다. 실패 메시지도 보존한다. 비밀번호·개인키는 기록하지 않는다. 로그나 결과 파일이 저장되지 않았거나 성공 여부를 알 수 없으면 다음 생성·서명을 멈춘다.

서명에 사용한 토큰 원문은 HSM 작업 성공 후 승인 증거로 보관한다. 중단한 경우에도 원문을 보존한다. 토큰의 사용 권한은 작업 성공·세션 종료로 무효화하고, 보관본 확인 후 작업용 사본만 삭제한다.

## A1 시작 확인

진행자가 다음 사항을 확인한다.

1. 행사 수행 승인이 있고, 사용할 스크립트·명령·설정이 승인본과 일치한다. 실행 부록 `commands.md`의 파일명·버전·해시가 모두 기입되어 있고 실제 파일과 일치하는지 확인한다. 빈칸이나 불일치, 환경·통제·복구 검토의 미해결 사항이 있으면 시작을 보류한다.
2. 참여자와 계정·승인키가 명단과 일치한다. 입회자의 소속·담당 업무, 실행·승인 관여 여부, 실행팀과의 지휘·평가 관계를 기록하고 진행자가 독립성을 확인한다. 입회자가 실제 화면과 작업을 관찰할 수 있는지도 확인한다.
3. 접속 환경과 접근 제한이 승인한 구성과 같다. 자료를 보관할 폴더가 준비되어 있다.
4. 실행자가 로그 기록을 시작한다. 진행자는 환경 조회 결과가 실제 로그 파일에 저장되는지 확인한다.

**기록:** 시작/보류 판정, 승인 자료, 참석자, 환경 확인 결과, 입회 시작 시각과 로그 파일 위치를 A1 행에 적는다. 시작 조건이 충족되지 않으면 보류한다.

## A2 Root 생성·발급

### A2.1 Root 생성 승인

1. 실행자가 Root 생성 계획과 사용할 명령을 제시한다.
2. 승인자 2명 이상이 계획에 서명한다. 진행자가 앱의 서명 검증 결과와 실제 입력을 확인한다.
3. 접근 담당자가 Root 키를 생성할 수 있도록 임시 접근을 연다.

**기록:** 계획 ID·해시, 실제 승인자, 승인 서명·검증 결과, 접근을 연 담당자와 시각.

### A2.2 Root 키 생성과 확인

1. 실행자가 Root 키를 생성하고 생성 응답, 키 ID, 공개키와 키 조회 결과를 저장한다.
2. 진행자가 알고리즘·보호 속성·소유자·공유 사용자·quorum·HSM 노드 상태와 공개키가 승인한 내용에 맞는지 확인한다.
3. 접근 담당자가 임시 생성 접근을 회수한다. 진행자는 회수 결과와 키 보호 상태를 확인하고 백업 확인 담당자에게 신규 키를 알린다.

**기록:** Root 키 ID·공개키 지문, 설정 검사 결과, 접근 회수와 보호·백업 확인 상태.

### A2.3 Root 인증서 서명

1. 실행자가 승인 설정과 Root 공개키로 서명할 인증서 본문을 만든다. 진행자가 필드·프로파일을 확인하고 serial을 예약해 중복을 검사한다.
2. 승인자 2명 이상이 본문을 확인하고 **Root 키의 새 토큰**에 서명한다. 진행자가 본문·키·토큰·세션·기한·승인을 확인한다.
3. 실행자가 Root 키로 서명 명령을 실행한다. HSM의 서명 응답을 저장하고 이를 본문에 반영해 Root 인증서를 완성한다.

**기록:** 본문 해시, serial, 실제 승인자와 승인 파일, 서명 응답, Root 인증서 파일.

### A2.4 Root 인증서 검사

1. 진행자가 독립 검증 도구로 자기서명, 승인 본문과의 일치, HSM 공개키와의 일치, CP 프로파일을 검사한다.
2. 검사 결과와 발급 원장을 저장한다. 입회자는 실제 관찰 범위와 절차에서 벗어난 사항이 있는지 확인한다.

**기록:** 검사한 인증서와 항목별 판정, 발급 원장, 일탈 여부. 검사·파일 저장·키 보호가 확인되면 A3으로 진행한다.

## A3 First 생성·CSR·발급

### A3.1 First 생성 승인

1. 실행자가 First 생성 계획과 사용할 명령을 제시한다.
2. 승인자 2명 이상이 **First 계획에** 서명한다. 진행자가 앱의 검증 결과와 실제 입력을 확인한다.
3. 접근 담당자가 First 키 생성을 위한 임시 접근을 연다.

**기록:** First 계획 ID·해시, 실제 승인자, 승인 서명·검증 결과, 접근 활성화 담당자와 시각.

### A3.2 First 키 생성과 확인

1. 실행자가 First 키를 생성하고 생성 응답, 키 ID, 공개키와 조회 결과를 저장한다.
2. 진행자가 승인 설정·소유자·공유 사용자·quorum·HSM 노드 상태를 확인한다. Root와 다른 키인지도 확인한다.
3. 접근 담당자가 임시 생성 접근을 회수한다. 진행자는 회수 결과와 키 보호 상태를 확인하고 백업 확인 담당자에게 신규 키를 알린다.

**기록:** First 키 ID·공개키 지문, 설정 검사 결과, 접근 회수와 보호·백업 확인 상태.

### A3.3 First CSR 서명

1. 실행자가 First의 이름·공개키·요청 확장으로 서명할 CSR 본문(CertificationRequestInfo DER)을 만든다. 진행자는 내용과 HSM 공개키가 일치하는지 확인한다.
2. 승인자 2명 이상이 본문을 확인하고 **First 키의 새 토큰**에 서명한다. 진행자가 본문·키·토큰·세션·기한·승인을 확인한다.
3. 실행자가 First 키로 서명하고 HSM 응답을 저장한다. 서명을 본문에 반영해 CSR을 완성한다.

**기록:** CSR 본문 해시, First 키 ID, 승인 파일, 서명 응답, CSR 파일. CSR 검사 결과는 다음 단계에 기록한다.

### A3.4 CSR 검사와 발급 허가

1. 진행자가 독립 도구로 CSR 서명, 승인 본문·Subject·공개키·요청 확장과의 일치, CSR schema를 검사한다.
2. 요청자의 신원과 First 인증서 발급을 요청할 권한을 확인한 뒤 발급을 허가한다. CSR 서명 검사만으로 신원·권한 확인을 대신하지 않는다.
3. 다음 단계에서 사용할 CSR 원본과 해시를 확정한다.

**기록:** CSR 검사 결과, 요청자·권한 확인 자료, 발급 허가자·시각·판정.

### A3.5 First 인증서 서명

1. 실행자가 검증된 CSR의 이름·공개키와 승인 설정으로 First 인증서 본문을 만든다.
2. 진행자가 HSM·CSR·인증서의 공개키 일치, First issuer와 Root Subject의 일치, First AKI와 Root SKI의 일치, 프로파일·serial 예약/중복·상태 서비스 준비를 확인한다.
3. 승인자 2명 이상이 본문을 확인하고 **Root 키의 새 토큰**에 서명한다. 진행자가 본문·키·토큰·세션·기한·승인을 확인한다.
4. 실행자가 Root 키로 서명 명령을 실행한다. HSM 응답을 저장하고 First 인증서를 완성한다.

**기록:** 사용한 CSR와 본문 해시, serial, 실제 승인자·Root 토큰, 서명 응답, First 인증서 파일.

CSR 서명 승인과 인증서 서명 승인은 별개다. OCSP 응답자 키·인증서와 서비스는 별도 승인 절차로 준비하고 이 단계 전에 준비 결과를 확인한다.

### A3.6 First 인증서 검사

1. 진행자가 독립 검증 도구로 Root 서명, 승인 본문과의 일치, Root→First 체인, CSR 공개키와의 일치, CP 프로파일을 검사한다.
2. 검사 결과와 발급 원장을 저장한다. 입회자는 실제 관찰 범위와 절차에서 벗어난 사항이 있는지 확인한다.

**기록:** 검사한 인증서와 항목별 판정, 발급 원장, 일탈 여부.

## A4 종료 확인·서명

### 1. 결과와 보호 상태를 확인한다

- 진행자가 Root·First 키, CSR·인증서, 발급 원장과 증거 목록을 대조한다. First의 실제 serial로 상태를 조회하고 지속 운영 담당자를 확인한다.
- 실행자가 최종 키·권한을 조회하고 로그아웃한다. 접근 담당자가 임시 접근 종료를 확인한다. 진행자가 토큰 무효화와 승인 증거 보관, 남겨 둔 정상 권한, 개인 승인키와 키·기록의 보호 책임자를 확인한다.
- 백업 인수자와 접근 담당자가 실행 부록 A4 3)에 따라 백업 포함 여부, off-site 사본, 보호 상태와 관련 감사 로그의 증거를 넘긴다. 진행자는 신규 키·최종 권한이 반영됐는지 대조한다. 확인하지 못한 항목은 담당자·기한과 함께 남긴다.

### 2. 기록을 확정하고 서명한다

1. 실행자가 당일 증거 저장과 두 세션의 로그 기록을 끝낸다. 진행자는 로그의 최종 SHA-256을 증거 목록에 기입하고, 모든 증거의 경로·해시를 실제 파일과 대조한 뒤 수행 기록을 확정한다.
2. [수행 확인서](templates/signoff.md)에 스크립트·실행 부록·수행 기록의 파일명과 해시, 종료 판정을 적는다. 실행 부록의 버전·해시가 빠짐없이 확정되어 있는지 서명 전에 다시 확인한다.
3. **실제 참여자와 입회자 전원이 각자 한 번 서명한다.** 접근 담당자를 포함해 실제 참석자 명단과 서명란을 대조한다. 본인이 실제 수행·승인·관찰한 범위와 일탈 여부를 확인한다. 작업별 사전 승인 서명은 별도로 보관한다.

이 확인서는 스크립트의 서명 부속서다. 스크립트에 같은 종료 서명을 다시 받지 않는다. 종이 서명은 원본과 스캔본을, 전자 서명은 서명본과 검증 자료를 보관한다.

### 3. 보관하고 종료 상태를 남긴다

진행자가 실행 부록을 포함한 스크립트·수행 기록·서명본·증거 파일을 지정된 저장소에 보관·백업한다. 스크립트를 심사에 제공할 때도 식별된 실행 부록을 함께 제공한다. 서명 후 확인한 보관 결과는 작성자·시각과 함께 별도 기록으로 남긴다.

백업이나 로그 확인이 남으면 **후속 확인 대기**로 기록한다. 접근 종료와 보호 인계가 끝나면 입회를 마칠 수 있지만 전체 완료로 표시하지 않는다. 담당자는 실행 부록 A4 3)의 확인을 마치고 새 증거·해시를 후속 기록으로 넘긴다. 진행자는 미완료 항목이 모두 해소됐는지 확인하고 완료 판정·성명·시각을 남긴다. 서명한 원본은 고치지 않는다. 보관 확인만으로 전원 재서명하지 않으며, 새 생성·서명이 필요하면 해당 승인과 입회를 갖춘다.

## 중단과 재개

승인 부족, 잘못된 입력·키, 입회 단절, 기록 저장 실패, 결과 불명 중 하나라도 발생하면 다음 요청을 멈춘다. 진행자는 마지막으로 확인한 상태와 원문을 보존하고, 접근 담당자는 열린 임시 접근을 회수한다. 보호 책임자와 조치 내용을 기록한다.

결과를 모르는 상태에서 임의로 다시 생성·서명하거나 삭제하지 않는다. 저장된 서명 응답이 있으면 그 응답으로 파일 조립·검사만 복구한다. 원인·실제 결과·변경 영향을 확인하고 필요한 승인을 받은 뒤 남은 작업을 입회하에 재개한다. 중단 시에도 실제 수행 범위·일탈·보호 상태에 대해 확인 서명한다.

First CSR은 [PKCS #10][pkcs10] DER 형식으로 작성한다. 버전은 `0`, Subject와 공개키는 위 First 설정·생성 결과와 일치시킨다. `extensionRequest`에는 First의 Basic Constraints·Key Usage·Certificate Policies를 위 값과 critical 여부로 요청한다. AIA·SKI·AKI는 인증서 발급 시 승인 설정과 실제 키에 따라 구성한다. CSR에는 인증서의 issuer·serial·유효기간을 넣지 않는다.
