# Root Key Management System 설계 시작 가이드

작성일: 2026-09-17 KST

설계를 어디서 시작할지, 설계 문서에는 무엇을 담을지, 외부 요구사항과 팀의 결정을 어떻게 구분할지 정리한 메모다. Root CA 서명키를 예로 설명하며, 예시와 제안 자체를 프로젝트의 확정 요구사항이나 설계 결정으로 취급하지 않는다.

## 1. 문서 골격부터 시작하기

처음에는 **팀이 답해야 할 질문을 목차로 만들고, 합의되는 내용을 채워 간다.**

Root Key Management System은 암호 기술, 소프트웨어, 사람의 권한, 운영 절차가 함께 얽혀 있다. 한꺼번에 결정하려 하기보다 다음 순서로 접근한다.

**목적과 범위 → 요구사항 → 업무 흐름 → 시스템 구조 → 검증 방법**

우선 Root Key의 용도를 명확히 한다. Root CA의 서명키인지, 펌웨어 서명키인지, 다른 키를 암호화하는 최상위 키인지에 따라 세부 설계가 달라진다.

## 2. 설계 문서란 무엇인가

설계 문서는 **무엇을 만들고, 왜 그렇게 만들며, 어떻게 제대로 동작한다고 확인할지 팀이 합의하는 문서**다.

읽는 사람이 다음을 이해할 수 있어야 한다.

- 이 시스템의 목적과 책임 범위
- 반드시 만족해야 하는 조건
- 구성요소와 각각의 책임
- 정상 작업과 실패 상황에서의 동작
- 선택한 방식과 그 이유
- 아직 결정하지 못한 사항
- 구현 후 확인할 기준

예를 들어 “Root Key를 HSM에 보관한다”는 문장 다음에는 다음 내용이 필요하다.

> 누가 키를 생성하는가. 누가 서명을 요청하고 승인하는가. 승인한 내용과 실제 서명할 내용이 같은지 어떻게 확인하는가. HSM이 고장 나면 어떻게 하는가. 키가 유출됐다고 의심되면 무엇을 중단하고 교체하는가.

이 질문들에 답하면서 설계가 구체화된다.

## 3. 첫 페이지에서 시스템의 책임 범위 정하기

| 구분 | 먼저 정리할 내용 |
|---|---|
| 관리 대상 | Root CA 개인키, 인증서, 하위 CA 정보, 백업, 승인 기록 중 무엇을 관리하는가 |
| 허용하는 작업 | 키 생성, 하위 CA 인증서 서명, CRL 서명, 교체, 폐기 등 |
| 사용자와 책임자 | 요청자, 승인자, 실행자, 감사자, 사고 대응 책임자 |
| 외부 시스템 | HSM, 하위 CA, 인증 시스템, 인증서 배포처, 단말 등 |
| 책임 경계 | 단말에 새 신뢰 키를 배포하는 일까지 포함하는가 |
| 성공 조건 | 어떤 작업을 안전하게 수행할 수 있으면 첫 버전이 완성되는가 |

**개인키의 관리와, 그 공개키를 신뢰하는 쪽의 관리는 구분해서 연결해야 한다.** RFC 5280에서도 신뢰 앵커는 인증서 경로 검증에 주어지는 입력이다. 서버에서 키를 교체했다고 검증자들의 신뢰 설정까지 자동으로 바뀌지는 않으므로, 그 변경을 누가 책임지는지 정해야 한다. [RFC 5280 §6.1](https://www.rfc-editor.org/rfc/rfc5280.html#section-6.1)

## 4. 설계 문서의 기본 골격

처음에는 한 파일로 시작하고 내용이 커질 때 나눠도 된다.

| 문서 항목 | 들어갈 내용 |
|---|---|
| 1. 목적과 범위 | 만드는 이유, 관리 대상, 제공 기능, 외부 시스템과의 경계 |
| 2. 요구사항과 제약 | 적용 정책·표준, 조직 요구, 운영 환경, 예산·인력 제약 |
| 3. 보호 대상과 위협 | 키 유출, 무단 서명, 승인 내용 변조, 관리자 계정 탈취, 키 소실 등 |
| 4. 전체 구조 | 사람·관리 서비스·HSM·저장소·외부 시스템의 관계와 신뢰 경계 |
| 5. 키 수명주기 | 생성, 사용 개시, 사용, 백업·복구 정책, 교체, 사용 종료, 폐기 |
| 6. 주요 작업 흐름 | 요청 → 검증 → 승인 → 실행 → 결과 확인 → 기록, 실패·재시도 처리 |
| 7. 권한과 보안 통제 | 역할 분리, 승인 조건, 관리자 권한, 통제 우회 방지 |
| 8. 데이터와 인터페이스 | 키 식별자, 요청·승인 상태, 인증서, 감사 기록, API·HSM 연동 |
| 9. 운영과 사고 대응 | 장애 복구, 침해 대응, 승인자 부재·퇴사, 정기 점검 |
| 10. 검증과 미결정 사항 | 완료 기준, 시험 방법, 결정이 필요한 항목과 담당자 |

키 관리 검토 항목을 찾을 때는 NIST SP 800-57을 참고할 수 있다. 키 보호뿐 아니라 가용성, 백업, 복구, 침해 등도 다룬다. 다만 그 권고를 프로젝트에 어떻게 적용할지는 따로 정해야 한다. [NIST SP 800-57 Part 1 Rev.5](https://csrc.nist.gov/pubs/sp/800/57/pt1/r5/final)

## 5. 정해진 것과 팀이 결정할 것 구분하기

| 구분 | 예시 | 처리 방법 |
|---|---|---|
| 적용되는 외부 요구사항 | 인증서 프로파일, 참여 프로그램의 키 보호·감사 요구 | 적용 대상·버전·조항을 확인해서 준수 |
| 확인해야 하는 기술 제약 | HSM이 지원하는 승인 기능, 기존 단말의 알고리즘 지원 | 공식 문서와 실험으로 확인 |
| 조직이 정할 정책 | 허용 가능한 중단 시간, 운영 인력, 책임자, 예산 | 사업·보안·운영 책임자와 합의 |
| 팀이 선택할 설계 | 구성요소 분리, 작업 상태 관리, API, 승인 구현 방식 | 대안과 장단점을 비교해서 결정 |

**어떤 규격을 적용할지와 그 적용 범위가 먼저 정해져야 무엇이 의무인지 판단할 수 있다.** C2PA를 위한 시스템이라면 관련 정책과 프로그램 요구사항을 확인해야 하지만, 다른 용도의 Root Key까지 같은 조건이라고 가정해서는 안 된다.

예를 들어 다음 항목은 적용 정책이 값을 지정하지 않는 한 팀과 조직이 결정해야 한다.

- Root를 몇 개로 나눌지
- 오프라인으로 운영할지, 네트워크에 연결해서 운영할지
- 어떤 HSM을 사용할지
- 어떤 작업에 몇 명의 승인이 필요할지
- 키 사용 기간과 교체 시점을 어떻게 정할지
- 백업과 복구를 어떤 방식으로 허용할지

이 결정은 서로 영향을 준다. 승인 인원을 늘리면 운영 인력과 부재 시 처리 방법도 함께 정해야 한다. 키를 교체하려면 그 키를 신뢰하는 시스템의 전환 방법도 필요하다. 신뢰 앵커 관리 지침에서도 키 소실·침해 후 복구를 별도로 다룬다. [RFC 6024 §3.11](https://datatracker.ietf.org/doc/html/rfc6024#section-3.11)

## 6. 요구사항·설계 결정·검증 방법 연결하기

다음은 설명을 위한 예시이며 확정된 프로젝트 요구사항이 아니다.

| 구분 | 예시 |
|---|---|
| 요구사항 후보 | 운영자 한 사람이 단독으로 Root 서명을 실행할 수 없어야 한다. |
| 설계안 | 서로 다른 승인자 2명의 승인을 요구한다. 승인은 특정 서명 대상과 연결하고, 대상이 바뀌면 다시 승인받는다. |
| 결정 근거 | 내부자 오용 위험과 실제 운영 가능한 인력을 고려한다. |
| 검증 | 승인 부족, 대상 변경, 승인 재사용, 관리자 우회 시도를 차단하는지 확인한다. |
| 미확정 | 선택할 HSM과 연동 방식이 필요한 통제를 지원하는지 확인한다. |

이렇게 쓰면 “2명 승인”이 표준 요구인지, 팀의 제안인지, 구현 가능한지 확인된 결정인지 혼동하지 않게 된다.

CA를 운영한다면 인증서 정책인 **CP**, 실제 인증 업무 수행 방식을 설명하는 **CPS**, 시스템 설계 문서의 역할도 구분한다. RFC 3647은 CP/CPS 작성을 위한 틀을 제공한다. 시스템 설계에서는 해당 정책과 운영 방식을 구성요소와 제어 흐름으로 어떻게 구현할지 설명한다. [RFC 3647](https://www.rfc-editor.org/rfc/rfc3647.html)

## 7. 첫 작업과 팀 회의의 목표

첫 작업으로 **범위 1쪽과 대표 시나리오 3개**를 작성한다.

1. Root Key를 처음 생성하고 사용할 준비를 하는 과정
2. Root Key로 하위 CA 인증서 하나를 발급하는 과정
3. Root Key 침해가 의심되어 사용을 중단하고 신뢰를 전환하는 과정

각 과정에서 **누가, 무엇을 확인하고, 무엇을 승인하며, 어디서 실행하고, 실패하면 어떻게 하는지**를 적는다. 그러면 필요한 기능과 구성요소가 드러난다.

첫 팀 회의에서는 **관리할 키의 용도, 시스템의 책임 범위, 첫 버전에서 끝까지 지원할 작업**을 합의하는 것을 목표로 삼는다.
