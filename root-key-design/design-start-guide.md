# Root Key Management System 설계 시작 가이드

작성일: 2026-09-17 KST · 수정일: 2026-09-19 KST

## 1. 목적과 범위

이 가이드는 Root Key Management System에서 **무엇을 설계하고, 어떤 산출물을 남기며, 어디까지 정해야 설계가 끝나는지** 관리한다. 상세 동작은 항목별로 연결된 설계 문서에 작성한다.

대상은 Root와 중앙 관리 ICA의 운영, 하위 CA 운영 조직과의 인계, 운영 영역 간 연계, 인증서 상태 제공, 감사·복구 및 신뢰 전환이다. 실제 제품·지역·배포 환경과 현재 결정은 [요구사항과 결정 상태](requirements.md)에서 관리한다. 현재 정책 적용 사례는 C2PA이며 S09에서 추적한다.

본문에서는 다음 역할명을 사용한다.

| 역할·경계 | 의미 |
|---|---|
| 중앙 키 관리 시스템 | 중앙에서 관리하는 CA 키의 사용을 통제하고 인증서 발급·상태 관리·기록을 제공하는 시스템 |
| 하위 CA 운영 조직 | 자신의 CA 키를 관리하고 CA 인증서를 요청·수령하며 하위 인증서 발급·폐지를 운영하는 주체 |
| 승인자 | 특정 발급 요청의 인증서 내용과 사용할 CA 키를 확인하고 승인하는 권한자 |
| 운영 영역 | 계정·접근 권한·네트워크·운영 책임을 구분하는 경계. 중앙 운영 영역 밖의 연계 영역을 외부 운영 영역으로 부르며, 같은 조직 안에도 존재할 수 있다. |
| 검증 시스템 | 신뢰 설정을 사용해 인증서나 서명을 검증하는 단말·애플리케이션·서버 |

설계 문서를 읽은 사람이 **시스템의 동작, 그 이유, 남은 결정, 검증 방법**을 설명할 수 있어야 한다.

## 2. 작성 원칙

1. **항목마다 목적을 하나 정한다.** “ICA 발급 — 승인받은 인증서 내용만 서명한다”처럼 다룰 작업과 달성할 조건을 밝힌다.
2. **첫 문장에 결정이나 동작을 쓴다.** 배경은 그 선택의 이유를 이해하는 데 필요한 만큼만 붙인다.
3. **주체·조건·동작을 명시한다.** “적절히 검증한다” 대신 “실행기는 서명 직전에 승인 대상과 실제 서명할 내용을 대조한다”고 쓴다.
4. **요구사항·설계안·확정 결정·검증 결과를 구분한다.** 선택한 방식에는 이유와 중요한 제약을 붙인다. 설명용 예시는 제안으로 표시한다.
5. **미결정 사항을 실행 가능한 질문으로 남긴다.** 선택지, 결정에 필요한 증거, 결정 전 진행할 수 없는 작업을 적는다.
6. **규칙은 한 곳에 정의한다.** 승인·보존·프로파일 규칙을 여러 절차에 복사하지 않고 해당 정의를 연결한다.
7. **실패 조건은 생략하지 않는다.** 승인자 부재, 실행 중단, 결과 불명, 복구 후 불일치처럼 동작을 바꾸는 조건을 남긴다.

문장을 지웠을 때 결정·동작·이유·제약·검증 정보가 사라지지 않으면 삭제를 검토한다. “보안을 강화한다”, “안정성을 확보한다”만으로 항목을 끝내지 않는다.

초기 상태는 기존 초안이 있는 **설계 중**으로 둔다. 위 완료 기준의 충족이나 구현 시험 통과를 확인했다는 뜻은 아니다.

- **미작성:** 담당 설계 내용이 아직 없다.
- **설계 중:** 초안을 작성하거나 결정을 검토하고 있다.
- **설계 완료:** 산출물과 검증 방법을 검토했고, 해당 동작을 바꾸는 미결정 사항이 해소됐다.
- **검증 완료:** 정한 시험을 수행하고 결과·환경·버전을 기록했다. 외부 등록·승인은 별도 결과로 남긴다.

공통 구현 사항도 담당 항목에 포함한다.

- **구성·신뢰 경계 — S04:** 접수·승인 서비스, 서명 실행기, HSM, 저장소의 배치와 접근 경로, 상시·작업 시 실행 방식 선택, 개발·운영 분리.
- **데이터·인터페이스 — S03·S05·S06:** 요청 ID, 키·프로파일 버전, 요청·승인·발급·폐지 상태, API·전달 형식, 동시 실행·중복·만료 처리.
- **위협·검증 — 각 항목:** 무단 서명, 승인 후 변조, 계정 탈취, 기록 소실 등 해당 작업의 위협을 통제와 거부 시험에 연결한다. 시험 증거는 S08의 기록 정책으로 보존한다.

개인키 복구(S08), 인증서 폐지(S05), 검증자에게서 구 공개키의 신뢰를 제거하는 작업(S07)은 각각의 절차와 연결 지점을 정한다. 신뢰 앵커는 인증서 경로 검증의 입력이므로, 서버의 키 변경과 검증자의 신뢰 설정 변경을 함께 설계해야 한다. [RFC 5280 §6.1](https://www.rfc-editor.org/rfc/rfc5280.html#section-6.1)

## 4. 작업별 문서에 남길 내용

S02·S03·S05·S07·S08의 절차는 아래 항목으로 작성한다. S01의 계층도, S04의 권한표, S09의 대응표처럼 표나 그림이 적합한 산출물은 그 형식을 사용한다.

| 항목 | 적을 내용 |
|---|---|
| 목적·결정 | 달성할 조건과 선택한 방식, 선택 이유 |
| 입력·시작 조건 | 요청 데이터, 요청자 권한, 필요한 시스템·키 상태 |
| 정상 흐름 | 주체별 확인·승인·실행 순서와 결과 |
| 거부·중단·재시도 | 거부 조건, 중단 후 상태, 결과 불명 시 확인·재개 방법 |
| 데이터·증거 | 저장할 식별자·상태·결과·승인 기록과 참조할 보존 정책 |
| 검증 | 구체적인 시험 입력과 기대 결과 |
| 미결정 | 선택지, 필요한 확인, 영향받는 작업, 결정 담당 역할 |

예를 들어 S03에는 다음 수준의 문장을 쓴다. 아래는 **작성 예시인 설계안**이다.

1. 하위 CA 운영 조직이 CSR, 인증서 용도, 요청 유효기간을 제출한다.
2. 중앙 키 관리 시스템이 요청 권한과 CSR·프로파일을 검증하고, 발급할 인증서 내용과 사용할 CA 키 버전을 확정한다.
3. 서로 다른 승인자 최소 2명이 동일한 발급 내용을 확인하고 승인한다.
4. 실행기가 승인 대상과 실제 서명 대상을 대조한 뒤 HSM의 발급 CA 키로 서명한다.
5. 중앙 키 관리 시스템이 결과 인증서를 검증하고 요청·승인·발급 기록을 연결한 뒤 하위 CA 운영 조직에 전달한다.

인증서 내용이나 CA 키 버전을 바꾸면 기존 승인을 무효화한다. 서명 중 연결이 끊기면 결과 확인 상태로 두고, 기존 실행 결과를 확인하기 전에는 재실행하지 않는다.

이 예시를 상세 설계로 채울 때는 비교할 데이터의 표현, 승인 기록 보호, 상태 저장 방식, 결과 확인 수단까지 정한다. “내용을 대조한다”는 문장만으로 관리자 우회까지 차단됐다고 판단하지 않는다.

## 5. 작성 순서

| 단계 | 작성할 항목 | 다음 단계에 넘길 결정 |
|---|---|---|
| 1. 범위·제약 정리 | S01·S09, S07의 기존 검증 시스템 제약 조사 | CA 계층, 관리·신뢰 경계, 적용 요구사항, 교체 가능한 대상 |
| 2. 생성·사용 통제 정리 | S04·S02 | 권한·승인 구조, HSM·실행기 경계, 키 생성·사용 허용 조건 |
| 3. 발급·인계 정리 | S03·S06 | 승인된 입력에서 인증서 수락까지의 흐름·상태·입출력 계약 |
| 4. 운영·실패 처리 정리 | S05·S08 | 폐지·상태 제공, 감사 증거, 장애 복구, 변경·종료 조건 |
| 5. 신뢰 전환·전체 검토 | S07 상세화, S01–S09 대조 | 정상·침해·알고리즘 전환 절차와 전체 검증 계획 |

운영·복구·교체에서 앞선 구조의 문제가 드러나면 해당 단계의 결정을 수정한다. 모든 단계에서 정상 흐름과 함께 거부·중단·복구 시나리오를 작성한다.

첫 검토에서는 범위 1쪽과 **키 최초 생성, ICA 한 건 발급, 키 침해 후 신뢰 전환**의 흐름을 작성한다. 이 세 흐름으로 역할·인터페이스의 공백을 찾고 항목표에 반영한다.

## 6. 외부 요구사항과 팀의 결정

| 구분 | 기록할 내용 |
|---|---|
| 외부 요구사항 | 공식 원문의 버전·조항, 적용 대상, 의무 수준, 설계·검증 위치 |
| 기술 제약 | HSM·실행 환경·검증 시스템·SDK 버전, 확인한 제한, 확인 방법과 결과 |
| 조직 정책 | 운영 인력, 중단 허용 시간, 예산, 책임과 승인 역할 |
| 설계 결정 | 선택한 방식, 이유, 주요 대안과 제약, 영향받는 항목 |

알고리즘, 인원수, 기간, 복구 목표 등은 외부 요구인지 조직·팀의 선택인지 표시한다. 기존에 확정한 항목은 그 결정을 연결하며, 변경하려면 사유와 영향을 남긴다.

참고 자료는 다음 용도로 사용한다.

- [NIST SP 800-57 Part 1 Rev.5](https://csrc.nist.gov/pubs/sp/800/57/pt1/r5/final): 키 보호·수명주기·백업·복구의 검토 항목. 프로젝트에 채택할 조건을 구분한다.
- [RFC 6024 §3.11](https://datatracker.ietf.org/doc/html/rfc6024#section-3.11): 신뢰 앵커 키 소실·침해 후 복구 검토.
- [RFC 3647](https://www.rfc-editor.org/rfc/rfc3647.html): CP/CPS의 정책·운영 항목 확인. 해당 정책과 운영 방식을 시스템 동작에 연결한다.
- [원문 자료 안내](../references/root-key-sources.md): C2PA 등 원문의 위치와 버전 확인. 사실 근거는 연결된 공식 원문에서 확인한다.

## 7. 누락과 완료 확인

요구사항이 추가되면 담당 설계 항목을 연결한다. 기존 9개 항목에 들어가지 않으면 새 번호를 추가한다. 범위에서 제외하는 요구는 사유와 인계할 시스템·역할을 기록한다.

완료 검토에서는 **요구사항 → 설계 항목 → 동작·통제 → 검증 방법·결과**가 이어지는지 확인한다. 상세 문서가 존재한다는 이유만으로 완료 처리하지 않는다. 문서·범위·구현이 바뀌면 영향받는 항목의 완료 여부를 다시 검토한다.
