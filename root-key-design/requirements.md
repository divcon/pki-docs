# 요구사항과 결정 상태

기준: 2026-09-16 KST 사용자 대화와 초기 메모 및 공식 원문 검토. 사용자 결정, 표준에서 도출한 조건, 설계 제안과 검증 과제를 구분한다. 이 기록은 표준 적합성의 증명이 아니다. 원문 근거는 [자료 목록](../references/root-key-sources.md)에서 별도로 관리한다.

## 사용자 확정 사항

| ID | 요구사항 | 설계에 미치는 영향 |
|---|---|---|
| R01 | 플랫폼 Root는 서비스·기기 플랫폼의 ICA 인증서를 발급한다. 첫 대상은 C2PA다. | 콘텐츠 서명과 CA 서명을 분리한다. |
| R02 | Global과 CN은 동일한 Root 키를 공유한다. CN에 별도 CloudHSM은 구축하지 않는다. | 중앙 보관·서명 후 공개 인증서 전달. Root 개인키의 CN 복제를 의미하지 않는다. |
| R03 | CA 발급은 저빈도이며, 일상 발급 시 Global Root와 CN 사이의 실시간 호출 의존성을 두지 않는다. | CSR·인증서의 비동기 반입·반출 경로는 필요하다. 상태 정보·신뢰 목록 배포는 별도 설계한다. |
| R04 | Root 개인키는 AWS CloudHSM에서 관리한다. | 중앙 First ICA까지 동일 보관 원칙을 적용하는 안을 제안한다. Phone/TV가 운영하는 하위 CA의 키 보관은 인계 요구사항으로 다룬다. |
| R05 | Root → C2PA First ICA → Phone/TV Issuing ICA → leaf 구조를 사용한다. | Root pathLen=2, First=1, 최종 Issuing ICA=0. First ICA의 Trust List 등록을 목표로 한다. |
| R06 | C2PA CP는 공통 운영 정책의 주요 참고 자료로 사용한다. Root에는 필요한 통제를 선별 적용한다. | C2PA 참여 범위의 의무와 범용 플랫폼 Root에 자율 채택할 통제를 구분한다. |
| R07 | Root·First ICA를 통한 ICA 발급에는 최소 2인의 통제가 필요하다. | 구현 대안과 C2PA 요구사항의 충족 근거를 비교한다. 특정 방식은 아직 미확정이다. |
| R08 | Phone TSA는 on-device다. TV에는 TSA ICA를 발급하고 TV가 서버/on-device 구현을 선택한다. | 시간 신뢰·시계 오차 관리는 각 플랫폼 책임이다. 중앙은 발급·인계 경계와 필요한 증빙을 정의한다. |
| R09 | CRL은 발행하지 않고 OCSP만 사용한다. | 발급 CA별 OCSP 위임, 응답자 키·인증서 교체, 상태 배포 및 장애 정책을 설계한다. |
| R10 | 단말에 탑재된 Root의 교체와 향후 양자내성 알고리즘 전환을 설계한다. 현재 갱신 수단은 FOTA다. | 신뢰 데이터 갱신과 검증 코드·보안 부팅 기능 갱신을 구분한다. |
| R11 | 운영 책임자·승인 조직의 실제 지정은 보류한다. | 역할과 필요한 권한만 정의하고 조직명·인명은 정하지 않는다. |

## 원문 검토로 추가한 필수 조건

아래는 사용자의 새 결정이 아니라 C2PA CP v0.2와 Program에서 도출한 적용 조건이다. C2PA 참여 CA·제품에 해당하는 범위에 적용한다. 범용 G0에 공통 정책으로 채택한 항목은 [운영 모델](operating-model.md)에 별도로 표시하며, G0의 공식 적용 범위(V01)를 확정한 것으로 취급하지 않는다.

| ID | 조건 | 설계 위치 |
|---|---|---|
| N01 | 해당 CA가 이미 인증서를 발급한 키 쌍으로 새 인증서를 발급하지 않는다. Subscriber re-key는 신규 신청과 같은 검증을 거친다. | [새 키로 교체](operating-model.md#rekey) |
| N02 | CP 아래 발급한 모든 인증서의 기록을 각 인증서 만료 후 최소 1년 보존한다. serial·subject·유효기간·확장과 값·폐지 상태를 포함한다. | [기록 보존](operating-model.md#records) |
| N03 | Claim 인증서의 OCSP 응답은 필수 기록 보존 기간까지 제공한다. CRL을 사용하지 않으므로 하위 CA·TSU 인증서에도 OCSP를 제공한다. | [OCSP 운영](operating-model.md#ocsp) |
| N04 | 공식 CA 키 백업·복구 계획을 매년 검토한다. 모든 백업을 원본과 같은 다인 통제로 보호하고 off-site 사본을 유지한다. CA 개인키의 장기 아카이빙은 하지 않는다. | [백업·복구](operating-model.md#backup) |
| N05 | TSA의 시간 추적성·선언 정확도·오차 초과 시 발급 중단·전용 키·허용 해시를 적용한다. On-device는 TEE 실행·키 생성·보관 및 적어도 24시간마다 온라인 동기화 시도가 필요하다. Backend는 별도의 TSU 암호 장치 기준을 따른다. | [TSA 인계](operating-model.md#tsa-handoff) |
| N06 | 발급·폐지·접근·해당 시 attestation 검증 등을 감사하고, 기록 보호·정기 검토·검색·복원 절차를 둔다. 사업 관행은 공개 CPS 또는 C2PA와 협의한 다른 방법으로 고지한다. | [기록·공개 정책](operating-model.md#records) |
| N07 | Claim 발급의 제품 자격·Assurance Level·해당 시 Dynamic Evidence, Subscriber 식별·동의 및 키 생성·용도 제한을 하위 CA에 인계한다. CP의 폐지 사유를 처리할 경로를 둔다. | [발급 인계](operating-model.md#issuance), [폐지](operating-model.md#revocation) |
| N08 | Trust List 등록 증빙에는 인증서 프로파일 검증과 독립 입회한 키 생성 ceremony의 서명된 script를 준비한다. Program의 WebTrust 대체 증빙 예외는 해당 조건이 확인된 경우에만 사용한다. | [2인 통제 및 생성 증빙](dual-control-options.md#c2pa-controls) |

근거 조항과 실제로 남은 검증은 [C2PA 요구사항 대응표](c2pa-requirements-matrix.md)에 연결한다. 위 목록은 CP 전체 의무를 빠짐없이 열거한 목록이 아니다.

## 제안과 확인 사항

| ID | 상태 | 내용 |
|---|---|---|
| D01 | 설계 제안 | Claim용 First와 TSA용 First는 별도 키·인증서를 사용한다. Root는 공유한다. |
| D02 | 설계 제안 | CloudHSM HSM 다인 승인 + 작업 시 실행하는 서명 환경을 우선안으로 한다. 2-of-3은 부재 대응을 위한 제안값이다. |
| D03 | 설계 제안 | OCSP는 각 발급 CA가 직접 발급한 응답자 leaf 인증서를 사용한다. 일반적인 OCSP ICA는 만들지 않는다. |
| D04 | 설계 제안 | CA 키와 독립된 업데이트 권한으로 변경 가능한 신뢰 저장소를 관리한다. |
| D05 | 설계 제안 | 운영 절차·복구·교체·감사 설계는 에이전트가 초안을 작성한다. 사용자에게 구현 방법의 선결정을 요구하지 않는다. |
| V01 | 해석 미확인 | 사용자는 미등록 상위 Root가 C2PA 준수 범위 밖이라는 문구를 본 것으로 설명했다. 검토한 CP/Program v0.2에서 포괄적인 운영 책임 면제 문구는 찾지 못했다. 등록 증빙 범위·검증 경로·운영 의무를 구분하여 기록한다. |
| V02 | 외부 원문 정합성 검증 | TSA Issuing CA 프로파일의 Issuer Name 설명은 Root CA를 언급하지만 AKI 설명은 root/intermediate를 허용한다. First→TSA Issuing ICA 구조의 공식 프로파일 적용 해석을 확인한다. |
| V03 | 구현 검증 | 선택한 HSM/SDK/CLI/알고리즘에서 quorum, 인증서 서명 인코딩, 우회 차단·복구 후 통제가 동작하는지 확인한다. |
| V04 | 단말 조사 | Root/First 공개키가 어디에 저장되고 어떤 검증자가 사용하는지, 저장소·검증 코드·부팅 키를 각각 갱신할 수 있는지 확인한다. |
| V05 | 구현 검증 | PQC는 HSM 지원, C2PA 프로파일, 단말 검증기, 업데이트 신뢰 경로 각각의 지원을 따로 확인한다. |

## 범위

중앙 설계는 Root/First 운영, 하위 CA 인계 조건, 중앙 발급 인증서의 상태 제공, 감사·복구, 신뢰 앵커 배포 및 교체 절차를 포함한다. Phone/TV의 TSA 구현이나 시계 동기화 알고리즘은 구현하지 않는다. 다만 인계 이후의 인증서 상태 제공·기록 보존·사고 통보와 필수 TSA 조건의 증빙이 빠지지 않도록 인터페이스·책임 경계를 명시한다.

Lambda는 사용자 확정 요구사항이 아닌 실행 환경 후보다. 발급 빈도가 낮다는 사실만으로 실행 시간·세션 유지·다인 승인 지원을 가정하지 않는다.
