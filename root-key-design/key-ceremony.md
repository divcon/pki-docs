# Root·공용 First ICA Key Ceremony

Root와 공용 First ICA의 키를 새로 만들고, Root 자기서명 인증서와 Root가 서명한 First 인증서를 발급한다. 두 개인키는 Global의 AWS CloudHSM에 보관한다. 하위 Issuing ICA는 이번 생성·감사 범위 밖이며, 이후 관리·발급 대상으로 유지한다.

**현재는 절차 설계안이다.** 키 생성 통제, 운영 파라미터, 담당자·입회자와 실행 도구가 미정이므로 운영 키 생성 준비는 끝나지 않았다. 확정된 구성은 [요구사항](requirements.md), 기술 통제는 [다인 통제](dual-control-options.md), 구현 기능은 [CA 앱](ca-software-requirements.md)에서 관리한다.

## 진행 절차

여기서 **스크립트**는 참여자, 명령, 입력값, 기대 결과, 중단 조건을 적은 실행 절차서다. 자동화 프로그램의 유무와 관계없이 필요하다. 아래는 여섯 작업 구간의 실행 순서다. 각 번호는 하나의 작업이며, 실제 도구와 담당자에 맞춰 구체화한다.

### 1. 생성 계획을 승인한다

1. 운영 담당자는 Root·First의 키 설정을 정한다.
2. 운영 담당자는 Root·First 인증서에 넣을 값을 정한다.
3. 운영 담당자는 스크립트를 작성한다.
4. 승인자는 적용 정책, 역할 분담, 생성·서명 통제와 증거 수집 방법을 확인한다.
5. 승인자는 생성 계획과 행사 수행을 승인한다.

- 준비할 것: 아래 [생성 전 확인](#생성-전-확인)의 설정표, 참여자 역할표, 스크립트.
- 남길 것: 승인된 문서 버전과 행사 수행 승인.

### 2. 테스트 키로 전 과정을 연습한다

1. 실행자는 운영과 구분된 테스트 환경을 준비한다.
2. 실행자는 테스트 키로 아래 Root·First 생성·발급 절차를 연습한다.
3. 실행자는 승인 부족, 본문 변조, 직접 HSM 접근, 관리자 우회, 연결 단절과 저장 실패를 시험한다.
4. 담당자는 시험에서 발견한 문제를 해결한다.
5. 담당자는 운영 환경의 도구·설정을 고정한다.

- 준비할 것: HSM 연결, 발급 도구, 권한 설정, 로그·증거 저장소.
- 남길 것: 환경·모듈 확인 자료, [통제 시험](dual-control-options.md#검증-기준)과 [앱 기능 시험](ca-software-requirements.md#기능-검증)의 결과.

### 3. 당일 참여자와 환경을 확인한다

1. 시작 판정 담당자는 실행자·승인자·독립 입회자의 참석을 확인한다.
2. 실행자는 승인된 스크립트·설정과 실제 환경을 대조한다.
3. 독립 입회자는 입회를 시작한다.
4. 기록 담당자는 로그 수집을 시작한다.
5. 시작 판정 담당자는 필수 통제와 기록 준비 상태를 확인한다. 빠진 항목이 있으면 중단한다.
6. 시작 판정 담당자는 키 생성 시작을 승인한다.

- 준비할 것: 개인별 계정, 역할·권한 확인, 입회자 독립성 확인, 시작 판정 담당자.
- 남길 것: 참석·환경 점검 결과, 시작 승인, 입회·로그 기록.

### 4. Root 키와 자기서명 인증서를 만든다

1. 실행자는 다인 통제 아래 HSM 안에서 Root 키를 생성한다.
2. CA 앱은 Root 인증서 본문을 구성한다.
3. 승인자들은 인증서 내용과 사용할 Root 키를 확인한다.
4. 승인자들은 Root 인증서 서명을 승인한다.
5. 실행자는 Root 서명 명령을 명시적으로 내린다.
6. HSM은 Root 키로 인증서 본문에 서명한다.
7. 앱은 서명 결과를 결합해 Root 인증서를 조립한다.
8. 앱은 Root 인증서의 자기서명을 검증한다.

Root 인증서 서명에는 신뢰 역할 담당자 최소 두 명이 참여해야 한다. [CP Certificate Issuance][issuance]

- 필요한 기능: 키 생성·식별, 인증서 구성, 승인, HSM 서명, 결과 검증.
- 남길 것: 생성 로그, 공개키 지문·HSM 키 식별자·속성, 승인 본문과 서명 기록, Root 인증서·검사 결과.

### 5. First 키 생성과 인증서 발급

1. 실행자는 다인 통제 아래 Root와 별개의 First 키를 HSM 안에 생성한다.
2. 앱은 First CSR의 본문을 구성한다.
3. 승인자들은 CSR 서명을 위한 First 키 사용을 승인한다.
4. 앱은 HSM에 First 키로 CSR 서명을 요청한다.
5. HSM은 First 키로 CSR 본문에 서명한다.
6. 앱은 서명 결과를 결합해 First CSR을 완성한다.
7. 앱은 CSR 서명·공개키·요청 내용을 검사한다.
8. 앱은 First 인증서의 최종 본문을 구성한다.
9. 승인자들은 First 인증서 내용과 사용할 Root 키를 확인한다.
10. 승인자들은 Root 키를 통한 First 인증서 서명을 승인한다.
11. 실행자는 Root 서명 명령을 명시적으로 내린다.
12. HSM은 Root 키로 First 인증서 본문에 서명한다.
13. 앱은 서명 결과를 결합해 First 인증서를 조립한다.
14. 앱은 First 인증서의 서명을 검증한다.
15. 앱은 Root → First 연결을 검증한다.

Root 서명에는 앞 구간과 동일한 최소 2인 참여·명시적 실행 통제를 적용한다.

- 필요한 기능: 키 생성, CSR 생성·검증, 인증서 구성·승인·발급.
- 남길 것: First 생성 로그·키 설정, CSR, 승인·서명 기록, First 인증서·체인 검사 결과.

### 6. 결과 확인과 운영 인계

1. 검증 담당자는 승인한 내용과 결과 인증서가 일치하는지 확인한다.
2. 검증 담당자는 생성 로그와 공개키가 일치하는지 확인한다.
3. 참여자·입회자는 실제 수행 결과와 절차 이탈을 확인한다.
4. 참여자·입회자는 스크립트에 서명한다.
5. 운영 담당자는 키·기록·백업의 관리 책임을 인수한다.
6. 운영 담당자는 임시 권한을 회수한다.
7. 운영 담당자는 세션을 종료한다.

- 필요한 기능: 증거 취합, 일탈 처리, 완료 확인, 보관·인계.
- 남길 것: 서명된 스크립트, 증거 목록, 최종 검사 결과, 인수·접근 종료 기록.

필수 검사나 증거가 빠지면 완료·배포를 보류한다. Ceremony 완료, 운영 준비, 감사, Trust List 등록은 각각 확인한다.

## 생성 전 확인

CP §6.1.1은 안전한 생성 환경, 신뢰 역할 담당자의 다인 통제·지식 분리, 적격 암호 모듈, 입회 및/또는 기록, 생성 로그와 상세 스크립트를 요구한다. 등록 대상 First에는 Program의 **독립 입회한 키 생성과 서명된 스크립트** 증거도 준비한다. 녹화만으로 등록 증거를 대신하지 않는다. WebTrust 보고서 대체는 해당 보고서가 ceremony·스크립트의 적합성을 입증하는 조건에서만 검토한다. [CP 키 생성][generation] · [Program][program]

| 준비 항목 | 실행 전에 고정·확인할 내용 |
|---|---|
| 적용 기준 | CP·Program·프로파일 버전, Root/First별 적용 조항, 등록할 신뢰 목록. 미등록 상위 Root의 적용 범위는 별도 확인 |
| HSM·실행 환경 | 모델·모드·인증 범위, 클러스터, 호스트·네트워크, 도구 버전, 테스트/운영 구분, 로그·시간 설정 |
| 키 생성·사용 통제 | 개인별 계정, 생성용 자격증명과 호스트 접근 통제, 키별 소유·공유 권한, N-of-M, 관리자 우회 차단, 개인별 승인 키 보호 |
| 행사 운영 | 실행·승인·기록·검증 역할, 독립 입회자, 시작·중단·재개·완료 판정자, 스크립트와 활성화 재료 목록 |
| 생성 직후 보호 | 키·활성화 재료의 접근 통제, 증거 저장·변경 권한·보존 기간, 백업 식별·보관·인수 책임 |

생성 모듈의 CP 기준은 FIPS 140-2 Level 2 이상, FIPS 140-3 Level 2 이상 또는 적절한 CC PP/ST EAL 4 이상이다. 보관·사용 조항의 기준은 별도로 대조한다. CloudHSM 제품명만으로 적격성을 판단하지 않는다. [CP 키 보호][keys]

**키 생성 명령 자체의 CloudHSM quorum은 지원 목록에 없다.** 생성 때 지정하는 quorum은 이후 키 사용·관리의 통제다. 생성용 계정·실행 환경의 통제안과 우회 시험을 먼저 완료해야 한다. [AWS 지원 작업][aws-services]

### 키·인증서 설정표

| 항목 | 결정·검사할 내용 |
|---|---|
| 알고리즘·키 속성 | 적용 CA 프로파일의 RSA 3072 이상 또는 EC P-384/P-521 안에서 선택. 해시·서명 방식, 비추출 설정, 용도·라벨·권한과 quorum 지정 |
| 이름·기간·일련번호 | Root/First의 C·O·CN, 유효기간, 양의 serial 최대 20 octets. Root 20년·First 5년은 원문의 예시이며 확정값이 아님 |
| 인증서 확장 | X.509 v3, SKI/AKI, KU/EKU, Basic Constraints, 정책 OID, 확장별 critical 여부. 계층 설계는 Root pathLen=2, First=1 |
| 상태 조회 | Root의 AIA/CDP는 금지. First는 OCSP 전용 운영에 맞는 HTTP AIA 주소와 서비스 책임 확정. CRL 미사용이어도 프로파일의 cRLSign 비트 유지 |
| CSR·발급 요청 | PKCS#10 인코딩, 요청자 권한·발급 허락·정보 확인 자료, 공개키·CSR 서명 검증, 허용 확장 목록. CSR 확장을 그대로 복사하지 않음 |
| 검사 결과 | 승인 본문·공개키·서명·issuer·체인·기간·확장을 독립 검증. 정책과 schema 차이는 검사 결과와 함께 기록 |

[Root 프로파일][root-profile]과 [First 프로파일][first-profile]을 기준으로 값을 확정한다. Root AKI의 선택/필수 차이, First AKI 문구, AIA의 caIssuers 검사 차이는 [분석의 해석 확인 사항](conformance-analysis/05-design-inputs-and-open-questions.md)에 남아 있다. Claim/TSA 하위 적용은 [운영 모델](operating-model.md#hierarchy)에서 확인한다. 미해결 프로파일로 운영 인증서를 발급하지 않는다.

## 증거 보관과 중단 처리

한 작업 ID로 승인된 스크립트·설정·도구 버전, 참여 역할, 단계별 수행자·시각·결과, HSM·키 식별자, 공개키·CSR·인증서 지문, 승인한 본문 해시, 프로파일·serial, 입회·로그 참조, 일탈 처리와 최종 서명을 연결한다. 비밀번호·개인키·승인용 비밀은 기록하지 않는다. 발급 기록과 나머지 증거의 보존 기간은 [기록 정책](operating-model.md#records)을 따른다.

| 상황 | 처리 |
|---|---|
| 권한·CSR·프로파일 오류, 승인 부족 | 실행 전에 거부하고 원인을 기록 |
| 승인 후 본문·키·설정 변경 | 기존 승인 무효화, 재검토 |
| 세션 종료·단절, 승인 기한 경과 | 중단 후 작업 상태 확인. 재개 승인과 필요한 새 토큰 확보 |
| 생성·서명 결과 불명, HSM 성공 후 저장 실패 | 기존 키·결과·원장 대조 전 자동 재생성·재서명 금지 |
| 키 생성 후 중단 | 생성한 키의 사용을 제한하고 재사용·폐기 판단을 기록 |
| 인증서 불일치·필수 증거 누락 | 완료·배포·등록 제출 보류, 원인과 일탈 처리 |
| 생성 당시 통제·입회를 입증할 수 없음 | 당시 자료와 인정 가능한 대체 증거를 확인. 해소할 수 없으면 새 키 생성·ceremony 재수행 필요성 판단 |
| 보고서·색인·제출 묶음만 미완성 | 원래 증거로 보완. 문서 누락만으로 자동 재생성하지 않음 |

생성 당시 없었던 통제·입회 사실을 사후 문서로 만들 수는 없다. 재생성 가능성은 이 제약에서 도출한 위험 판단이며, 원문이 모든 서류 누락에 재생성을 명령하는 것은 아니다. 개인키 노출·부적격 환경은 [사고·복구 절차](operating-model.md#backup)로 처리한다. 발급 인증서의 내용 오류는 [동일 키 재발급 금지](operating-model.md#rekey)도 확인한다.

## 남은 결정과 운영 인계

| 결정할 것 | 확정할 결과 |
|---|---|
| 배치·구현 | 같은 클러스터 사용 여부, 실행 호스트, 서버/스크립트 형태, CLI 실행 주체, 원장·증거 저장 방식 |
| 권한·다인 통제 | N/M과 실행자 승인 포함 여부, 생성·관리자 통제, 승인 키 보관·교체·회수, 우회 시험 결과 |
| 프로파일·요청 계약 | 위 설정표의 실제 값, 상태 조회 주소, 요청·검사 규칙과 원문 차이의 처리 |
| 행사·증거 | 담당자·입회 방식·일정, 실행 명령과 입력값, 보존·완료·재개·재생성 판단 책임 |
| 운영·감사·등록 | 조항별 적용·담당·절차·증거·미비점 연결, 공개 정책·OCSP·백업·등록 자료의 완료 시점 |

발급·폐지·상태 제공, 인력·권한·변경 관리, 기록 검토, 백업·복구와 등록 준비는 [운영 모델](operating-model.md)과 [요구사항 대응표](c2pa-requirements-matrix.md)로 인계한다. 키 보호와 백업 책임은 생성 직후부터 이어져야 한다.
